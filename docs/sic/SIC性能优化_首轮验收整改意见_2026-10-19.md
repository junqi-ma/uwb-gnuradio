## 2. PERF-R01：修复自能量缓存的浮点坐标等价问题

### 2.1 发现与影响边界

位置：`gr-uwb/lib/uwb_preamble_sic_core.cc`，受检版约 716–740 行 `fill_self_energy_table`，以及约 1684 行起的 `rel_index` 命中逻辑。

缓存以 `w0=0, tau=rel+delta` 构造模板；实时搜索以 `w0=fit_lo, tau=fit_lo+rel+delta` 构造模板。代码注释认为整数平移后两者相同，但浮点加法不严格满足该性质。绝对起点较大时，`select_phase` 得到的插值权重可变化。

在本机，用当前实际 `build_shifted_f` 和相同 VOLK 自点积，对同一复数重复模板检查 108×21=2268 个候选：

| origin | 候选模板逐字节不同数 | 自能量不同数 | 最大能量绝对差 |
|---:|---:|---:|---:|
| 1997 | 0 | 0 | 0 |
| 122000 | 0 | 0 | 0 |
| 2000000 | 0 | 0 | 0 |
| 16777216 | 1728 | 954 | 0.0009765625 |

这证明的是**缓存分母与实际候选列可能不匹配**，不是已经证明当前 A/B 窗口发生误码或输出退化。该测试使用泛用复数重复模板，不冒充 canonical Ipatov 波形。不能据此否认已验证的 A/B 一致性，也不能再无条件宣称此缓存适用于所有整数起点且 E0。

### 2.2 可执行复现

附件：`docs/sic/review/sic_perf_self_energy_coordinate_probe.cc`。

在当前 worktree 根目录：

```bash
g++ -O3 -DNDEBUG -std=c++17 -I gr-uwb/include docs/sic/review/sic_perf_self_energy_coordinate_probe.cc -lvolk -o /tmp/sic_perf_self_energy_coordinate_probe
/tmp/sic_perf_self_energy_coordinate_probe
```

附件直接包含当前 `.cc`，用于访问匿名命名空间内核；**只是审查诊断，不替代正式库 QA**。不同 STL/VOLK/编译器可能产生不同计数；关注“不匹配可发生”，不要把本机计数写成跨平台 golden。

### 2.3 整改要求

- 缓存命中条件应验证实际候选列的生成几何/系数，包含相位行、有效浮点插值系数、整数偏移/相位 wrap、裁剪范围与 M、模板身份等依赖；不匹配就回退实时 VOLK 自点积。
- 可选择其他经证明的等价方案，但不允许仅按某个经验 origin 阈值强行宣称正确；若选受限 fast path，应证明限制条件并测试边界。
- 不为匹配缓存去改变原实时候选生成语义；若确需改变，明确升级为 E1 并走原任务的数值差异验收，不能仍写 E0。
- 添加正式回归：缓存开/关、不同整数起点、分数候选、短训练裁剪、相位 wrap、模板/scratch 重建、复杂模板。验证真正命中时分母逐位一致，不匹配时确实 fallback。
- 至少保留一个证明旧逻辑不足的测试用例，并验证修复后的缓存行为；不要只检查最终路径恰好没变。

**关闭条件：** 正式 QA 覆盖反例，命中/回退可观察，旧反例不再使用错误缓存分母；A/B 代表回归不退化。

## 3. PERF-R02：重新建立可信的源码、开关和效果绑定

### 3.1 已确认的问题

六份正式 summary 的 `provenance.repo_root` 指向主仓库，`git_branch=feature/sic-research`，`git_head=794056c…`，记录主仓库 dirty 状态。候选 `benchmark_source_sha256` 也读到了主仓库旧源码：

- summary 记录 `96d6dc66867669f49ed7e59feadd5be84255d21569ca6f77d5574e6e8fb6cf56`。
- 候选受检源码实际为 `a3e506a1200c98c9a829d4c7198c7f5b3f5f4246fefcef9a3317c4c4f3cb084b`。

运行库路径/哈希是正确的，因此耗时结果有诊断价值，但源码绑定不符合正式交付要求。

此外，基线 benchmark 使用候选库效果 run，却写 `effect_verified=true`。候选效果库为 `f95aca…`，基线实际库为 `e93378…`。这不能由报告中的说明自动修复，复现指南也不能继续指导这种绑定。

`UWB_SIC_*` 开关会影响执行路径，但没有完整进入逐 run provenance。即使不加入算法 `model_id`，也必须归档实际有效配置。

### 3.2 整改步骤

1. 完成代码修复并提交，确认最终测试提交干净；从提交后源码构建。后续纯文档提交另列 code-tested SHA。
2. 每个进程从对应 worktree 启动，显式检查源码根/构建根/运行库一致性。错误 cwd 或显式 repo 参数冲突时应拒绝，或可靠解析出正确根；不能仅把错误字段留给报告解释。
3. baseline、candidate 分别生成本库通过的 S1 效果 run，分别绑定。共享输入可只读复用，但要核对哈希与 effective_config，不共享“效果通过”身份。
4. 为效果绑定增加负向验证：把另一库的 effect run 交给 candidate 时必须失败，不能继续输出 `effect_verified=true`。基线源码不被随意改写；若旧 benchmark 缺少检查，可使用版本化外层 verifier 作为强制准入并单列其身份，或在独立控制分支做纯测量补丁，不能悄悄修改冻结基线。
5. 保存所有优化开关的有效值及默认来源、编译 flags、库/bindings/executable/source 哈希、实际 K/M/窗口长度、诊断模式。E0 开关不进 `model_id` 可以，但必须进性能 manifest。
6. 同输入、同诊断设置、同机器串行补跑三组 baseline→candidate 配对 core。持有 benchmark 排他锁；正式配置仍为每组 10000 窗×3轮、warmup 200、64 distinct 输入。
7. 最终 GR SIC-only/CIR/full-demod 行也必须绑定正确版本与效果来源，至少重跑原报告的一组对照；其采样规模不足正式标准时继续标为诊断。

不要手工改旧 summary 冒充重跑。旧结果标注为历史诊断/被新 run 替代，保留原文件。

**关闭条件：** 新结果 provenance 与实际文件、提交逐项相符，交换效果 run 的负样本被拒绝，最终报告只用正确绑定的新数据作正式结论。

## 4. PERF-R03：补齐 B 正式矩阵和 B 几何计时

### 4.1 正式效果矩阵

按原任务及现有 `uwb_sim_sic_payload.py` 的 `run_matrix()` 执行固定 **32 格 / 24200 包**。不缩减包数、不改种子/信道/门槛、不使用 exploratory 降格通过。

- 最终候选与基线分别独立运行和验证；如要复用基线结果，必须证明其覆盖全部正式格、输入/配置/代码与本次对照一致。此前只有 11 格 smoke，不能用它作正式对照。
- 每格报告 clean/raw/sic 错误数、PSDU/FCS、救回、损伤、提交/旁路/失败。
- 逐窗配对输入及输出状态。E0 预期不产生新增解调差异；任何差异先解释，不能只用总体 PER 相似掩盖。
- 正式矩阵 completeness 验证不能用 smoke schema 替代。资源不足未完成则保留“候选、未最终验收”，不能关闭该项。

### 4.2 B 的性能单独测

B 的前导位于 payload，公开可见前缀与输入窗口都不同于 S1 性能语料。增加同输入配对计时，至少覆盖：中心重叠、早/晚边界、多径 ±50 kHz，以及实际不提交的旁路控制。保留实际 K/M 和缓存命中/未命中。

可以使用配套 runner，但必须真实调用本库且不把生成器、落盘时间算作核心；单列端到端费用。不要直接套用 S1 的 24.7% 降幅。

**关闭条件：** 正式矩阵完整通过独立 verifier，未发现效果退化；B 代表几何具备版本正确、同环境的独立配对时间证据。

## 5. PERF-R04：补测 200 窗/s 准入与冷启动

目前饱和串行完成率不能代替按计划到达的 admission 回放。按原任务补测真实 GNU Radio 队列路径，沿用单 worker、入口 in-flight 与队列上限，不改变输入负载掩盖过载。

- 优先查现有 paced runner；旧 benchmark 没有成功验证的 `--rate/--duration` 命令，不发明参数。需要补 runner 时，在本性能分支实现并加 QA。
- 至少测 SIC-only 与实际下游链路（CIR、完整解调分别列），明确 baseline/candidate 配对、输入长度、诊断模式和计时范围。
- 建议每条至少持续 60 s（12000 个计划到达事件），3 次独立重复；记录实际测试时长，不够则标诊断。
- 固定计划到达时间，记录 scheduled/offered/admitted/completed、missed admission、队列拒绝/丢弃/取消、queue wait、服务时间、terminal latency P50/P95/P99/max。
- 解释计数关系：missed admission 与拒绝是否重叠、drain 后尚未完成多少，不重复统计或漏掉失败。
- 源端迟发也计 missed admission。不能让回放源等待上一窗完成后才安排下一窗来维持“无丢包”。
- 自能量表首次填充目前在 `core_total` 内且历史观察约 8–11 ms 冷窗。分别报告 prepare、首个有效窗口、稳定热窗；冷热分开，不把首窗藏进 warmup 后只给稳态数字。

**关闭条件：** 给出上述真实数据和明确通过/失败判定。200 窗/s 或 P99 未达标可以作为诚实的失败项交付；“未测”不能等同于已完成这项验证。

- 两个独立进程，分别使用各自头文件和库；禁止一个进程加载两个同名库。
- 归档编译命令、输入生成规则/seed、库/程序 SHA256、比较字段清单和机器可读结果。
