## 1. 结论

审核意见 **成立且准确**：`admit_range_capable_time()` 的 `switch (ev->outcome)`
没有 `default`，未定义枚举值穿过 switch 到达成功路径。我独立复现了审核给的两行：

```
outcome=5   (invalid) completed()=0 admitted=1 reason=admitted
outcome=255 (invalid) completed()=0 admitted=1 reason=admitted
```

**但审核把范围报小了。** 同一根因在配置校验层还有 **19 处**被接受，另有一处会
**抛异常而非拒绝**。最终修复范围是 **20 个 fail-open 站点（C++）/ 19 个（Python）
+ 3 处误导性拒绝 + 3 个会抛异常的查表函数**，全部覆盖，全部有永久回归。

审核的定级 P2 可以接受（触发需要调用方构造域外值），但按工程自己写进 AGENTS.md 的
**default-deny / fail-closed** 原则，以及两次都发生在"决定能否发布距离"的路径上，
我倾向 P1。分歧不影响修复。

---

## 2. 根因

**枚举只在 JSON reader 通过 `get_enum` + `from_string` 校验；C++ 直接构造路径
（以及 Python 的直接赋值路径）完全没有域校验；门的判定用 `==` 或成员测试，
不覆盖域。**

三个后果，按危险程度排序：

| 后果 | 说明 |
|---|---|
| **fail-open** | 域外值通过 `validate()`。**这是单一准入闸门** |
| **自相矛盾** | 通过校验的配置序列化成 `"invalid"`，再被**同一层自己的 reader 拒绝** |
| **误导** | 拒绝但报的是**无关字段**（`session.protocol=2` 报成 `timing.response_to_final.ns`） |

一个把三者钉死的实测：

```
validate(rx.agc=250, link_delay_unit=250).ok = 1     ← 闸门放行（修复前）
to_json_string  →  "agc": "invalid"                  ← 自己的序列化器说它非法
from_json_string(那份文档).ok = 0                     ← 自己的 reader 又拒绝
```

修复后 `validate().ok = 0`，三者一致。

## 3. 修复范围（实测数字）

### 3.1 fail-open：修复前被接受，现在被拒绝并点名

| 类别 | 站点数 | 具体 |
|---|---:|---|
| 审核点名的 `TxOutcome` | 1 | 测距准入门 |
| 普通配置枚举 | 7 | `frame.fcs_append`、`tx.pulse_shaping`、`rx.agc`、`calibration.link_delay_unit`、`calibration.first_path_algorithm`、`calibration.cfo_compensation`、`calibration.sfo_compensation` |
| `TimedField.marker` | 12 | 每个 `TimedField` 的第三个枚举（`frame.sfd_timeout` 到 `timeouts.rx_timeout`） |
| **合计（C++）** | **20** | Python 无准入层，故为 **19** |

`TimedField.marker` 那 12 处是**我第一轮修完后仍然漏掉的**：我加了 `.domain` 和
`.reference` 就假定这一对是完整的。它之所以容易被忘，正因为它**是可选的**
（`Opt<TimestampMarker>`，主机单调时钟下必须缺席）。

**发现方式值得记录**：我用 dataclass 的**类型注解**递归枚举出全部 enum 字段，
再逐个注入域外值、断言 `validate()` 既不抛异常也不接受 —— 才把它扫出来。
按"值"枚举会漏掉默认 `None` 的字段。

### 3.2 误导性拒绝：修复前拒绝但报错字段

| 字段 | 修复前报的 | 修复后 |
|---|---|---|
| `session.protocol` | `timing.response_to_final.ns zero_value` | `session.protocol unknown_enum_value` |
| `session.role` | `timing.poll_start.ns field_conflict` | `session.role unknown_enum_value` |
| `timeouts.*.domain` | `timeouts.rx_timeout.marker field_conflict` | `…​.domain unknown_enum_value` |

fail-closed 但**诊断错误**：调用者会去查时间预算，而真正的问题是枚举域外。

### 3.3 抛异常而非拒绝：3 个查表函数

`validate()` **必须报告，不能抛异常** —— 抛异常的闸门什么都没报告，不等于拒绝。

| 函数 | 修复前 | 修复后 |
|---|---|---|
| `sfd_mode_symbols` | `{...}[v]` → `KeyError: 99` | `.get(v, 0)`，与 C++ 的 `return 0` 一致 |
| `frame_type_timestamp_count` | `{...}[t]` → `KeyError` | `.get(t, 0)` |
| `evidence_required_level` | `{...}[u]` → `KeyError` | `.get(u, VENDOR_INTEROP_VERIFIED)` —— 未知用途要求**最高**一级，永不降低门槛 |

其中 `sfd_mode_symbols` 是真实可达的：`frame.sfd_mode = 99` 会让
`validate()` 直接抛 `KeyError` 而不是返回报告。

### 3.4 我上一轮报告里的一处错误

上一轮我写过「Python 的 `_StrEnum` 在构造时就抛 `ValueError`，所以 Python 侧
结构上安全」。**这是错的。** 枚举类确实拒绝构造域外值，但
**dataclass 属性在运行时不强制类型**：

```python
cfg.rx.agc = 250      # 存进去了
T.validate(cfg).ok    # -> True   （修复前）
```

所以这是**双侧**缺陷，而且 145 条共享 JSON 语料**结构上无法覆盖它**
（`get_enum` 只接受已知字符串）。这也解释了为什么它一直没被发现。

## 4. 修复设计

### 4.1 C++：一个统一的域校验层

`ConfigValidator::run()` 的**第一步**是新增的 `check_enum_domains(cfg)`，
对**每一个**枚举字段（含 15 个 `TimedField` × 3 个枚举 + `radio.peers[i].role`）
跑一遍，拒绝理由 `UnknownEnumValue` —— 与 JSON reader 同一套词汇，调用者
无论从哪条路径拿到坏值都看到同一个说法。

每个枚举配一个 `xxx_is_known()`：

```cpp
inline bool agc_mode_is_known(AgcMode v)
{
    switch (v) {
    case AgcMode::Manual: case AgcMode::Disabled: case AgcMode::VendorDefault:
        return true;
    }
    return false;                      // 注意：没有 default
}
```

**为什么用 switch 而不是 `<= kXxxMax`：** 这些 switch **没有 `default`**，所以
给枚举加成员时 **`-Wswitch` 会报错**，而不是静默扩大被接受的域。`<= last` 形式
需要维护第二个常量；加 `default` 则会消掉让它安全的那条警告。

这与工程既有惯例一致（`timestamp_marker_is_known` / `timestamp_source_is_known`），
`frame_profile_id_is_supported()` 已覆盖 `FrameProfileId`，故不重复。

**为什么先于其他检查：** 域外的值无法推理，而且先查能让拒绝**点名真正的字段**，
而不是让依赖它的检查报出一堆无关错误（3.2 就是）。

### 4.2 N07 本体：域测试与 switch 配对

在测距准入门里，域测试放在 `switch` **之前**：`switch` 于是只处理已知值。

```cpp
if (!tx_outcome_is_known(ev->outcome)) { reject(...); return r; }
switch (ev->outcome) { ... }         // 仍无 default，仍受 -Wswitch 保护
```

新增 `tx_outcome_is_known()`（`RangeAdmissionReason` 等仍沿用既有的 `kXxxMax` + `from_string`）。

### 4.3 Python：同一套，逐字段镜像

`ConfigValidator.check_enum_domains()` 在 `run()` 里第一位，字段列表与 C++
**逐项对应**。域测试用 `isinstance(v, cls)`：

```python
if not isinstance(v, cls):
    self._cfg_rej(f, ConfigReason.UNKNOWN_ENUM_VALUE, "...")
```

Python 里这是**精确**的：枚举成员是且仅是其枚举的实例，所以裸 int、或
**恰好友成员值的裸字符串**，都在域外。**没有需要同步的成员列表**，因此不会漂移。

## 6. 顺带修正：两个既有测试的**理由**变了

- `every_other_phr_rate_is_rejected_with_its_own_reason`
- `unknown_frame_profile_is_rejected_not_defaulted`

两者**本来就在拒绝**域外值，但走的是**偶然**路径（"这不是我实现的成员"），
报 `Unsupported`。现在先报 `UnknownEnumValue`（更准：它不是"未实现"，是
"这个枚举没有这个值"），而语义的 `Unsupported` **照旧一并给出** —— 只读后者
的调用者不会失去 codec 的解释。两个测试已更新为同时断言这两种答案。

## 10. 这一轮真正学到什么

审核的 N07 与我的 N01/N02 是**同一个错误的第三次出现**：

| 轮次 | 错误方向 |
|---|---|
| N02 | 把**合法**输入拒了（需求允许 scheduled TX） |
| N01 | 把**非法**输入截断后接受，且文档描述了不存在的行为 |
| N07 | 把**非法**输入放行（枚举域外值穿过 switch） |

共同点：**把枚举/字段的枚举成员当成了它的域**，或者**把测试通过当成了行为正确**。
具体 bug 各有各的修法，但防复发的办法只有一个：**domain 要显式、要穷举、
要 fail-closed，并且要用"扫全部字段"的方式验证，而不是用抽样** ——
`TimedField.marker` 那 12 处就是抽样会漏、穷举才抓到的。

**仍未实现**：TWR 协议能力（无 FSM、无 ToF 公式、无双端点、无 TWR 硬件收发）。
本轮不推进 M2/M3，不夹带 pybind 迁移，不宣称性能无回退，不承诺厘米级。
