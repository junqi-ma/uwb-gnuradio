- N01：C++/Python reader 已在收窄前检查 unsigned 字段范围。此前的 `261→5`、
  `2^32+1→1`、`65537→1` 等反例现在被拒绝；154 条语料和两侧 parity 测试通过。
- N02：`ScheduledCalibrated` 只允许用于发送 RMARKER，并要求四项计划记录及
  `TxOutcome::Completed`；接收预测、缺记录、仅 send accepted、late、underflow、cancelled
  均拒绝，且不改标为 `HardwareMeasured`。
- N03：纳秒投影改为单一有理数商/余数路径。此前 737.28 MHz 的 490625→490624
  及 1 GHz/15 ticks→14 ns 反例已修复，返回值和 lossless 标志来自同一计算。
- N04：分数合并后重新检查半周期上界；12-bit 域的 2048.5 ticks 现在返回
  `WrapAmbiguous`，测距准入也拒绝。
- N05：`uwb_twr_tof_input.h` 已加入安装清单，QA 专用 `uwb_twr_test_output.h` 保持不安装；
  schema v2 consumer、临时安装、外部 C++/Python consumer 和 CTest 注册均已更新。
- N06：公开 `thaw()` 已移除，`mutable_copy()` 返回独立可变副本；运行中的 capability
  表保持只读。

## N07 / P2：未知 TxOutcome 会 fall through 到成功

位置：`gr-uwb/include/gnuradio/uwb/uwb_twr_tof_input.h` 中
`admit_range_capable_time()` 的 `switch (ev->outcome)`。

当前分支有 `Completed`、`Late`、`Underflow`、`Cancelled`、`Unknown` 五个 case，
但没有 `default`。`TxOutcome` 是公开 enum，调用者可以从外部值、反序列化或错误映射得到
未定义枚举值。对此类值，switch 不执行任何拒绝分支，函数继续执行到最终：

```text
outcome=5   completed=0 admitted=1 reason=admitted
outcome=255 completed=0 admitted=1 reason=admitted
```

这与报告中“Unknown 只能拒绝”“任何未完成/未知发送都不能发布有效距离”的规则冲突，
属于准入层 fail-open。`TxSendEvidence::completed()` 本身也只返回 equality，不能代替
对 enum 域的完整性检查。

修复建议：

1. 在 switch 增加 `default`，返回 `ScheduledTxEvidenceMissing` 或新增
   `InvalidTxOutcome`，并保持 `admitted=false`；
2. 增加 `tx_outcome_is_valid()`/`TxSendEvidence::is_well_formed()`，在计划记录检查后
   先验证 enum 域；
3. 为 5、255 等未定义值增加永久 C++ QA 和 `verify_m0_1_findings.py` 反例，
   断言无效值不会到达 `ExchangeStatus::Ok`；
4. 检查 Python/JSON/异步事件映射是否也对未知状态 default-deny。

这是小范围修复，不需要改变 N02 的合法规则，也不会进入 IQ 热路径。

## 对整改报告结论的调整

以下表述可以保留：

- N01–N06 的原始缺陷已分别修复并有对应代码/测试证据；
- work-grid 证据仍不等于 native、ToA、硬件或 vendor interop；
- TWR FSM、ToF、双端点、native 闭环和硬件收发仍未实现；
- 历史重采样吞吐失败未被放宽，也未被归因到 TWR。

以下表述需要改为条件式：

- “6 条已全部独立复现并关闭”可作为 N01–N06 的局部结果，但不能推出 M0.1 总体完成；
- “M1 可开始”应改为“修复 N07、补测试并更新门禁后开始 M1”；
- `14/14` 只能证明脚本中的 14 个断言，不覆盖未知 enum、完整发布构建或硬件行为。
