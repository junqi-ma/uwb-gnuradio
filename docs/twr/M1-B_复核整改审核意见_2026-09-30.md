## 2. R01–R09 逐项

### R01 / P1：TxPlanned 不得提前发布成功 —— VERDICT：CLOSED

- **原坏行为**：`TxPlanned` 携带 `outcome=Completed`，同批输出 SubmitTx 与成功终态，`outcome_events=0`。
- **我检查了什么**：四角色下发计划后是否有终态；同 token 第二次计划是否二次提交；仅 `TxAccepted`
  是否闭合；`internally_consistent` 失败时是否拒绝。
- **观测**（`/tmp/opencode/m1b/probe.cpp`，P1）：
  ```
  P1 responder poll: prep=1
  P1 plan: submit=1 terminal=0 (expect submit=1 terminal=0)
  P1 dup plan: submit=0 terminal=0 (expect 0/0)
  P1 terminal after plan alone: results=0 inflight=1
  ```
  代码：`on_tx_planned` 用计划构造 `TxRecord`，`evidence.outcome`/`rec->outcome` 一律
  `Unknown`（`uwb_twr_core.cc:1180-1182`）；`TxRecord::completed()` 要求 `outcome==Completed`
  （`:303-307`）；`pending_prepare=false` 后重复计划走 `tx_token_mismatch`。`TxAccepted` 只置
  `accepted/send_accepted`，不置 outcome（`:1239-1250`）。
- **VERDICT：CLOSED**（QA `r01_tx_planned_alone_never_completes_an_exchange` 四角色 + `TxAccepted`
  场景亦通过）。

### R02 / P1：DS initiator 必须等 Poll 与 Final —— VERDICT：CLOSED

- **原坏行为**：Poll outcome Unknown 时，Final Completed 即成功；之后 Poll Underflow 仅计 token mismatch。
- **我检查了什么**：两种完成顺序；其中一个 Unknown/失败；RX 先于 outcome；晚到失败；闭合后矛盾回调。
- **观测**：
  - `probe.cpp` P2：`Final completed while Poll unknown: terminal=0 inflight=1`；
    `late Poll underflow: terminal=1 status=tx_underflow`。
  - `probe2.cpp` A：Final 先 Completed 不终止，Poll 再 Completed 才终止。
  - `probe.cpp` P9：SS 成功后晚到 Poll Underflow → `terminal=0 mismatch=1`（计 mismatch，不复活）。
- **代码**：`maybe_finish()` 显式列出四组成功 TX 集合（`:691-733`），DS initiator 需
  `tx_poll.completed() && tx_final.completed()`；未闭合时只布防证据上限，不发布成功。
- **VERDICT：CLOSED**（QA `r02_ds_initiator_needs_both_poll_and_final` 两顺序、
  `r02_unknown_and_failed_required_tx_fail_exactly_once`、`r02_duplicate_callbacks_never_advance_twice` 通过）。

### R03 / P1：全部角色的本端严格准入 —— VERDICT：COUNTEREXAMPLE（阻断）

- **原坏行为**：SS responder 在 RX 质量 NotRecorded、TX plan 域/epoch 错误下仍 complete。
- **我检查/确认已修的部分**：
  - 本端 RX 准入 `admit_rx_single()` 对**全部四角色**（responder Adopt Poll、DS responder Final、
    initiator Response）在驱动计划/公式前调用，检查 domain identity+epoch 与严格
    `admit_range_capable_time`（质量/校准/修正链）；见 `uwb_twr_core.cc:612-636,923-930,977-984,1035-1043`。
  - 计划层的 domain/epoch、校准 id、校准窗口、RMARKER_TX 修正、内部恒等式、符号/次序、wire
    可表示、deadline verdict 均在 `on_tx_planned` 校验（`:1089-1149`）。
  - `probe.cpp` P10：SS responder 计划用**另一设备 domain** → `submit=0 terminal=1`（拒绝）。正确。
- **反例（缺失的负例）**：`TxPlan` 的 `source` 只被 `timestamp_source_is_known()` 检查
  （`uwb_twr_core.h:158`），**不要求** `ScheduledCalibrated`。`to_air_timestamp()`→
  `Timestamp::from_ticks()` 只拒绝 `Unknown`。因此 `HardwareMeasured` / `Estimated` /
  `Reconstructed` 计划均被接纳；对**不计算 ToF 的角色**（SS responder、DS initiator），
  该计划不会被任何 `admit_local` 覆盖，直接产生成功终态。

- **最小反例**：`/tmp/opencode/m1b/repro_source_matrix.cc`
  ```bash
  g++ -std=c++17 -O0 -Igr-uwb/include -Igr-uwb/lib \
      /tmp/opencode/m1b/repro_source_matrix.cc gr-uwb/lib/uwb_twr_core.cc -o repro_srcm && ./repro_srcm
  ```
  实测输出：
  ```
  source=scheduled_calibrated submit=1 terminal=complete
  source=hardware_measured    submit=1 terminal=complete
  source=estimated            submit=1 terminal=complete
  source=reconstructed        submit=1 terminal=complete
  source=unknown              submit=0 terminal=invalid_time_domain
  ```
  SS responder 单例（`repro_source_estimated.cc`）：`plan(source=estimated) submitted=1`，
  `terminal completion=complete`。
  同一缺陷对 DS initiator 亦成立（`probe2.cpp` B：`OK(complete)`）。

- **对照**：demo 的独立 verifier 自己硬要求 `plan.source == "scheduled_calibrated"`
  （`verify_m1_b_protocol.py:782`），说明约定就是 ScheduledCalibrated；但**核心本身不执行该约定**，
  这是一层被绕过的边界。任务单 R03 明确要求"错 …/source 各自独立负例"，现有 QA 只有
  `TxPlanDefect::SourceOutOfDomain`（=`static_cast<TimestampSource>(99)`），**没有**"已知但非
  ScheduledCalibrated"的负例。
- **VERDICT：COUNTEREXAMPLE（阻断）**。修复建议：在 `internally_consistent()`（或
  `on_tx_planned`）显式要求 `source == TimestampSource::ScheduledCalibrated`（计划是调度发送，
  不是测量值），并补四角色负例。

### R04 / P1：身份屏障、token 复用、configure/reset 原子性 —— VERDICT：CLOSED（带非阻断观察）

- **原坏行为**：本地代次递增即清 wire 重放屏障；token 计数器被 reset 归零导致旧 plan 被新交换接受。
- **我检查了什么**：
  - **token 不复用**：`token_counter` 只在 `next_token()` 自增，`configure()`/`reset()`/`on_reset`
    都不清零（`uwb_twr_core.cc:357,519-525,1449-1451,1495-1502,1396`）。
  - **wire 屏障随 session**：`on_reset` 仅在 `has_new_wire_session_id && new id != cfg.session_id`
    时 `seq_used.fill(false)` 并清 `seq_issued`（`:1402-1406`）；纯本地代次 bump 不清。
  - **代次核对**：`post()` 在 kind 域检查后先做 `ev.generation != 0 && != live` 拒收（`:1534-1540`）。
  - **原子性**：`configure()` 在途拒绝、校验先于任何写（`:1431-1454`）；`reset()` 先构造 `next`
    并校验/要求新 binding，再整体替换（`:1469-1509`）。
  - **未取走结果保留**：`on_reset` 不碰 `results`（QA `r04_reset_event_retains_undrained_results` 通过）。
- **观测**：`probe.cpp` P8（见下"非阻断观察"）；QA `r04_*` 全通过；module 级 `qa_core` 通过。
- **非阻断观察 1（通配 generation）**：`generation==0` 被当作"不检查"。任务单/G0 说"每个事件带
  generation"，但维护版 `twr_m1b_test_support.h::TwoEndpointDriver` 的 `begin/rx_to_event/
  process_submit` **从不设置 generation**（全默认 0）；e2e 用例 `r04_e2e_new_wire_session_clears_
  the_replay_barrier` 实际是靠 `seq_used` 而非代次拦截。我未能把"generation=0 的旧事件"构造成
  真正有害的反例（token 单调 + `seq_used` 已覆盖主要危害），故**不判为 COUNTEREXAMPLE**，但建议
  显式文档化 0 的语义或要求非 0。
  - `probe.cpp` P8 输出：`after reset gen=2, poll with default gen(0): prep=1 accepted=2`
    —— 该 Poll 的 seq 是未用过的，本身合法；它只证明"代次字段缺省即不设防"。
- **非阻断观察 2（G0 文档与代码不一致）**：G0 §3 写"`Reset` 事件会清 `seq_issued` 但不清
  `seq_used`"，而代码在**无新 wire session 时两者都不清**（`:1407-1413`）。代码方向更 fail-closed
  （正确），G0 文本需更正。
- **非阻断观察 3（configure 丢弃未取走结果/计数）**：见 §3。
- **VERDICT：CLOSED（带上述非阻断观察）**。

### R06 / P1：无主终态 —— VERDICT：CLOSED

- **观测**（`probe.cpp` P6）：`idle bad outcome: actions=0 terminal=0 accepted=0 inflight=0`。

### R07 / P2：绝对 exchange 上限不可被证据等待延长 —— VERDICT：COUNTEREXAMPLE（阻断）

- **原坏行为**：`Begin(0), exchange_timeout=1000`，RX(300)、`evidence_wait=1000` 时
  `Deadline(1000)` 未终止（上限被覆盖成 1300）。
- **确认已修的部分**：两个上限**分别**保存，`arm_evidence_deadline` 只在首次欠结果时布防且不延长
  （`:383-394`），`arm_exchange_deadline` 在接纳时固定（`:397-408`），`ArmRx.deadline_ticks` 取
  最早有效者（`:514-515`），`on_deadline` 用 `earliest_deadline()` 只终止一次且加法溢出安全
  （`:1326-1348,102-105`）。`probe.cpp` P4 的对照与 QA `r07_*` 均通过这一层。
- **反例（校验前提错误）**：`validate_core_config` 只拒绝"两个上限都为 0"（`:165-169`），
  其报错文案声称"另一项就提供了有限终止条件"。但**证据上限只在"已欠一个结果"的事件（maybe_finish）
  里才布防**；当一个被接纳的交换还没走到"欠结果"就卡住（plan 永不到 / Response 永不到）时，
  `evidence_wait` 永远不会生效，而 `exchange_timeout==0` 意味着 `earliest_deadline()==0`，
  `on_deadline` 直接返回（`:1335-1336`）。于是**已被接纳的请求永无终止**。
- **最小反例**：`/tmp/opencode/m1b/repro_unbounded_deadline.cc`
  ```bash
  g++ -std=c++17 -O0 -Igr-uwb/include -Igr-uwb/lib \
      /tmp/opencode/m1b/repro_unbounded_deadline.cc gr-uwb/lib/uwb_twr_core.cc -o repro_dl && ./repro_dl
  ```
  实测输出：
  ```
  configure(et=0, ew=1000) ok=1
  begin accepted=1 terminal=0 in_flight=1
  deadline(2e9) produced_terminal=0
  ```
  即合法配置下 `Begin` 被接受、plan 永不到、即使投递 20 亿 tick 的 `Deadline` 也不产生终态，
  `in_flight` 恒为 1，违反守恒（`accepted != terminal + in_flight`）。
- **可达性说明**：现有 `TwrConfig` 校验要求 `exchange_timeout>0` 且 `rx_timeout>0`
  （`uwb_twr_config.h:4279-4290` 的 `required=true`），所以 demo 的 R09 路径目前不会产生该配置；
  但 `EndpointCore` 是公开 API（安装消费者直接使用），其自身校验即承诺了"有限终止"，故此为核心缺陷。
  若沿用"某项为 0 表示关闭"的语义，则应要求 `exchange_timeout_ticks > 0`，或在接纳时就（以接纳
  tick 为基）布防证据上限。
- **VERDICT：COUNTEREXAMPLE（阻断）**。

### R08 / P1：数值计划的完整映射 —— VERDICT：CLOSED（数值映射）

- **原坏行为**：计划只有 `Timestamp`+4 bool，无 command/量化/marker offset 数值。
- **我检查了什么**：内部恒等式 `calibrated_air == quantised_instant + marker_offset`（溢出安全）、
  符号/次序（负 offset、负 quantised、command 晚于 quantised）、域内范围、域/epoch 与本地一致、
  校准 id/窗口、RMARKER_TX 修正集、wire 可表示、deadline verdict、t3B/t5A 取自提交计划。
- **观测**：`probe.cpp` P7 负 marker offset → `submit=0 terminal=1`；QA `r08_*`（含
  `r08_negative_offset_and_command_order_are_refused`、`r08_wire_unrepresentable_air_instant_is_
  refused`、`r08_submitted_frame_carries_the_plan_air_instant`）全部通过；demo 的

## 3. 联动核查项（任务单 §4）

| 项 | 观测 | 结论 |
|---|---|---|
| Cancel/Stop/Timeout 对已 Submit 未 completion 的 TX | `on_cancel`/`on_stop`/`on_overflow` 对在途请求发终态；`AbortPending` 只在 `pending_prepare` 时发出，**不对已提交信号假装撤销**；晚到 outcome 在终态后只计 `tx_token_mismatch`。见 `probe.cpp` P9。 | **符合任务单**：已发出信号不可撤回，晚到事件不污染后续请求（非阻断）。 |
| `configure()` 重入 | 在途拒绝 + 失败原子（QA `r04_failed_reset_and_configure_are_atomic` 通过）。但**成功的 configure 会清空未取走的终态结果与计数器**：`probe2.cpp` C → `re-configure ok=1 counters.terminal_results=0 pop_ok=0`。`reset()` 相反是保留的。任务单 §4 把它列为需核查项。 | **非阻断观察**：`configure` 是"全新快照"语义，调用方可先 `pop_result` 排空；但与 `reset` 的保留策略不对称，建议在 G0/头注释显式说明，或拒绝在有未取走结果时 configure。 |
| RX 先于 TX plan/Submit | SS initiator 下先到 Response 再补 Poll plan：pending token 不丢。**DS responder 下先到 Final 会使状态回退**：`probe2.cpp` D → 早到 Final 后 `state=final_received`；随后 Response plan 到达把 state 写回 `poll_received`，交换卡到 deadline → `protocol_timeout`。DS initiator 下先到 Response 会覆盖 pending PrepareTx（Poll 计划随后被 token mismatch 拒收）。 | **非阻断**：物理上对端不可能在我们发出 Response/Poll 前就发 Final/Response，且结果 fail-closed（超时而非假成功）。但任务单明列"回退状态"需核查，故如实记录；核心未校验"对端帧依赖的本端帧确已提交"。 |
| `post()` 路径分配 | 全局 `operator new` 计数（`probe3.cpp`，`-O2`）：`rx poll(adopt)=0`、`tx planned(submit)=0`、`tx accepted=0`、`begin=0`、`bad outcome(reject)=0`；**触发终态的 post 为 6–7 次**（`outcome completed(terminal)=7`、`cancel(terminal)=6`）。数量随 detail 字符串是否落入 SSO 而变动。 | **已如实测量**：任务单"无每事件动态分配"**不成立**（协调者报告 §8 已更正，与本次测量一致）。事件消费多数零分配，产生/搬运终态估计时才有分配。 |
