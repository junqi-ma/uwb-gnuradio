## 【评审结果已回，本报告结论作废】

外部评审（[评审意见_M0.1_2026-09-29.md](评审意见_M0.1_2026-09-29.md)）判定
**「需要修改，暂不认可 M0.1 已完成、四层契约冻结」**，并给出 **2 个 P1 + 4 个 P2**
（N01–N06）。全部 6 条已独立复现，其中两条把**错误行为写进了实现或测试约定**：

- **N01（P1）**：JSON 越界整数被静默截断后当作合法配置接受。更严重的是，语料
  `negative_local_address_is_a_negative_index` 的 note 描述的机制**代码里根本不存在**
  （声称 reader 保留 int64、validator 拒绝；实际 reader 掩码成 65535，靠"保留地址"
  规则偶然拒绝）。**145 条语料只能证明指定输入上的一致性，不能证明这些共同约定正确**。
- **N02（P1）**：测距准入门拒绝**全部** scheduled_calibrated TX，而 REQ-TIME-03 原文
  明确允许"确定性时序加标定取得合格 TX timestamp"。测试还把这个错误行为写成契约。
  这会直接堵死计划中的 X410 timed TX 路线，并诱导后续把来源错标成 HardwareMeasured。

因此本报告的 §1「四层契约已冻结」、§3「M0.1 已完成」等表述**不再成立**；
§5 的疑问已被评审回答（见下表），§6 的推送建议为"可作为待评审分支发布，
不能标为验收通过或合并 main"。

| 5.1 Python 双轨 | 现在切 C++ 权威 + pybind 薄接口；**先修 N01 并独立确定语义再绑定**，不能把错误语义统一得更彻底 |

## 3. 三个提交做了什么

### `9610970` M0 契约层
4 个 UHD-free / GNU-Radio-free header（`types` / `timestamp` / `frame` / `config`），
实测 PHY 能力矩阵（318 行）、时序预算（4 份 CSV）、帧字节 golden、设计契约与回归基线。

顺带修了两个既有缺陷：
- `rate_matches_strict` **接受 `+Inf`** —— 设备返回非有限速率读回会被当成匹配的
  737.28 MHz 放行，击穿"静默速率强制转换即硬失败"保证
- `check_frame_lengths` 把 FCS 计入 `need` 却与不含 FCS 的字段比较

### `eb7904d` 关闭复核发现 R1–R8
Codex 复核 M0 报告后给出 R1–R6（P1 契约缺陷）与 R7–R8（P2 证据/交付缺项）。
**6 个 P1 全部独立复现并关闭**。要点：

- **R1** Python 快照共享可变对象 → 配置边界深复制 + 能力表冻结（含
  `PhyCapabilityRow` 本身可变这一隐蔽绕过路径）
- **R2** 配置要求 `phr_rate == data_rate`，因而**拒绝调制器实际使用的 0.85 Mb/s PHR**、
  却接受 6.81 → 独立 `PhrRate` 枚举，字符串域与 `DataRate` 不相交
- **R3** config 的 7 字节几何 vs codec 的 14 字节 → frame 层建立唯一权威，
  7 字节声明被逐字段点名；`session_id` 经 `session_id_to_wire` 收窄，超范围拒绝
- **R4** `duration_is_tick_exact` 在 737.28 MHz 下**把截断标为无损**（真实 1.356 ns
  却报 `nanos=1, exact=true`）→ 拆为 `is_whole_ticks` / `duration_is_lossless_ns`，
  旧标志删除；新增 `RelativeTickInterval`（无 ns 字段）作为 M1 安全路径
- **R5** 恰好半周期在**双向都返回"在对方之前"** → 严格小于并双向一致拒绝；
  新增分数感知比较；过程中发现一个真实 bug（模分数差需**向下**借位，由 4.2M 对穷举抓出）
- **R6** 裸 IQ 时间戳可产出 `Ok` interval → 新增测距准入门，类型私有构造 + friend 门控，
  "忘了验证"在类型层面无法表达；**伪造全部修正位仍被拒**（marker 检查独立于修正位）
- **R7** 318 行 `path` 全是 `work_direct_998p4*`（7 行 `NOT_RUN`）→
  五级证据阶梯，48 行标 `work_decode_verified` 且把未建立的四级**写成数据**
- **R8** 4 个头未安装、`twr_config.py` 未安装、Python QA 未注册 CTest →
  临时 `DESTDIR` 前缀做外部消费测试，当场抓到两个真实缺陷

**文档撤回 5 处**被复核否定的过强结论（详见 §4）。

### `cf1e06e` 差分测试发现的校验漏洞
`calibration.record.native_sample_rate_hz` 的适用性规则用 `> 0.0` 守卫，
**NaN 不满足该比较**，于是绕过整个 validator。危险之处在于**两侧都被钉在错误行为上**：
corpus 记 `accepted=true`，差分测试因此报绿，而 NaN 一路畅通。修复后必须同时改三处
才能自证（corpus 期望、清空两处 `unchecked` 绊线、删除被拒用例的 effective 期望）。

## 4. 被推翻的结论（我自己的）

保留下来是因为它们**直接影响 M1 该怎么做**：

| 原结论 | 现状 |
|---|---|
| 没有 work→native 抽取器，原生栅格无法调制 | **过强**。仓库已有 Python `resample_poly` 路径（`x410_cg400_hrp_echo_cir.py:183`），缺的是 C++ 集成/buffer 复用/时间映射 |
| `EXEC_LATE_CMDS(1)` 使迟到定时 TX 一律立即发 | **混淆了两条路径**。该参数属 ctrlport 定时控制；TX 数据走 `radio_tx_core.v:333`，迟到触发 `ERR_TX_LATE_DATA`。必须同时处理主机 deadline 和设备 async 错误 |
| 128 SYNC 结构性不可能 | **撤回**。Qorvo 器件支持 128/256/512/1024（DW1000 v2.7 §5.12；DW3xxx pp.32–34），限制在本仓库的 decoder/CFO 路径。当前**仍拒绝**（fail-closed 不变），但理由改为"当前软件实现限制" |
| 自建有界队列即系统内存有界 | **不足**。PMT 入口仍可能积压，需 credits/限速/背压 |
| 排除所有 `tagged_stream_block` | **过宽**。只针对零流端口 controller，其他 adapter 按各自 scheduler 语义选型 |
| 回绕无歧义窗口 = 全周期 | **应为半周期** `2^(bits-1)/rate`（超半周期的模差与负向区间不可区分），严格更强 |

## 5. 我判断不确定、想听建议的地方

### 5.1 `twr_config.py` 涨到 7049 行，是否该拆？
M0 是 4899 行，M0.1 后 7049 行。方案 §2.A 第 5 条明确警告
"避免继续扩充 5000 行单头和另一套 5000 行 Python 平行实现"。

**当前状态**：C++ `uwb_twr_config.h` 6424 行，Python 7049 行，两者**手工保持同步**。
同步靠的是 145 用例的差分测试（捕获行为漂移），不是靠共享代码。

**我担心的是**：M1 还要往 config 里加 per-message override、统计/诊断、attempt 策略，
可能到 9000+ 行；而两套实现的同步成本是线性增长的。

**想听的**：是该继续同步维护两套，还是现在就切到"C++ 权威 + pybind 暴露、Python 只做
构建接口"？后者会推迟 M1 的 Python 可用性，但消除长期双轨。

### 5.2 五级证据阶梯的粒度是否合适？
现状：`work_decode_verified` / `native_roundtrip_verified` / `toa_verified` /
`hardware_verified` / `vendor_interop_verified`，单调累加。48 行只有第一级。
代码层面 `allows(work_decode, Ranging) = 0`，即当前能力**不可用于测距**。

**疑问**：这个阶梯是否过细或过粗？M2 做完 native 往返后，`native_roundtrip` 和
`toa` 之间的差距（帧能过但首径精度未知）是否值得单独一级？

### 5.3 16 SYNC 该不该现在就从白名单拿掉？
现状：16 SYNC **能往返通过且自描述**（PHR 索引 0 = 16，合法 BPRF 时长），
CFO 误差 0.000 Hz。但短积分窗（16.3 µs vs 64 SYNC 的 65.1 µs）下**首径 ToA 精度未测**，
所以保留在白名单但用 `twr_sync_reps_needing_toa_validation(16)` 标记为
"未验证前不可用于测距"。

**评审更正（2026-09-29，本报告初稿的表述有误导）**：64 SYNC 同样**没有任何 ToA
证据**，不能因为"65.1 µs 的窗更长"就默认它是已验证的测距配置。本报告若让读者以为
"只有 16 SYNC 未验证"，那是错的：`allows(work_decode, Ranging) = 0` 对所有 48 行
成立，16 和 64 没有区别。配置合法、试验许可和"正式结果有效"是三件事，必须分开；
否则"未验证就不能测试、没测试又不能验证"会形成闭环死锁。

**疑问**：这个"进白名单但标记不可测距"的双重状态，会不会比直接不收更清晰？
理由是 M2 一旦测出 ToA 精度就能立即启用，不必再改白名单。
（评审建议：保留 decode-only 行，测距用途继续禁用，与本节倾向一致。）

### 5.4 native 往返（M2-A）的前置缺口该怎么排？
仓库只有上采样器（48→65、32→65、native→work），**没有 work→native 抽取器**。
Python 侧有 `resample_poly` 路径可先建立离线 oracle，但反应式 TWR 需要
C++ 实现 + buffer 复用 + 时间映射。

**疑问**：M2-A 是先做"Python 离线 oracle 证明 native 往返可行"（快，但证明力弱），
还是直接上 C++ 实现（慢，但直接可用于 M3）？我倾向后者，理由是 Python 路径无法
复用 buffer、无法验证时间映射，而这正是 M3 上板要依赖的部分。

### 5.5 时序预算的硬下界来自一个未定的 RMARKER 假定
实测：PollRMARKER → Response 首芯片 ≥ **117.372 µs**（假定 RMARKER 在
`PreambleStart`）。但 RMARKER 的绝对约定**仍是 OPEN**（M2/M5 对照芯片文档）。

DS 一次 exchange 纯 RF 帧时长 = 117.37 + 127.63 + 132.76 = **377.76 µs**（未含两次
turnaround）。主机侧五项延迟全部 `UNMEASURED`，
`min_feasible_reply_delay = NOT_COMPUTED`。

**疑问**：RMARKER 的绝对约定该在 M2 就钉死，还是先按"帧尾相对实际 marker 的偏移"
做相对预算、等 M3 上板再标定？我担心现在钉死会引入一个后来被推翻的常量。
