## 1. 评审结论

**需要修改，暂不认可“M0.1 已完成、四层契约冻结”。**

上轮发现已得到实质处理：PHR 类型分离、14 B frame authority、源配置/getter 复制隔离、
分数排序、原始 IQ timestamp 拒绝、证据标注、Python CTest 和库加载路径均有改进。

可以继续准备独立数学 oracle；M1 的生产接口、ToF 准入与配置绑定应先关闭以下问题。

## 2. Findings

### N01 / P1：JSON 越界整数先截断，再作为合法配置接受

位置：`gr-uwb/include/gnuradio/uwb/uwb_twr_config.h:6021`、`:6055`；
`gr-uwb/python/uwb/twr_config.py:6280`、`:6321`、`:6415`、`:6433`。

C++ `get_i64()` 后直接 cast 到 uint8/16/32；Python 新增 `_u8/_u16/_u32` 掩码，
主动复制这个行为。后续 validator 看不到原始越界值。
从 corpus 的 `ss_initiator` base 单独修改一字段，实测两端全部 import/validate 成功：

| 原始 JSON 字段和值 | 实际采用值 |
|---|---|
| `phy.channel = 261` | 5 |
| `session.session_id = 4294967297` | 1 |
| `frame.geometry.mac_header_bytes = 65550` | 14 |
| `session.local_address = 65537` | 1 |

这违反参数越界拒绝、无静默回落及 R3 不截断 session 的要求；可造成错误信道、地址/
session 碰撞，也会让 requested/hash 失去原始输入。`session_id_to_wire()` 本身拒绝超限，
但输入已在 JSON→uint32 阶段被截断，无法挽救这条实际执行路径。

**修复**：reader 在收窄前按目标字段/协议范围检查；负数转 unsigned 同样必须拒绝。
补 uint8/16/32 边界及“加一个模数后落回合法值”的语料。两端共同拒绝这些输入，
不能把 C++ 的 cast 行为当作配置规范。schema 的精度和量化变更须显式记录。

### N02 / P1：测距准入门拒绝全部 scheduled_calibrated TX，违背既定 X410 路线

位置：`uwb_twr_tof_input.h:756`；`qa_uwb_twr_tof_input.cc:514`。
需求对照：`docs/twr/需求_UWB_SS_DS_TWR.md:206`（REQ-TIME-03）。

需求明确允许确定性定时加标定得到合格 TX timestamp，要求保留
`scheduled_calibrated` 来源并关联 async error。新门却只接受 `HardwareMeasured`，
QA 也明确断言 calibrated scheduled **TX** 必须被拒。
实测：完整 corrections、有效 calibration context 的 `RmarkerTx` 将 source 改成
`ScheduledCalibrated`，即返回 `not_measured`。

这会使计划中的 X410 timed TX 无法进入 SS/DS，除非后续错误地将来源改成
`HardwareMeasured`。拒绝预测 RX 是正确的；不能据此拒绝需求允许的校准 TX。

**修复**：按 marker/source/发送状态分别建规则。scheduled TX 需明确 command time、
实际量化时刻、marker offset、校准和发送有效性证据；仅 `send()` 成功不够。
相关 late/underflow/取消必须使 exchange 无效；终态收敛之前可以保存 planned 时间，
但不能提前发布有效距离。最终结果仍标 scheduled_calibrated，绝不伪装成硬件回读。

### N03 / P2：lossless 判定与真正写出的 ns 数值仍不一致

位置：`uwb_twr_timestamp.h:1533`、`:1536`、`:1542`。

新 predicate 用精确整除判断理论 ns 是否为整数，但真正输出走 double 除法/乘法后
截断。浮点值落到整数下方时，会丢 1 ns，predicate 仍是 true。
本次通过公共 `timestamp_interval()` 复现：

| tick rate | ticks | 精确 ns | 返回 ns | lossless |
|---|---:|---:|---:|---|
| 737.28 MHz | 361728 | 490625 | 490624 | true |
| 491.52 MHz | 241152 | 490625 | 490624 | true |
| 998.4 MHz | 8112 | 8125 | 8124 | true |
| 63.8976 GHz | 519168 | 8125 | 8124 | true |

最小例子还有 1 GHz 的 15 ticks 返回 14 ns。当前独立验证只测 1 tick @737.28 MHz
的“不精确”情况，漏掉了“理论精确、实际投影错误”。

**修复**：投影结果和 lossless 标志由同一套受溢出保护的有理数商/余数产生，
不要用 epsilon 补偿 double 后再截断。新增 exact 值断言；不能只断言两个同源
predicate 相等。现有 RelativeTickInterval 保留正确 tick 值，因此不能把该缺陷
描述为已实现 ToF 的距离误差；它直接破坏的是时间投影/序列化契约。

### N04 / P2：interval 的最大范围在加入 fraction 后没有重验

位置：`uwb_twr_timestamp.h:1294`、`:1451`、`:1525`；
`uwb_twr_tof_input.h:1055` 附近的 interval 准入。

8-bit domain，earlier=`0+1/4`、later=`128+3/4`：整数差 128 先通过 raw gate，
合并 fraction 后变成 **128.5** ticks，仍返回 Ok。具备有效校准上下文时，
`admit_ranging_interval()` 也返回 admitted=true。超过半周期却得到准入。

这里不是反对“已知 later/earlier 时允许恰好半周期”的已说明策略；问题是最终值
超过了该 API 自己规定的半周期上界。排序函数的穷举通过不能替代 interval 检验。

**修复**：规范化 tick+fraction 后检查完整区间上界；补 P/2−fraction、P/2、
P/2+fraction、跨回绕和交换端点用例。如果协议采用其他最大 interval 策略，
用显式策略/预算传入，不能靠忽略 fraction 放宽。

### N05 / P2：R8 在最终集成版本仍未关闭，安装消费者记录已过期

位置：`include/gnuradio/uwb/CMakeLists.txt:59`；
`apps/install_consumer/install_consumer.cc:70`、`install_consumer.py:66`。

**修复**：安装新准入头；消费者验证当前 schema 并真实使用准入入口；对最终 HEAD

QA 专用 `uwb_twr_test_output.h` 是否要作为公共安装头也应重新收窄职责。

### N06 / P2：公开 thaw() 仍能解除运行快照的 capability 冻结

位置：`twr_config.py:2231`、`:5638`。

`snapshot.caps` 返回内部表，公开 `thaw()` 直接解除它的 `_frozen`。无需访问任何
私有成员，下面调用就使运行中的能力表可变：

```python
s = T.TwrConfigSnapshot(T.effective_config(c), T.capabilities())
s.caps.thaw()
s.caps.channels.append(9)
# s.caps.read_only == False
```

修改 channels 本身不一定足以让新 PHY 行通过所有联合校验，但它已经违反快照
capability 不可变保证；thaw 后同样能改整个矩阵、版本及其他校验依据。

**修复**：公共 mutable copy 返回独立对象；内部 thaw 仅对新副本操作，不能公开原地
解冻运行表。或 caps getter 返回隔离副本。新增通过公开 API 修改 snapshot.caps 的测试。
Python 的任意私有反射篡改不在此评审范围；这里是正常公开方法留下的绕过路径。

## 4. 对报告五个决策点的建议

| 决策 | 建议与理由 |
|---|---|
| Python 是否继续双轨 | **现在切向 C++ 权威 + pybind 薄接口。** 先修 N01 并独立确定语义，再绑定；不能把错误语义统一得更彻底。Python 保留 dataclass/builder/JSON 易用接口，执行前走同一 validator。短期双轨仅作为迁移过渡，禁止继续分别扩充全部业务规则。 |
| 五类证据是否太细 | **保留五类区分，但不要无条件按一个 ordinal 推导所有证据。** 硬件解码通过不天然证明 ToA，vendor 收发通过也不天然证明精度。每项保存 profile、方向、算法/固件版本、测试条件和证据引用；用途 gate 检查所需集合。阶段入口可以串行，实测证据仍分别记录。 |
| 16 SYNC 是否删除 | **保留 decode-only 行，测距用途继续禁用。** 64 SYNC 当前同样没有 ToA 证据，不能默认当成已验证测距配置。配置合法、试验许可和正式结果有效性分开；否则“未验证就不能测试、没测试又不能验证”会形成闭环死锁。 |
| M2-A 先 Python 还是 C++ | **先做短帧 Python 离线参考，再实现 C++，使用同一组输入对照。** 复用既有 resample_poly，验证完整帧、FCS、冲激/延迟/相位位置；再明确 C++ FIR 延迟、边界、缩放和 buffer 生命周期。Python 不进实时回复路径；它能验证数学映射，不能证明 C++ 性能。MATLAB 独立对照仍保留。 |
| RMARKER 何时确定 | **M2 定义协议参考点及 work-grid offset；M3 测设备/链路延迟；M5 逐厂商 adapter 核对。** 语义常量与校准量分开、按 profile 版本管理。当前仅做相对 marker→帧尾预算，117.372 µs 继续注明 PreambleStart 假设，不变成通用下界。 |
| 三提交是否推送 | **可以作为待评审分支发布，不能标为验收通过或合并 main。** 先补本评审结论和必要交付文档，让远端看见完整上下文。本次请求是评审，未执行 push；本地 tracking ref 显示 ahead 3，没有重新核实远端网络状态。 |

pybind 迁移应先绑定 config/frame/validation 的少量稳定入口，保持既有 Python 调用
形态；JSON、错误格式化和 capability 描述分离到冷路径。不要再把 7000 行文件仅拆成
几个文件后继续维护两套规则。新增 timestamp 准入中的 string/value 拷贝还需要在 M1/M2
集成时测分配次数；不能仅凭 header-only、无 UHD 依赖推断实时路径无分配。
