## 3. 失败项详述

### 3.1 唯一失败项：`#14 uwb_qa_uwb_pdu_rational_resampler.cc`

**失败范围：整个 test binary 判定 Failed，内部 1 个 test case
`test_pdu_resampler_throughput_sanity` 失败，产生 3 条断言错误。**
该文件其余 13 个 test case 全部通过（upfirdn golden、坐标映射、CaptureOnly、
坏输入率、短 guard、e2e 抽取+重采样+实时解调+FCS 等功能性断言均通过）。
即：**这是纯性能断言失败，不是数值/功能正确性失败。**

失败断言源码位置与阈值（`gr-uwb/lib/qa_uwb_pdu_rational_resampler.cc`，
`BOOST_AUTO_TEST_CASE(test_pdu_resampler_throughput_sanity)`，line 768 起）：

```cpp
const double cont_best_in_msps = 260.7;   // line 826，连续流 best 参考值
...
const double pdus_s  = blk->pdus_emitted() / wall;      // line 814
const double in_msps = 1e-6 * total_input_samples() / wall;  // line 820

BOOST_REQUIRE_EQUAL(blk->pdus_emitted(), 80);           // line 839 —— 通过
BOOST_CHECK_GT(pdus_s, 400.0);                          // line 841 —— 失败
BOOST_CHECK_GT(headroom_200, 2.0);                      // line 842 —— 失败
BOOST_CHECK_GT(in_msps, 50.0);                          // line 844 —— 失败
```

测试规模（line 775–792）：输入 737.28 MS/s → 输出 998.4 MS/s（65/48），
tap 文件 `testdata/resampler_65_48/taps_realtime_minorder.txt`（5276 B =
1319 × float32，与源码注释 "realtime_minorder (1319 taps)" 一致），
每 PDU `pre=8000 / cap=140000 / post=4000` 样点，连续投递 80 个 PDU，
PDU 路径同步处理（`sync handler`）。

### 3.3 确定性与负载敏感性判定

**确定性：是（完全可复现，非 flake）。** 共 5 次串行执行，`pdus/s` 落在
**212.90 – 215.29**，极差 2.39 PDU/s，相对离散度 **< 1.2%**；`in_MS/s` 落在
26.29–32.72 的同一相对区间。`BOOST_REQUIRE_EQUAL(pdus_emitted, 80)` 每次都通过，
说明失败不是丢包或未排空导致的计时假象，而是稳定偏低的实际吞吐。

**与历史记录的一致性：一致。** `开发路线与验收矩阵.md` §6 记录
「单独复跑约 217 PDU/s，要求 >400」。本次 5 次串行实测均值 **≈ 214.1 PDU/s**，
与 217 相差 **< 1.5%**。历史结论在本机可复现，**成立**。

**负载影响：显著，且已被量化。** `-j8` 并行全量跑时测得 172.99 PDU/s，
比串行低约 **19%**（26.29 vs 32.61 `in_MS/s`）。因此：

- 本项失败在**任何**负载条件下都会发生——最宽松的串行实测 215.29 仍不到阈值 400 的 **54%**。
  阈值与实测相差 **≥ 1.86 倍**，负载波动不可能翻转结论。
- 但引用本项数字时**必须注明并行度**：报告「~214 PDU/s」应写「串行/单独复跑」；
  `-j8` 下为 ~173 PDU/s。历史记录的 ~217 对应串行口径。

**其他 agent 并行编译的影响：本项的失败判定不受影响。** 即使把机器负载推到最高
（末次复跑时 loadavg 1 分钟值 0.85–1.26），`pdus/s` 仍为 215.29，串行 5 次数据
单调收敛在同一窄带内，未见随负载上升而单调下降的趋势。

### 3.4 根因初判（仅记录，未定位、未修复）

- 串行实测 214 PDU/s、32.6 MS/s 输入吞吐，**仅为源码 line 826 记录的连续流 best 参考值
  `cont_best_in_msps = 260.7` 的 0.125 倍**，而该测试注释预期 PDU 路径只付出窗口样点代价、
  应「comfortably above」200 slot/s 的 QM35825 时隙率。
- 当前 `headroom_vs_200slot/s ≈ 1.07`，即**仅比 200 slot/s 高约 7%**，达不到断言要求的 2×
  裕量（400 PDU/s）。
- 同目录下 `radar_75us_pdu` 行输出 `steady_mean_handler_us=3597.5 p95_us=4895`，与
  「单窗处理约 3.6 ms」一致；80 窗 / 3.6 ms ≈ 22 ms 的纯计算量之外，其余为 handler 开销。
- 该项的**修复方向（重采样器多 worker 复用、窗内 guard 裁剪、或按目标时隙率下调断言）
  本次不作为 M0 范围**；M0 只做记录与定位线索留存。若后续调整该断言阈值或实现，
  必须按 REQ-REG-01 在同一测量配置下前后对照，且不得把数值下降说成吞吐提升。
