## 1. 结论

**M0 已有较完整的配置、帧和时间类型草案及离线测试，但不宜按“全部冻结、验收完成”进入 M1。**

修复快照和时间运算，再做独立协议核心。两路 RX、分数首径、delayed TX 和 SS/DS
状态机仍未实现；本次没有硬件、MATLAB 或商用模组验收。

可以保留的成果：协议核心与 GNU Radio/UHD 解耦方向、固定容量 frame codec、
明确的 clock domain/epoch/marker、FCS 单层负责、离线 PHY 扫描和时序预算框架。
这些成果有价值，但测试通过不能替代不同模块之间的契约一致性检查。

## 2. 必须先修复的问题

### R1 / P1：Python 快照实际共享可变对象

位置：`gr-uwb/python/uwb/twr_config.py:3743`、`:3889`。

`effective_config()` 把同一 `cfg` 赋给 requested/effective，readback 也直接引用；
`TwrConfigSnapshot` 直接保存传入对象，`get()` 返回内部可变对象。
因此绕过 `set_overrides()` 就能在 exchange 中修改已校验配置，hash、ok、量化结果
仍保留旧值。现有测试只比较快照初值，没有验证修改隔离。

实测：用 `apps/test_twr_config.py` 的 `_minimal()` 建立合法配置，再把原对象 channel
改为 9，快照随之变成 9，`ok=True`、hash 不变，但重新 `validate()` 已失败。

修复：配置边界深复制/值语义，递归只读内部快照或 getter 返回副本；同时隔离 caps、
readback、嵌套列表。复制只在 configure/exchange 边界发生，不进入 IQ 或逐样本路径。

### R2 / P1：PHR 速率校验与实际调制器相反

位置：`uwb_twr_config.h:2677`、`twr_config.py:2764`；
对照 `uwb_hrp_mod_core.h:10`、`:44`、`:1006`。

C++/Python 均要求 `phr_rate == data_rate`，白名单只允许 6.81 Mb/s 数据，
因此它们接受 6.81 Mb/s PHR，却拒绝现有调制器真实使用的 0.85 Mb/s PHR。
调制器的 PHR 是 21 symbols、512 chips/symbol；PHR 内的数据速率字段描述 payload
速率，不能据此推断 PHR 自身的调制速率。

修复：分别校验两种速率；当前 profile 固定为实际支持的 PHR=0.85 / data=6.81，
新增高 PHR 速率需另行实现及验证。Qorvo API 也明确区分这两个字段，见 §5。

### R3 / P1：配置 schema 与 frame v1 仍是两套几何和字段宽度

位置：`apps/test_twr_config.py:97`、`:637`；`uwb_twr_frame.h:423`。

当前被测试为合法的配置使用 `mac_header_bytes=7`、`session_id=0x11223344`，
effective budget 断言仍是空口 9/19/24 B。frame v1 实际是 14 字节头、16-bit session，
空口 16/26/31 B。C++ config 的 session 类型为 uint32；codec 为 uint16。
测试分别通过，但不证明 accepted config 能无损构造实际 frame。

这会低估 buffer/帧时长预算；将 session 直接缩窄还会引入碰撞。
若希望支持多种 frame profile，必须有 profile→codec 的显式选择及验证，
不能用任意非空 profile 字符串把当前未实现的几何作为可执行配置。

修复：frame profile 提供唯一长度/宽度权威；定义本地会话 ID 与 wire session ID
是否分离及映射规则；加 `validate → encode → append FCS → 实际样本数` 集成测试。

### R4 / P1：时间间隔的“精确”标志不成立

位置：`uwb_twr_timestamp.h:1236`；报告 §11 第 5 条。

737.28 MHz 下 1 tick = 1.356336805… ns。实测 `timestamp_interval()` 返回
`ticks=1, duration.nanos()=1, duration_is_tick_exact=true`。
“tick 至少 1 ns”不等于“换算后是整数 ns”；这里是截断，已经丢失精度。
按报告建议只在该标志为 false 时使用 ticks，会让 M1 ToF 引入系统量化误差。

修复：ToF 始终在相对 tick+fraction 或明确归一化的高精度相对时间上计算；
整数 ns 只作 API/显示投影。若保留 exact 标志，必须判定实际换算无损，
不能仅依据 tick 频率。顺带补足 Duration 溢出边界及舍入规则测试。

### R5 / P1：模时间排序边界和亚 tick 顺序错误

位置：`uwb_twr_timestamp.h:1018`、`:1283`。

8-bit 时钟上，实测 0 与 128 两个 timestamp：`precedes(0,128)` 和
`precedes(128,0)` 均成功返回 true。代码使用 `> period/2`，没有拒绝等于半周期。
同一整数 tick 的 0.25 与 0.75 也被排序函数当成相等。

修复：若采用半周期串号排序策略，严格要求距离小于半周期，并把 fraction 纳入
比较及边界判定；补双向比较、零点跨越、恰好半周期及 ±fraction 测试。
半周期是当前无额外历史信息的排序策略；在有明确先后顺序和最大持续时间约束时，
模间隔可以使用不同策略，不应把“半周期”写成所有协议/芯片的普遍硬件定律。

### R6 / P1：原始 IQ timestamp 仍可通过 interval API

位置：`uwb_twr_timestamp.h:332`、`:1145`、`:925`。

两个 `UhdRxFirstIqSample + HardwareMeasured + 无 corrections` 的 timestamp
可产生 `status=Ok` 的 interval；本次 C++ 复现已确认。
这作为通用采样时间差工具可以合理，但与报告“裸设备时间戳无法产出协议 interval”不符。

修复：明确通用 interval 与测距输入的边界；ToF 接口逐项检查 range-capable、
marker、校准和质量条件，或引入已验证测距时间类型。不能把 `interval.status==Ok`
单独作为计算距离的授权条件；也不能只设置 correction bits 冒充做过实际映射。

### R7 / P2：能力白名单的证据范围被扩大

位置：`qa_uwb_twr_phy_matrix.cc:545`、`:1774`；`uwb_twr_config.h:1610`。

原 CSV 共 318 行，路径名均为 `work_direct_998p4*`；其中 7 行 `not_run`。
第二张表 84 行，其中 48 行 supported。它证明 work-grid TX/RX 自洽；
表内 `native_rate_hz=737280000` 标签不等于完成了 native 下采样→上采样闭环。

建议能力分别记录 `work_decode_verified`、`native_roundtrip_verified`、
`toa_verified`、`hardware_verified`、`vendor_interop_verified`，并保留证据来源。
M0 work-grid 支持不能直接解释成可上板测距；16 SYNC 的首径精度仍待验。

### R8 / P2：安装与回归入口缺项

`include/gnuradio/uwb/CMakeLists.txt` 未安装四个 TWR 头文件；
`python/uwb/CMakeLists.txt` 只安装 `__init__.py`，遗漏 `twr_config.py`。
Python QA 也未注册 CTest。源码树测试通过，不等于安装后的 API 可用。

修复：完善 install/CTest，使用临时 DESTDIR 验证外部 include/import；
不依赖源码树或 build/test_modules 掩盖遗漏。

## 3. 报告中的技术结论纠正

| 原结论 | 核实结果及对开发的影响 |
|---|---|
| 没有 work→native，原生栅格无法调制 TWR | 仓库已有 `apps/x410_cg400_hrp_echo_cir.py:184` 的 `NativeRateProfile.tx_native()`，用 48/65、32/65 `resample_poly`。缺口应写为适合反应式 TWR 的 C++ 转换、内存复用和时间映射集成；可先复用现有路径建立离线 oracle。 |
| 128/256/512 因 PHR 不逐值自描述而无法支持 | Qorvo API 支持这些长度，其中 DW3xxx 将它们列为 non-standard preamble lengths。当前软件 decoder/CFO 有限制，不等于商用芯片不能工作。应保留“当前 profile 暂拒绝”，移除“永久结构性不可能”的冻结结论。 |
| `EXEC_LATE_CMDS(1)` 说明迟到定时 TX 一律立即发 | 该参数用于 X4xx ctrlport 定时控制路径。TX 数据另有 `radio_tx_core.v:333`，迟到触发 `ERR_TX_LATE_DATA` 并进入错误策略；不能混为一谈。必须同时处理主机 deadline 和设备 async 错误。 |
| 自建有界队列就能限制消息排队 | GNU Radio PMT 入口仍可能积压。需要生产者 credits/限速/背压或显式限制入口；owner 队列有界不是整个系统内存有界的证明。 |
| backend 接口结构上绝不可能接收驱动 | 现接口强耦合预定 TX/RX pair，确需适配；但 RX 后生成新 schedule 并非数学上不可能。应以 listen-only、两个 RX 路由、取消、资源仲裁等用例决定扩展接口，而非推倒重写既有 timed I/O。 |
| 所有 tagged_stream_block 都应排除 | 消息型 controller 采用零流端口 `gr::block` 合理；其他 adapter 应按 scheduler 语义和实际分配路径选型。保持热路径不分配的要求，不把 controller 选型变成对所有模块的 blanket 禁令。 |
| CTest 必然用新库，直接运行必然不可信，必须 sudo install | 本机生成的测试脚本继承 `LD_LIBRARY_PATH`。实测默认 `ldd` 指向 `/usr/local/lib`，`env -u LD_LIBRARY_PATH ldd` 才指向 build/lib。应验证加载路径，CTest 也需正确环境；测试不要求系统安装。 |

局部 RTL 证据：`/home/oi/uhd/uhd/fpga/usrp3/top/x400/x4xx_core_common.v:428`
和 `fpga/usrp3/lib/rfnoc/blocks/rfnoc_block_radio/radio_tx_core.v:333`。
这是本地源码行为，仍需将实际设备 FPGA/UHD 版本写入 M3 manifest 后验证。

此外：

- 零注入 CFO 是已知真值 0 Hz；有噪声时应报告误差分布，不能因注入为零而排除误差。
- 几何映射残差 0 是坐标自洽证据，不是首径或物理测距精度证据。
- “117.372 µs”来自候选 RMARKER=PreambleStart 的预算；RMARKER 未确定前，
  不能作为所有 reply-delay 定义的统一下限。帧尾相对实际 marker 的偏移才是预算起点。
- 四个头共 9315 行属实；五个 C++ QA 是 **9516** 行，非 10516；Python schema
  当前 **4899** 行；目录是 **6 CSV + 1 JSON**。这些计数不应当成完成度指标。
- 自定义 14 B 帧不自动等同于 Decawave 示例 MAC；M5 要按具体固件适配字节格式、
  FCF/寻址与 timestamp 单位。当前 frame v1 只能视为阶段一内部协议。
