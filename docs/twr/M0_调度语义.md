| **B. 端点化 FSM + message/PDU controller + 共用 radio owner** | 纯 C++ `twr_core`（FSM/算式/codec）+ 零流端口 `twr_controller`（消息/PDU，短 handler、有界事件队列）+ 一个 radio owner | `uwb_realtime_echo_timer`（零流端口 block + worker）、`uwb_realtime_demodulator`（有界队列 + worker）、`uwb_pdu_window_crop` / `uwb_pdu_rational_resampler_*`（PDU 链） |
| **C. tagged_stream_block 端到端** | 用 `packet_len` 把"一次 exchange"包成流，包进包出 | `uwb_echo_timer_stream.{h,cc}` |

### 3.2 选型：**Model B 为主，A 的 radio 适配层复用，C 只用于 PHY 采集链**

**一句话理由**：TWR 的响应时刻是**实际观测到的 RX 事件**决定的，而
`IRadioBurstBackend` 的三元组接口把 `rx_ticks` 在 `issue_rx()` 之前就**冻结**了
（`uwb_echo_burst_backend.h:101-107` `RxCommand::rx_ticks`；`:159` `issue_rx` 的
契约写明 `with rx_ticks in the device future`），`collect_result()` 又只等一个
`schedule_index`（`:174-176`）——**反应时刻根本无处表达**。因此 FSM 必须上移到
一个以"帧事件"为输入的端点对象，而不是以"计划索引"为输入的调度器。

具体分层与 block 类型：

| 组件 | 类型 | 理由（对应规则 2/3） |
|---|---|---|
| `twr_core`（FSM + ToF/clock/wrap + frame codec） | **纯 C++，不是 block** | 无 I/O、无 stream 口。REQ-GR-01 要求"C++ worker 驱动协议"。放成 block 会强行引入 stream 端口和调度器约束，M1 的"不依赖 UHD 即可运行 + fake radio 测试"也无法成立 |
| `twr_controller`（对外） | **`gr::block`，`io_signature::make(0,0,0)` / `make(0,0,0)`，纯消息/PDU** | ① 唯一入向是"解出的帧"（PDU），唯一出向是"结果/状态"（PDU），没有流；② `tpb_thread_body.cc:74-81` 证明 handler 跑在该 block 的线程上，`basic_block.h:395-400` 证明它与 `work()` 互斥 → **绝不能在里面做 I/O 或长计算**；③ 0 流口的 block 走 `tpb_thread_body.cc:96-104` 的 `BLKD_IN` 分支，不占 buffer、不做数据搬运。本仓库 `uwb_realtime_echo_timer.cc:337-339` 就是这个签名，已在生产使用 |
| `twr_controller` 的入向 handler | **短 handler：只做校验 + 有界入队** | `basic_block.cc:187` `push_back` 无上限 → 上游不慢就会撑爆内存；`tpb_thread_body.cc:79` 是**排空式**循环 → 慢 handler 直接堆队列。REQ-GR-01 原文"短 handler、有界事件队列"就是这两条约束的结论 |
| 反应时序的执行者 | **block 私有 `std::thread`（owner 线程）** | ① `usrp_sink_impl.cc:46` 就是 GR 自己的做法（block 自建 `gr::thread::thread` 跑 `async_event_loop`）；② 只有自建线程能同时做「阻塞 recv / 阻塞 send / 定时等待」而不占用 TBR 线程；③ `uwb_realtime_echo_timer.cc:863` `d_worker_ = std::thread(&UwbRealtimeEchoTimer::worker_loop, this)` 是本仓库已有的同款 |
| radio owner（一个 `multi_usrp` + 2 RX + 2 TX 路由） | **不是 block**，是 owner 线程独占的 `uhd::usrp::multi_usrp` + streamers | REQ-GR-01 明确"同一个 UHD 设备只由一个明确的资源管理者协调时间初始化、调谐、streamer 和两个端点，不并发创建互相冲突的 radio owner"。`uwb_uhd_burst_backend.cc:542-549` 已经是单 owner（1 TX streamer + 1 RX streamer），TWR 要把 `rx_args.channels` 从 1 个扩到 2 个 |
| PHY 接收链（检测/抽取/重采样/解调） | **保持现状，全部 `gr::sync_block`（流口）+ PDU `gr::block`** | `uwb_auto_scheduled_extractor_sc16`(`:59` `sync_block`)、`uwb_detector_sc16`(`:sync_block`)、`uwb_pdu_window_crop`(`:43` `gr::block`)、`uwb_pdu_rational_resampler_ccf_65_48`(`:43` `gr::block`)、`uwb_realtime_demodulator`(`:149-151` `0/0 gr::block`)。这些不因 TWR 改类型 |
| `usrp_source` 兼容路径（可选，仅采集/回放） | **`gr::sync_block`（`usrp_block` 基类）** | 见 §2.1。**不作为反应时序路径**：`usrp_source_impl.cc:601-612` 的 `work()` 持 `d_mutex` 且阻塞 `recv`，无法在 µs 级 turnaround 内反应 |

### 3.3 为什么 Model A 不可直接扩展（逐条引用）

1. **`rx_ticks` 在 arm 之前冻结**：`uwb_echo_burst_backend.h:101-107` 定义 `RxCommand{schedule_index, rx_ticks, total_samples, fragments}`；`:156-159` 契约要求 `issue_rx()` `with rx_ticks in the device future`。反应式 responder 无法在 `issue_rx()` 时知道 Poll 的到达时刻，只能先开一个**大窗口**。
2. **结果按 `schedule_index` 归并**：`:174-176` `collect_result(schedule_index, wait_ms, out)`；`uwb_uhd_burst_backend.cc:903-907` 若 `armed_index != schedule_index` 直接报错。Responder 的 exchange 编号来自对端地址/序号，**不是本地计划索引**，两者不是一一映射。
3. **RX 必须先于 TX 提交**：`uwb_uhd_burst_backend.cc:723-727` `if (!impl.rx_armed || impl.armed_index != cmd.schedule_index) → BrokenChain`；`uwb_echo_burst_backend.h:155-158` 明确 `MUST be called before issue_tx() for the same schedule index`。反应式 responder 的 TX 命令时间**由 RX 结果算出**，而 RX 窗口是提前开好的——"先 RX 后 TX"仍然成立，但绑定关系从 `schedule_index` 变成 `exchange_id`，属于接口变更而非复用。
4. **RX 窗口只能开一个**：`uwb_uhd_burst_backend.cc:663-668` 一次 `issue_stream_cmd(STREAM_MODE_NUM_SAMPS_AND_DONE, num_samps=cmd.total_samples)`。TWR responder 需要的是**连续/滚动**接收 + 按协议时间范围预开窗（REQ-GR-02），不是固定 `num_samps` 的一次性窗口。
5. **Model A 的两个现有实现都不适合**：
   - `uwb_realtime_echo_timer` 是 `0/0` 的 message-only block + 私有 worker（`uwb_realtime_echo_timer.cc:337-339, 863`）→ **形态已对，但内容是 schedule 驱动**（`run_one_burst()` `:1854-1885` 直接 `d_grid_.next_schedule(now, slot)`）。**要复用的是它的线程/队列/生命周期骨架，不是它的 `EchoGrid`。**
   - `uwb_echo_timer_stream` 是 `tagged_stream_block` 且 **`work()` 内阻塞在 `collect_result`**（`uwb_echo_timer_stream.h:26-28` `work() blocks in the backend's collect_result wait — exactly ONE burst per call`；`uwb_echo_timer_stream.cc:7-9`）。反应式 responder 不能在一次 `work()` 里等一个预定 burst，否则整个 block 会停在这个 burst 上（`block_executor.cc:291-293` 的 `noutput_items` 由上游 buffer 决定，停顿直接反压上游）。
6. **一个 X410 两个 channel 各自成端点**：`uwb_uhd_burst_backend.cc:542-549` 现在只有 `rx_args.channels = {rx_channel}`（默认 `rx_channel = 1`，`uwb_uhd_backend_config.h:283`），且 TX 侧用 `kEchoMaxTxChannels = 4` 固定上界（`uwb_echo_multitx.h:45`，`TxCommand::tx_channel_count` 在 `uwb_echo_burst_backend.h:97`）。两 RX / 两 TX 路由在 `IRadioBurstBackend` 里没有表达位置（`TxCommand` 有 `tx_channel_count`，`RxCommand`（`:101-107`）**没有** channel 概念）。这是接口层面的缺口。

**结论**：保留 `IRadioBurstBackend` 的**错误语义与映射表**（`BurstStatus` `:53-62`、fragment flag 契约 `:64-72`、`map_uhd_rx_error_code` `uwb_uhd_backend_config.h:76-91` / `map_uhd_tx_async_event` `:100-126`、UHD ABI 常量 `:53-70`），不复用它的 `schedule_index` 三元组签名。TWR 新增 `ITwrRadio`（`arm_rx_window / await_frame / submit_delayed_tx / abort`），`UhdTwrRadio` 内部可复用 `uwb_uhd_burst_backend.cc` 里的 device 打开、严格 readback（`:475-503`）、fragment 校验（`validate_fragment_flags`）、async 线程与计数（`:1014` 的定长 `std::array`）等已经调通的代码。

## 4. 调度语义

### 4.1 线程模型

```
TBR thread A (usrp_source 0/0 gr::sync_block)   ── recv() 阻塞 ──► 设备
TBR thread B (PHY 链 sync_block)                ── work()
TBR thread C (twr_controller, 0/0 gr::block)    ── 短 handler：校验 + 入队
TBR thread D..N (PDU demod blocks)              ── work()
--- 以下不属于 TBR ---
owner thread (block 私有 std::thread)           ── 反应时序 / 全部 UHD I/O
UHD 内部线程（xport IO / async msg）             ── 设备 I/O
```

依据：

- **消息 handler 在 block 自己的 TBR 线程上跑**：`tpb_thread_body.cc:74-81` 与 `:96-97` 在**同一个 `while(1)` 循环体**内先排空消息再 `run_one_iteration()`。
- **handler 与 work 互斥**：`basic_block.h:395-400`（`block` 子类的线程安全由 runtime 保证）。
- **排队在 block 内部**：`tpb_thread_body.cc:79` 是 `while ((msg = delete_head_nowait(...)))` 排空式，所以 handler 慢 = 上游 `basic_block::msg_queue`（`basic_block.h:70` 的 `std::deque`）无界增长 + `basic_block.cc:187` 无上限 `push_back`。
- **TBR 线程的唤醒不是抢占式的**：`tpb_thread_body.cc:131-138` 阻塞在 `input_cond.timed_wait(guard, blkd_input_timer_value())`；`block.cc:389` 默认值来自构造。
- **0 流口 block 也占一条 TBR 线程**：`scheduler_tpb.cc:74-88` 对每个 block 都 `create_thread`；`tpb_thread_body.cc:98-104` 对 0/0 block 返回 `BLKD_IN` 循环。所以 `twr_controller` 只是"不搬数据"，**不是"不占线程"**。它的 handler 必须短。

### 4.2 队列

| 队列 | 上界 | 谁维护 | 满时行为 |
|---|---|---|---|
| PMT 连接队列（GR 内部） | **无界**（`basic_block.cc:187`） | GNU Radio | 不适用——所以我们不能依赖它限流 |
| `twr_controller` 事件队列 | 构造期参数 `event_queue_entries`（>0，构造期校验） | 我们的 block | handler 拒绝 + `status` 事件 `queue_full`（照 `uwb_realtime_demodulator.cc:596-607`） |
| RX 窗口队列（owner 线程） | 构造期参数 `max_pending_rx` | 我们的 block | 显式失败 `rx_overflow`（REQ-ERR-01） |
| 结果出队 | 构造期参数 | Python 侧慢回调**不得**阻塞 owner 线程（REQ-API-05） | 结果环形满 → 计入 `results_dropped` |

参考实现：`uwb_realtime_echo_timer.cc:1498-1513 enqueue()`（`d_queue_.size() >= d_queue_capacity_ → return false`，并维护 `d_queue_high_watermark_`）；`worker_loop()` `:1519-1572`（`unique_lock` + `d_queue_cv_` + 三个 wait 谓词：`d_stop_ || !d_queue_.empty() || d_armed_`）；`UwbRealtimeDemodulator::enqueue` `uwb_realtime_demodulator.cc:649-658`。

**注意**：`std::deque<Job> d_queue_` 在 `push_back` 时会分配。参考实现接受这一点（队列长度有界、`Job` 很小）。若 TWR 事件队列要严格"handler 内零分配"，须改成**预分配的定长环形**（`std::vector<Job>` 预分配 N + `head/tail` 原子下标，`std::array<Impl::AsyncEvent, kMaxAsyncEvents>` 就是本仓库已有的定长 drain 目标写法，`uwb_uhd_burst_backend.cc:1011-1014`）。**选哪一种留给 M1 定，本文只记录取舍。**

### 4.3 allocation 纪律

**必须在 `work()/general_work()`/handler 内零分配**（AGENTS.md 规则 4）。本仓库已有的 `reserve` 范式：

| 结构 | 位置 | 预留内容 |
|---|---|---|
| `HrpModScratch::reserve(max_psdu_bytes, max_samples)` | `uwb_hrp_mod_core.h:336-354` | `psdu_bits / rs_cw / conv_in / coded / phr19 / g0 / g1 / spread / iq_re`，`iq_im.assign(max_samples, 0.f)`（`:352`），`prefix.samples`（`:353`） |
| `DemodScratch::reserve(n)` | `uwb_demod_core.h:132-143` | `work/derotated/energy/metric/corr/soft_chips/cir_taps(64)/peaks(256)/peak_values(256)`；`:117-120` 注释 `Pre-allocated at construction and reused across jobs to avoid per-packet allocation in the hot path.` |
| `EchoScheduler` scratch | `uwb_realtime_echo_timer.cc:379, 383` | `d_rx_buf_.assign(max_rx_samples*2, 0)`、`d_zero_scratch_.assign(max_tx_samples*2, 0)` |
| `reserve(...)` 列表 | `uwb_realtime_echo_timer.cc:386-390` | `d_mtx_payloads_(kEchoMaxTxChannels)`、`d_mtx_freqs_(2048)`、`d_mtx_overlap_lead_/lag_(2048)` |
| 固定 fragment 数组 | `uwb_echo_timer_stream.h:266-267` | `d_txf_[kEchoMaxFragmentsPerBurst]`、`d_rxf_[...]` |
| 定长 async drain 目标 | `uwb_uhd_burst_backend.cc:1014` | `std::array<AsyncEvent, kMaxAsyncEvents>`，注释 `:1011-1013` `a worker-owned FIXED array — no std::vector on the hot path` |

**TWR 侧必须在构造期（或 `prepare()`/`start()`，`start()` 允许分配，参见
`uwb_echo_burst_backend.h:150-153`）预留的清单**（本文的建议，非源码结论）：

1. RX 滚动缓冲（两个端点各一份，按 `max_rx_window_samples * 2` int16，SC16）。
2. 调制 scratch（Response/Final 的波形 + 编码中间量）——按 `HrpModScratch` 范式，一个 `reserve(max_psdu_bytes, max_samples)`。
3. 解调 scratch（`DemodScratch::reserve(max_frame_samples)`）——**每个 worker 一份**（`uwb_realtime_demodulator.cc:157` `d_scratch_(num_workers)`，`:216-218` 循环 reserve）。
4. 帧/结果 POD 容器：固定大小 `std::array`（协议头最大长度、结果最大字段数），**不要 `std::string`**。
5. 事件队列：`event_queue_entries` 个 `Event` 的预分配存储。
6. 迟到回复的待发窗口表：`max_pending_tx` 个 `PendingTx`。
7. 统计/诊断的输出 PMT：**`pmt::make_dict()` 必然分配**。参考实现把 `publish_status` / `publish_burst` 放在 **owner 线程**（`uwb_realtime_echo_timer.cc:398-400` 的 `publish_burst`/`publish_status` 是 worker 调用的，不在 handler 路径）。**TWR 必须保持同一约定**：结果 PDU 的构造只发生在 owner 线程，handler 只构造**极小的**诊断 dict（或者更好：handler 不 publish，用一个 atomic flag 让 owner 线程 publish）。
8. `error` 字符串：`BurstResult::error` 是 `std::string`（`uwb_echo_burst_backend.h:128`），赋值会分配。TWR 的 owner 线程可以承受（不在 handler 内）；但**不要**把它放进 `work()`/handler 路径。预置一组 `const char*` 静态错误码表（`burst_status_to_string` `:216-237` 已经是这个形式），需要拼串时在 owner 线程做。

**明确禁止的写法**（本仓库内已有的反例，M1/M2 review 时逐条对照）：

- `tagged_stream_to_pdu_impl.cc:50,52,56,59`（GR 自己在 `work()` 里分配 4 次）
- `tagged_stream_block.cc:93`（基类 `general_work` 里 `std::vector<std::vector<tag_t>>`）
- `header_payload_demux_impl.cc:506,514`（`general_work` 里两个 `std::vector<tag_t>`）
- `header_payload_demux_impl.cc:442-443`（**消息 handler 里**按解出的可变长度调 `set_min_noutput_items`）
- `uwb_auto_scheduled_extractor_sc16.cc:1022` `pmt::init_s16vector(cap*2, iq)`（`work()` 内复制 PDU）——但这是 GR 生态里唯一能把流变 PDU 的办法，见 §4.5

### 4.4 `sync_block` / `block` / `tagged_stream_block` 的选择判据（规则 2）

| 判据 | 选 `sync_block` | 选 `block`（0 流口，消息/PDU） | 选 `tagged_stream_block` |
|---|---|---|---|
| 有 stream in/out 且**逐样点**处理 | ✅ `usrp_block`(`usrp_block.h:31`)、`UwbAutoScheduledExtractorSc16`(`:59`)、`UwbDetectorSc16` | | |
| 输入是**变长**、由 length tag 界定、且 tag 严格落在下一个待读样点 | | | ✅ `tagged_stream_to_pdu`(`:30-33`)、`UwbEchoTimerStream`(`:67`) |
| 只收发 PDU / 控制消息，无样点 | | ✅ `UwbRealtimeEchoTimer`(`:337-339`)、`UwbRealtimeDemodulator`(`:149-151`)、`UwbPduWindowCrop`(`:43`)、`UwbPduRationalResamplerCcf65_48`(`:43`) | |
| 需要在 `work()` 里做阻塞设备 I/O | ❌ 不可（会反压/卡住 flowgraph；`UwbEchoTimerStream` 已经这么干了，是**已知反例**） | ❌ handler 里更不可 | ❌ |

**TWR 落点**：协议控制面 = `block`（0/0，消息/PDU）+ 私有 owner 线程；PHY 数据面 = 现有 `sync_block` 链不变。**没有任何新组件是 `tagged_stream_block`。**

### 4.5 变长帧边界的处理（不要建 TSB）

理由：TSB 基类在 `general_work` 里分配（`tagged_stream_block.cc:93`），且要求 length tag 精确落在下一个待读位置否则 `throw`（`:102-105`）。两个都违反规则 4 / 稳健性。

替代方案（照搬本仓库既有做法）：**`sync_block`（或 `block` 带流口）在流内自己维护边界状态机，产出 PDU**。`UwbAutoScheduledExtractorSc16` 就是这个形态：`sync_block`（`uwb_auto_scheduled_extractor_sc16.h:59`），内部维护窗口/抽取状态，`work()` 里 `message_port_pub(pmt::mp("packet"), pmt::cons(meta, data))`（`uwb_auto_scheduled_extractor_sc16.cc:1022-1023`）。`data` 用 `pmt::init_s16vector` 构造（**一次分配**，在 `work()` 内），这是 GR 生态里不可回避的代价；我们的纪律是：**这一次分配之外，`work()` 内不再有任何分配**，并把分配量与 `max_pdu_samples` 显式绑成构造期参数（REQ-GR-03）。

### 4.6 帧头/载荷跨调度分段（`header_payload_demux` 的教训）

`header_payload_demux_impl.cc` 的状态机（`:39-46`、`:232-353`）给 TWR 的 `twr_core` 一个可复用的**结构**：

- 状态在对象里持久化，`general_work` 一次只推进一态，返回 `WORK_CALLED_PRODUCE`。
- 长度不够时**不 consume、不推进**，靠 `check_buffers_ready()`（`:178-206`）返回 false。
- `forecast()`（`:155-175`）随状态变化。

TWR 的 FSM 走消息/PDU 路径，不进 `general_work`，但**同样的纪律适用**：状态只能由 owner 线程改；任何"帧还没收全"的中间态不得触发 TX。

## 5. UHD timed TX / timed RX 的真实契约

### 5.1 timed RX（arm 一个窗口）

【源码已读】权威路径 `uhd_uhd_burst_backend` 已在生产使用，本仓库 `uwb_uhd_burst_backend.cc:663-668`：

```cpp
::uhd::stream_cmd_t stream_cmd(::uhd::stream_cmd_t::STREAM_MODE_NUM_SAMPS_AND_DONE);
stream_cmd.num_samps   = cmd.total_samples;
stream_cmd.stream_now  = false;
stream_cmd.time_spec   = ::uhd::time_spec_t(full, frac);
impl.rx_stream->issue_stream_cmd(stream_cmd);
```

契约要点：

1. **时刻 = 第一样点时刻**（`metadata.hpp:171-172`；【本地文档】`The first sample in 'buffs' will be captured at the requested time`）。
2. **设备侧实现是 4 次 32-bit 寄存器写**（`radio_control_impl.cpp:989-993`）：`NUM_WORDS_HI/LO` → `CMD_TIME_HI/LO` → `CMD`（触发）。**前 3 写必须先于触发写到达。**
3. **窗口收完自动停**（`NUM_SAMPS_AND_DONE`），`abort_rx()` 用 `STREAM_MODE_STOP_CONTINUOUS`（`uwb_uhd_burst_backend.cc:1068-1069`）。
4. **迟到 = 失败**：`ERROR_CODE_LATE_COMMAND`（`metadata.hpp:119`；`radio_control_impl.cpp:1141-1145`），且此时 `metadata.has_time_spec = false`（`rx_streamer_zero_copy.hpp:233`）→ **取不到时间**。本仓库映射 `uwb_uhd_backend_config.h:79` → `BurstStatus::LateCommand`。
5. **overflow 使时间基准断裂**：`usrp_source_impl.cc:654`（GR 侧 `_tag_now = true` 重新打时间戳）。TWR 必须在这里提升 `epoch/generation`。
6. **GR 自己的 RX 提前量 = 100 ms**（`usrp_source_impl.cc:506` `static const double reasonable_delay = 0.1; // order of magnitude over RTT`，`:513` 使用）。这是**流启动**的提前量，不是回复 turnaround；TWR 不能照抄，但它是本机 UHD 对"安全提前量"的量级参考。

### 5.2 timed TX（提交一个 delayed 波形）

【源码已读】契约：

1. `md.has_time_spec = true; md.time_spec = T;` 且 `T` 指向**第一样点**（`metadata.hpp:164-172`）。
2. `start_of_burst` 必须在同一次 `send()`（或至少在**第一次** `send()`，见 `uwb_uhd_burst_backend.cc:765-780` 的 `first_send_call` 保护）带上。
3. `end_of_burst` 用**独立的 0 长度 `send()`**（`usrp_sink_impl.cc:717`；本仓库 `uwb_uhd_burst_backend.cc:855-862`），且**任何数据 send 都不能带 EOB**（`uwb_uhd_burst_backend.cc:761-764` 注释）。
4. **partial send 必须重发余量且不带 SOB/time_spec**（`uwb_uhd_burst_backend.cc:790-794`），因为 `time_spec` 只在第一片有效（`usrp_sink_impl.cc:494` 之后 time_spec 是**相对推进**的）。
5. **设备侧检查的是"数据到达"**：`chdr_tx_data_xport.hpp:260-267` 把 tsf 写进 CHDR 包头；`uhd/host/lib/include/uhdlib/rfnoc/radio_control_impl.hpp:288-289` `ERR_TX_LATE_DATA = 2, // Late data (arrived after indicated time)`；FPGA 侧实现见 §2.8（`radio_tx_core.v:300-345`）。→ **提前量下界 = host 计算 + host→NIC + NIC→FPGA 的包到达时间。**
6. **迟到 = 立即发**：【本地文档】`"late" commands (commands with a command time that is in the past) are executed immediately.` → **deadline 没过时我们必须自己拒绝提交**（AGENTS.md 规则 5）。`usrp_block.h:466-476` 的 `set_command_time` 文档也写 `If the time spec is late, the command will be activated upon arrival.`
7. **排队会吃掉提前量**：【本地文档】`When the command queue is full, UHD will block until the USRP has signaled that there is space for more commands. That can cause timed commands to reach the FPGA after their desired execution time.`
8. **成功返回 ≠ 已发射**：`send()` 返回只表示数据进了传输；`EVENT_CODE_BURST_ACK`（`metadata.hpp:218`）是设备确认，而且【源码已读】`usrp_sink_impl.cc:749-755` 证明 GR 自己的 async 轮询**最坏 ~200 ms 才发现事件**。→ 绝不能用 BURST_ACK 做同步确认（REQ-TIME-03 要求标 `scheduled_calibrated`）。

### 5.3 最小 TX 提前量 —— **设备侧机制已查清，数值仍需 M3 实测**

#### 5.3.1 结论（分两层）

1. **设备侧没有"最小提前量"这个概念。** 设备只在数据包**到达 FPGA 的那一刻**检查一次
   `radio_time > requested_time`，是则报错，否则立刻按 `time_shift` 对齐并开始发射。
   → **提前量的下界完全由 host 计算 + 链路传输决定；本地 GNU Radio / UHD 源码树、手册和
   FPGA RTL 中都不存在可引用的数字常量。**
2. **但设备侧确实有一个硬性时间分辨率**，它决定了 turnaround 预算的最小可表达步长
   （详见 5.3.3）。

#### 5.3.5 turnaround 预算结构（不含数字）

```
turnaround_budget = T_rmarker→frame_end            (PHY 固有)
                 + T_rx_transport (设备→host)
                 + T_detect + T_decode              (PHY 链)
                 + T_fsm + T_frame_patch + T_modulate
                 + T_uhd_internal_queue              (手册: 队列满会阻塞并迟到)
                 + T_tx_link (host→NIC→FPGA 包到达)    ← 提前量下界
                 + margin
```

**可量化的只有两项**（都不是提前量）：

| 量 | 值 | 来源 | 级别 |
|---|---|---|---|
| 命令时间量化步长 | `SPC` 个 radio 样点（见 5.3.3） | 【源码已读】`radio_tx_core.v:199,280-282`；`x4xx_core.v:349`；【本地文档】`page_timedcmds.html` §Command Time Resolution（`tick rate = master clock rate`） | 公式已读；**本机 X410 的 `RADIO_SPC` 与 MCR 需运行时 readback**（候选 MCR：`page_usrp_x4xx.html` 的 245.76/250/491.52/500 MHz） |
| GR 的流启动提前量经验值 | RX 0.1 s / TX 0.15 s / overrun 重启 0.05 s | 【源码已读】`usrp_source_impl.cc:506,513`；`usrp_sink_impl.cc:698`；`radio_control_impl.cpp:35` | 是**流启动**量级，不是 delayed-TX turnaround。对 TWR 只能作为"绝对不能低于百毫秒级"的反向参考 |

**本仓库已有的 2 µs 数字不是 UHD 常量**：`pre_guard_ticks = 1475`（`lib/qa_uwb_uhd_backend.cc:158` 注释 `// 2 µs`，`:483` 断言 `plan.pre_guard_ticks == 1475`）是 **radar 调度器的项目自选 pre-guard**，用于在网格 slot 前预留采样。它是经验值，不是 UHD 契约，也未经 TWR turnaround 验证。

→ **M3 必须实测**（建议方法，供参考，不是结论）：用 `issue_tx` 以 `T = now + Δ` 提交，
`Δ` 从 0 向上扫描，统计 `EVENT_CODE_TIME_ERROR`（late）出现率；用
`EVENT_CODE_BURST_ACK` 的 `time_spec` 分布验证实际发射点。同时必须记录
`get_time_now()` 的单程延迟（我们用它算 `now`，延迟会直接吃掉提前量）。

### 5.4 结论对回复 turnaround 预算的影响

1. **不允许"即时补发"**（`AGENTS.md` 规则 5）：deadline 不满足时必须显式失败，状态入 `REQ-ERR-01` 的 `TX late` 分类，且该 exchange 只能出 provisional/失败结果。本仓库已具备 `BurstStatus::LateCommand`（`uwb_echo_burst_backend.h:57-58`，`:222-223` 字符串）可复用。
2. **TX 命令时间只能来自 RX 观测**：`T_tx = T_rx_observed_marker + T_rmarker_to_tx_marker`，其中 `T_rx_observed_marker` 必须是**设备 tick**（见 §6.5），不得用 `get_time_now()` 或主机 wall clock。
3. **`get_time_now()` 不进 per-packet 路径**：它是寄存器读（`radio_control_impl.cpp:348` `regs().peek64(...)`；更慢的是 MPMD 的 RPC，`mpmd_mb_controller.cpp:160-163`），带单向延迟偏置。**每包调一次会把偏置直接变成测距误差。**
4. **TX async 事件不能同步等**：`usrp_sink_impl.cc:749-755` 的 ~200 ms 最坏发现延迟。【推算】若按 200 ms 等待 TX 结果，则 ≥5 Hz 的请求率就不可能（TWR 目标 PRR 通常 ≫5 Hz）。→ 结果必须在 RX 侧证据上产生，TX 事件只用于**事后归因/降级**。

### 6.2 `rx_time` tag 的三个陷阱（若走 GR 路径）

1. **不是每包都有**：`usrp_source_impl.cc:629` 只在 `_tag_now` 为真时打。要么用 `usrp_source` 自己的时间记账（**推荐**），要么保证每次 `issue_stream_cmd` 后第一个样点有 tag。
2. **offset 是缓冲区第 0 个样点**（`usrp_source_impl.cc:637` `add_item_tag(i, nitems_written(0), TIME_KEY, val, _id)`）。下游 `tagged_stream_block` 只在 `nitems_read(i)` 处查 tag（`tagged_stream_block.cc:95`），`header_payload_demux` 靠 `nitems_read(PORT_INPUTDATA) - d_last_time_offset` 递推（`header_payload_demux_impl.cc:538-539`）。**任何会重排样点的 block（`tagged_stream_block::remove_item_tag` 删 tag、重采样、window crop）都会打断这个链。**
3. **多通道共享同值**：`usrp_source_impl.cc:636-645` 对 `_nchan` 每个通道在同 offset 打同一个 `val`。→ 两路 RX 天然对齐到同一时间基准，符合 AGENTS.md「一台 X410 两个 channel 各作为独立逻辑端点」的时间域要求。

**建议（本文立场）**：TWR 的 radio 适配层**自己**从 `rx_metadata_t::time_spec` 记账（照 `uwb_uhd_burst_backend.cc:991-1002` 的 `have_first_time` / `rx_time_ticks`），**不要**把时间戳的权威交给 GR 的 `rx_time` tag。理由：需要整数 tick、需要在 overflow/late 时作废、需要两个 RX 分别记账，而 GR 的 tag 是 double 秒 + 每通道冗余 + 非每包。

### 6.4 群时延/裁剪的现有公式（供 M2 复用）

```
native_index  = window_start + p.in_offset                       // window_crop_core.h:93,95
work_index    = mapped(rate_ratio, native_index)                  // 65/48 或 65/32
toa_index_work= work_index + first_path_offset_work + filter_delay
device_ticks  = round(rx_time_device_ticks + toa_index_work * (device_rate / work_rate))
```

【推算】`device_rate/work_rate` = 737.28e6/998.4e6 = 48/65（第一阶段 65/48 路径）。`filter_delay` 见上（输出速率下的样点）→ 换算到设备速率需 `× 48/65`。**`first_path_offset_work` 必须是分数样点**（REQ-TIME-05），不能只取整。

### 6.5 **重大发现：绝对时间不能走 double 秒**

本仓库现有代码把 `rx_time` 变成 double 秒绝对时间再用样点偏移推进：

- `uwb_auto_scheduled_extractor_sc16.cc:1009-1016`：`t = d_rx_time_s_ + (double)(lo - (int64_t)d_rx_time_abs_) / d_sample_rate_`
- `uwb_auto_scheduled_extractor_sc16.cc:1081-1087`：同样式子（scheduled 路径）
- `header_payload_demux_impl.cc:538-539`：`d_sampling_time * (nitems_read - d_last_time_offset)`

【推算】double 的 53 位尾数下，`t` 秒的 ULP = `2^(floor(log2 t) - 52)`。在 737.28 MHz 上 1 tick = 1.356e-9 s：

| 绝对时间 t | ULP(秒) | 折合 tick @737.28 MHz | 能否表达 10 ns ToF（≈7400 tick） |
|---|---|---|---|
| 1e5 s (27.8 h) | 1.455e-11 | 0.011 | 可以 |
| 1e6 s (11.6 d) | 1.164e-10 | 0.086 | 可以 |
| 1e7 s (116 d) | 1.863e-9 | 1.37 | 临界 |
| 1e8 s (3.2 y) | 1.490e-8 | 11.0 | 不可以 |
| 1e9 s (31.7 y) | 1.193e-7 | 88.0 | 不可以 |
| 1e10 s | 1.907e-6 | 1406 | 不可以 |

公式：`ULP = 2^(floor(log2 t) - 52)`；`ticks = ULP × 737.28e6`。**任何人都可以用这三个常数复算。**

UHD 自己也警告过：【源码已读】`time_spec.hpp:82-86` `Note: If this time_spec_t represents an absolute time, the precision of the fractional seconds may be lost.`

**结论（M1 硬约束）**：

1. TWR 的时间戳必须是 **`(epoch_id, int64 device_ticks)`**，`clock_domain` / `tick_rate` / `epoch_id` 一起携带（REQ-TIME-01）。本分支的 `gr-uwb/include/gnuradio/uwb/uwb_twr_timestamp.h`（A4 并行产出，未提交）已经这么做了。
2. 换算只用 `time_spec_t::to_ticks(rate)`（`time_spec.cpp:68-76`，整数路径）**或**手工 `full_secs*rate + llround(frac_secs*rate)`，**禁止** `get_real_secs()`（`time_spec.cpp:78-81`）。
3. GR 的 `rx_time` tag（`(uint64, double)`）可以用于**交叉校验**，不能作为 ToF 的输入。
4. `rmarker_to_antenna` 之类的固定延迟也要以 **ticks** 表达，不能以秒表达。

## 10. 一句话结论

**Model B。** TWR 的响应时刻由实际观测到的 RX 帧决定，而 `IRadioBurstBackend` 把 `rx_ticks` 冻结在 `issue_rx()` 之前（`uwb_echo_burst_backend.h:156-159`）并按 `schedule_index` 归并结果（`:174-176`），反应时刻无处表达；正确形态是本仓库已经跑通的 `gr::block`（0 流口）+ 短 handler + 有界队列 + 私有 owner 线程（`uwb_realtime_echo_timer.cc:337-339, 395-396, 863, 1498-1513, 1519-1572`），配合一个把设备 tick 记账放在 radio 适配层、不经过 GR `rx_time` tag、也不经过 double 秒的 `ITwrRadio`；PHY 数据面保持现有 `sync_block` 链不变，**不新增 `tagged_stream_block`**。
