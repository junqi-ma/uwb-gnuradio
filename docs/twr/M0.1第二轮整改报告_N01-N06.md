## 1. 结论

评审判定**「需要修改，暂不认可 M0.1 已完成、四层契约冻结」**，给出 **2 个 P1 + 4 个 P2**
（N01–N06）。**6 条已全部独立复现并关闭**，另修正 2 处自证不足。

本轮最重要的发现不是任何一个具体 bug，而是一个**方法论错误**：

> **N01 与 N02 都是「把错误行为写进了实现或测试约定」。**
> 145 条共享语料只能证明指定输入上的一致性，**不能证明这些共同约定正确**。
> 两侧被同时钉在错误行为上时，差分测试会**报绿**。

具体地：

- **N02**：实现把 `scheduled_calibrated` TX **整类拒绝**，而 REQ-TIME-03 原文明确**允许**
  确定性时序加标定取得合格 TX timestamp；QA 还把「必须被拒」写成断言。
  这会让计划中的 X410 timed TX 无法进入 SS/DS，并**诱导后续把来源错标成
  `HardwareMeasured` 来绕过门控** —— 也就是用更严重的错误去迁就一个错误的门。
- **N01**：语料 case 的 note 描述了**代码里根本不存在的机制**（声称 reader 保留 int64、
  validator 拒绝；实际 reader 掩码成 65535，靠"保留地址"规则**偶然**通过）。
  测试通过的理由与它声称的理由无关。

因此本报告不再出现「契约已冻结」这类表述。**配置合法、试验许可与"正式结果有效"是三件
不同的事**，本报告严格区分。

## 3. 逐条整改

### N01（P1）JSON 越界整数先截断，再作为合法配置接受

**根因**：C++ reader 用 `static_cast<uint16_t>(get_i64(...))` 赋值；Python 用
`v & 0xFFFF` **显式复刻**同一行为。越界值被回绕后写入配置，validator 看到的是回绕值。
**两份不同的文档可以产生同一份运行配置**，而文档真正携带的值已经丢失 ——
这正是 `session_id_to_wire()` 存在要防的静默回落（`session_id_to_wire()` 本身拒绝超限，
但输入在 JSON→uint32 阶段已被截断，救不回来）。

**关键判断**：**C++ 的 `cast` 不是配置规范，它只是缺失的检查。**

**修复**：
- 两端 reader 改为按字段宽度带界的读取器：`get_u8` / `get_u16` / `get_u32` / `get_u64`，
  范围 `[0, max]`；**越界或负数一律 `out_of_range` 拒绝并置 0**，不再掩码。
- 三个 uint64 字段（`cir_capture_max_bytes` 等）也改为拒绝负数，不再回绕成 `2^64−1`。
- Python 侧的掩码辅助函数 `_u8/_u16/_u32/_u64` **整体删除**，并把描述回绕行为的注释块
  改写为「带界检查」——留着包装函数只是给旧行为留复发的入口。

**schema 语义变更（显式记录）**：这是 `twr-config/2` 内部 reader 行为的**收紧**，
不改变任何字段的宽度、单位或 wire 编码，但会改变**哪些文档被接受**：
以前"加一个模数后落回合法值"的文档会被接受，现在被拒绝。

**语料**：`negative_local_address_is_a_negative_index` 更名为
`negative_local_address_is_refused_not_wrapped` 并**改写 note**（旧 note 描述的机制
不存在）。新增 **9 个**用例，总数 145 → **154**：

| 用例 | 修复前会怎样 |
|---|---|
| `channel_uint8_max_plus_one_is_refused` (256) | 掩码成 0 = 另一个信道 |
| `channel_one_modulus_past_a_legal_value_is_refused` (261 = 5+256) | **掩码回落到合法值 5**，validator 会接受一份没人写过的文档 |
| `session_id_one_modulus_past_uint32_is_refused` (2³²+1) | 掩码成 1 = 一个在用会话 |
| `local_address_one_past_uint16_is_refused` (65537) | 掩码成 1 |
| `pan_id_one_past_uint16_is_refused` (65536) | 掩码成 PAN 0 = 通配 |
| `sequence_uint8_max_plus_one_is_refused` (256) | 掩码成 0 = 序列重头开始 |
| `geometry_mac_header_bytes_out_of_uint16_is_refused` (65550) | 掩码成 14，**静默匹配权威几何** |
| `negative_tx_port_is_refused_not_wrapped` (−1) | 回绕成 0xffff |
| `sequence_uint8_max_is_accepted_at_the_boundary` (255) | **边界必须是闭区间**，否则和回绕一样错 |

第 2 行和第 7 行是关键：**「一 past the top」单独不够**，必须覆盖「加一个模数后落回
合法值」——那才是掩码真正危险的地方。

**测试**：Python 的 `test_unsigned_fields_narrow_exactly_like_cxx` 原本**断言回绕行为**，
已重写为 `test_unsigned_fields_refuse_out_of_range_instead_of_wrapping`；
C++ 新增同名的 `json_unsigned_fields_refuse_out_of_range_instead_of_wrapping`，两端对齐。

### N02（P1）测距准入门拒绝全部 scheduled_calibrated TX，违背既定 X410 路线

**需求原文**（`需求_UWB_SS_DS_TWR.md:206`，REQ-TIME-03）：

> UHD timed TX 的目标是第一样点；send 返回成功或 burst ACK 不等价于芯片提供的精细空口
> timestamp。**可通过确定性时序加标定取得合格 TX timestamp**，但必须标注
> `scheduled_calibrated` 来源，关联 async error，**不能冒充 `hardware_measured`**。

需求禁止的是**冒充**，不是**使用**。原实现只接受 `HardwareMeasured`，把需求允许的路径
整类拒掉，并迫使后续要么放弃 X410 timed TX，要么把来源改标成 `HardwareMeasured`
（即**为了通过门控而伪造证据类型**）。

**修复**：按 **marker class** 拆规则，而不是按单一 source 一刀切：

| 情形 | 处置 |
|---|---|
| RECEIVE 时刻 + `ScheduledCalibrated` | **仍拒绝**（预测的接收时刻就是 R6 那类东西） |
| TRANSMIT RMARKER + `ScheduledCalibrated` + **完整发送证据** | **准入**，且入门值保持 `scheduled_calibrated` |
| TRANSMIT RMARKER + `ScheduledCalibrated` + 无证据 | 拒绝，理由 `scheduled_tx_evidence_missing` |

新增 `TxSendEvidence`（REQ-TIME-03 逐项对应）：

```
command_time_recorded        // UHD command time
quantised_instant_recorded   // 量化后第一样点
marker_offset_recorded       // waveform marker offset
calibrated_air_time_recorded // 校准后预计空口时间
send_accepted                // send() 成功 / burst ACK —— 记录但单独不构成证据
outcome                      // Unknown / Completed / Late / Underflow / Cancelled
```

规则：
- 四项计划记录**缺一即拒**，拒绝信息**点名第一项缺失**（`missing=command_time`）。
- `outcome` 必须是 `Completed`；**`send_accepted=true` + `outcome=Unknown` 仍被拒** ——
  这正是「send 返回成功不等价于已发射」的直接编码。async 事件的发现延迟最坏 ~200 ms
  （`M0_调度语义.md` §5.4.4 / O-6），所以 `Unknown` 只能是拒绝。
- `Late` / `Underflow` / `Cancelled` **各有独立终态**（`ExchangeStatus::TxLate` /
  `TxUnderflow` / `Cancelled`），**不**归到 `InvalidTimeDomain`：
  时间域是好的，问题出在 burst 上。soak 报告要能不解析文案就区分它们（REQ-ERR-01）。
- **准入的值仍标 `scheduled_calibrated`，绝不改标 `hardware_measured`**（有专门断言）。

**测试**：错误断言 `tof_scheduled_calibrated_source_is_refused` 重写为
`tof_scheduled_calibrated_source_is_permitted_only_with_send_evidence`，覆盖 6 种情形
（预测 RX 拒绝 / 无证据拒绝 / 仅 send_accepted 拒绝 / 计划不全拒绝 / 三种失败模式各自
终态 / 完整证据准入且来源不变）。

**M1 义务**（已记入 `M0_调度语义.md` checklist **C-32**）：终态收敛**之前**可以保存
planned 时间，但**不得提前发布有效距离**。

### N03（P2）lossless 判定与真正写出的 ns 数值不一致

**根因**：`duration_is_lossless_ns` 用**精确整除**判定理论 ns 是否为整数，
但真正写出的值走 `double` 除法/乘法后**截断**。浮点落到整数下方时丢 1 ns，
而 predicate 仍为真。

修复前实测（经公开 `timestamp_interval()`）：

| tick rate | ticks | 精确 ns | 返回 ns | lossless |
|---|---:|---:|---:|---|
| 737.28 MHz | 361728 | 490625 | 490624 | true |
| 491.52 MHz | 241152 | 490625 | 490624 | true |
| 998.4 MHz | 8112 | 8125 | 8124 | true |
| 63.8976 GHz | 519168 | 8125 | 8124 | true |
| 1 GHz | 15 | 15 | **14** | true |

**修复**：投影值与 lossless 标志由**同一套**受溢出保护的 `unsigned __int128` 有理数
**商/余数**产生 —— 一次除法同时产出 `q` 与 `rem`，`rem == 0` 即 lossless，
且写出的 ns **就是** `q`。**不用 epsilon 补偿 double 再截断。**
`relative_interval_to_duration()` 也改走同一实现。

**测试**：精确断言**返回的 ns 值本身**（5 行全测 + 1 GHz/15 ticks 最小例），
并保留截断路径（`15+1/2`、DW UUS 1 tick → 0，`lossless=false`）。
**不再断言两个同源 predicate 相等** —— 那正是这类缺陷得以通过的原因。

**边界**：溢出情形仍是 `DurationOutOfRange`（实测 1 Hz / 9.3e9 ticks → `status=10`，
`ns=0`，`lossless=0`），不会出现"标志为真但值不可信"。

**范围**：本节破坏的是**时间投影/序列化契约**，不是"已实现 ToF 的距离误差"。
`RelativeTickInterval`（其 tick 值本就正确）保留不变。

### N04（P2）interval 的最大范围在加入 fraction 后没有重验

**根因**：整数差先过 raw gate（`d_ticks > P/2`），**分数在之后才合并**进整数部分，
合并后的完整值再也没检查。于是最终规范化值**超过 API 自己规定的半周期上界**仍返回 `Ok`，
准入门进一步放行。

修复前实测（12-bit 域，P=4096，P/2=2048，later = 2048+3/4，earlier = 0+1/4）：
`status=Ok, ticks=2048, frac=1/2` → 合并值 **2048.50 > 2048**；
`admit_ranging_interval` 返回 **`admitted=1`**。

**修复**：tick+fraction 规范化成**一个精确有理数**后，按精确有理数比较上界，
**严格大于** `P/2` 才拒绝 —— 保留「已知 later/earlier 时恰好半周期允许」这条
已说明的策略（评审明确不反对该策略），只堵住"超过上界"。

**三层分别覆盖**（排序函数的穷举通过**不能**替代 interval 检验，这正是旧脚本的盲区）：

1. 排序（`timestamp_precedes` / `timestamp_compare`）—— 原本已足够严格，**补测试证明**而非假设；
2. `timestamp_interval()`；
3. `admit_ranging_interval()`。

用例：`P/2−fraction`、恰好 `P/2`、`P/2+fraction`、跨回绕（界内/界外）、交换端点双向。

### N06（P2）公开 thaw() 仍能解除运行快照的 capability 冻结

**根因**：`snapshot.caps` 返回**内部表**，而 `thaw()` 是**公开**方法且**原地**解冻：

```python
s.caps.thaw()                     # 公开 API，原地解除冻结
s.caps.channels.append(9)         # 现在被接受
# s.caps.read_only == False
```

无需访问任何私有成员。改 `channels` 本身未必足以让新 PHY 行通过全部联合校验，
但它已经违反快照 capability 不可变保证；解冻后同样能改整个矩阵与版本。

**修复**（评审给出的方案 a）：
- 原地解冻降为私有 **`_thaw_in_place()`**，唯一合法调用者是 `mutable_copy()`，
  且只作用于它刚深拷贝出来的、无人可达的新对象。
- 公开面新增 **`mutable_copy()`**：返回**新对象**；`copy()` 是它的别名，
  供 `CapabilitiesBuilder` 使用。
- **公开面上不再存在任何原地解冻**；对一个在用的表，公开方法只能收紧（`freeze()`）
  或返回新对象。

**测试** `test_capability_freeze_cannot_be_undone_through_public_api`：
遍历 `Capabilities` 的**每个无参公开方法**并调用，断言调用后 `read_only` 仍为真、
容器未变；再断言 `mutable_copy()` 出来的副本被改动后，快照与进程级表都不受影响。
（评审明确排除"私有反射篡改"；本测试只走公开 API。）

## 4. 额外修正：自证不足的两处

评审 §3 指出、并已核实属实的两个问题：

### 4.1 独立验证脚本自身的弱断言

`tools/twr/verify_m0_1_findings.py` 对 R5 分数排序**只断言结果 `!= 0`**，
因此 `Equal=1`、`Later=3` 都能通过 —— **正是该脚本存在的意义所要防的

（R1–R7 + N01–N06），新增的 N01–N06 检查全部**从源码/头文件重新推导**，
不读取被测套件的结论。它现在同时覆盖 R2/R8 之外的新反例。

### 4.2 语料 note 描述不存在的行为

见 N01。**这是本轮最有代表性的问题**：测试通过的原因与它声称的原因无关。

**环境注意**：不要在交互 shell 直接跑测试二进制。环境里的

静默产生错误结论。必须 `env -u LD_LIBRARY_PATH`。

## 8. 本轮最该记住的

1. **一致性 ≠ 正确性。** 差分测试只能证明"两侧在指定输入上一致"。
   当两侧被同时钉在错误行为上时，它**报绿**。N01 与 N02 都是这种。
2. **需求原文要逐字读。** REQ-TIME-03 的"不能冒充 `hardware_measured`"被我读成了
   "不能用 `scheduled_calibrated`"。一个副词的方向决定了整条路径的生死。
3. **C++ 的 cast 不是规范。** `static_cast<uint16_t>(i64)` 是缺失检查，不是契约；
   Python **不该去复刻**它。
4. **不要用"测试通过"给错误行为背书。** N02 的 QA 断言、N01 的语料 note，
   都把错误行为固化了 —— 下次改代码的人会以为那是既定契约。
5. **C++ 权威与 Python 的长期双轨是这类问题的温床**（§5.1）。共享语料只是权宜之计。
