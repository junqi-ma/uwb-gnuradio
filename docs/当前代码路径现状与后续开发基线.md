# 当前代码路径现状与后续开发基线

> 更新日期：2026-08-12  
> 范围：当前工作区中的 X410 输入、65/48 重采样、检测/周期截窗、PDU 解调与写盘路径。

## 1. 先统一两个维度

当前代码的多条路径由两个互相独立的选择组成：

1. **数据入口**：采样率是 737.28 MHz 还是 998.4 MHz；host 数据格式是 SC16 还是 CF32（代码和 GNU Radio 使用 `CF32`，不是 `FC32`）。
2. **取包策略**：未知时刻使用能量门检测；已知雷达 `t0/T` 使用周期截窗。

所有 QM35 解调最终都进入 **998.4 MHz 的 PDU**。`UwbRealtimeDemodulator` 是消息/PDU block，不直接接连续流。

## 2. 数据入口路径

| 路径 | 当前连接 | 现状 | 定位 |
|---|---|---|---|
| A. RFNoC 65/48 → host SC16@998.4M | Radio@737.28M → RFNoC Upsampler → SC16 Streamer → `UwbDetectorSc16` | GRC、SC16 detector、Writer 已有；`UwbScheduledExtractorSc16` 也已实现。RFNoC FPGA 实现和 SC16@998.4M PDU→FC32 demod bridge 仍不在本仓库闭环 | 低 host 带宽的未知时刻检测候选 |
| B. RFNoC 65/48 → host CF32@998.4M | Radio@737.28M → RFNoC Upsampler → CF32 Streamer → CF32 block | scheduled GRC 和入口脚本已有；依赖外部 FPGA image；overflow 后 `rx_time/t0` 重映射未完成 | RFNoC 可用时的周期雷达候选 |
| C. host 连续流 65/48 | CF32@737.28M → `UwbRationalResamplerCcf65_48` → CF32@998.4M | 数值正确，但本机最高约 0.35× 实时；两个 GRC 仅保留作验证/回退 | **不再作为生产主线** |
| D. 原生率截窗 + PDU 65/48 | SC16/CF32@737.28M → `UwbScheduledExtractorSc16` / `UwbScheduledExtractor` → `UwbPduRationalResamplerCcf65_48` → FC32 PDU@998.4M | QA、golden、真实 QM35 与密集 DW1000 离线解调已闭环；SC16 仅在窗口内转 FC32，避免连续 host FIR 与全流格式扩展 | **当前 host-only 推荐路径** |

补充边界：

- UHD 的 `otw_format` 通常仍是 SC16；表中的 SC16/CF32 主要指 RxStreamer 交给 host block 的 CPU 数据格式。
- `uwb_rfnoc_upsampler.block.yml` 只是 UHD generic RFNoC block 包装，不包含 FPGA Upsampler RTL/image。
- `UwbScheduledExtractorSc16` 与 PDU resampler 已形成“SC16 周期截窗 → 窗内
  SC16→FC32 → 65/48 → FC32 demod PDU”的完整 737.28 MS/s 路径；它不是全流
  SC16→FC32 转换。

## 3. 取包与解调策略

### 3.1 能量检测后解调

```text
连续流 → UwbDetector / UwbDetectorSc16
       → 能量门形成 candidate Region
       → coarse-to-fine preamble 验证
       → packet PDU
       → UwbRealtimeDemodulator 或 UwbPacketWriter
```

- 适用：包到达时刻未知、需要发现任意 UWB 包。
- CF32 和 SC16 detector 均已实现并有 QA。
- SC16 路径全速部分使用整数能量门，候选区再转 CF32 做相关。
- 密集通信环境中，每个通信包都可能形成 Region，工作量随候选包率增加；不适合作为已知周期雷达的首选路径。

### 3.2 按雷达发送间隔截窗后解调

```text
连续流 + 已知 t0/T → UwbScheduledExtractor
                     → 每个雷达 slot 固定窗口 PDU
                     → 必要时 PDU 65/48
                     → UwbRealtimeDemodulator / Writer
```

- 适用：QM35 雷达 `t0/T` 已知或可先验获得。
- 默认 `EverySlot`，不因通信碰撞或验证失败丢窗；窗口数只随雷达 slot 率变化。
- 737.28 MHz 输入时，应先截窗、再做 PDU 65/48；不要恢复连续 host 重采样。
- schedule lock 已实现但默认关闭；0.5 s 数据上与宽搜索 FCS 打平，长时间与失锁重捕获仍待验证。

## 5. 后续开发基线

建议只保留两条主线，其他路径作为对照：

1. **周期雷达主线**：737.28M 原生率截窗 → PDU 65/48 → 998.4M 解调。先完成失败包 MATLAB 对照、schedule lock 长时间验证和 200 slot/s Writer 验收。
2. **未知包检测主线**：RFNoC 998.4M SC16 → `UwbDetectorSc16` → 解调/写盘。先确认 FPGA Upsampler、SC16 PDU 到 demod 和持续吞吐。

RFNoC CF32 scheduled 路径保留为硬件对照；连续 host 65/48 路径只用于数值回归，不再投入实时性能开发。

开发时必须记录四个坐标域：输入采样率、PDU 采样率、`t0` 所属采样域、重采样群时延映射；禁止在 737.28M 与 998.4M 之间直接复用 sample index。

## 6. 2026-08-12 配置与吞吐基线

`UwbRealtimeDemodulator` 当前支持 BPRF code 9–12，GRC 为受限选项；默认仍是
QM35 的 code 9 / 64 SYNC / 4z2。DW1000 实测需要根据发射配置选择 code、SYNC 数和
SFD，不能沿用 QM35 默认。已验证的两组实测配置为：

| 场景 | 解调配置 | 结果 |
|---|---|---|
| `dw1000_new_processed_1.dat` @998.4M | code 11、128 SYNC、Decawave DW-8 | GNU Radio 与 MATLAB 均 12 B、FCS pass |
| `dw1000_interference_…737p28…dat` | code 10、256 SYNC、Decawave DW-8，SC16 PDU 65/48 | 0.5 s 内 974/974 demod complete，已发布 973 条均 FCS pass |

第二组为约 1948 pkt/s 的密集周期流。本机 host-only 离线活跃吞吐约 83 pkt/s（单、双
demod worker 均接近此值），限制在连续 SC16 文件供给、PDU 重采样与大 PMT 传递，不在
demod worker。其单包 demod 均值 5.386 ms，主要是 timing 47.5% 和 SFD 33.9%。因此它
是正确性和热点基线，不是该包率下的实时可行性证明。
