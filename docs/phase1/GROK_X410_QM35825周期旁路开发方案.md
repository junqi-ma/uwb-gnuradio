# Grok 开发方案：X410 对 QM35825 RX 的周期旁路截取

更新时间：2026-08-08

## 1. 背景与目标

使用 USRP X410 旁路监听 QM35825 的 RX 输入，连续接收约 998.4 MS/s CF32 IQ。QM35825 雷达包可以降低到 100～200 packet/s，但环境中的 UWB 通信包可能达到 2000 packet/s。

现有能量门会把每个高能量通信包都变成候选 Region。按当前约 264k samples/Region 估算：

```text
2000 packet/s × 264k samples ≈ 528 MS/s Region IQ
```

单 worker 当前约处理 200.8 MS/s Region IQ、约 760 region/s，因此持续将所有通信包送入完整相关会积压或丢 Region。

本项目的核心目标不是实时解调所有通信包，而是：

1. 按 QM35825 雷达周期，从 X410 连续流中稳定截取每个雷达时隙的原始混合 IQ；
2. 即使雷达包被通信干扰、相关失败，也保留该时隙 IQ 供离线 MATLAB/SIC；
3. 让实时计算量与雷达包率 100～200/s 成正比，而不是与全部通信包率 2000/s 成正比；
4. 保持输入流吞吐 ≥1 GS/s，正常运行 0 window drop；
5. 与 `UWB_demodulation/run_decode_uwb_radar.m` 的固定周期候选逐样本对照。

---

## 2. 核心设计决策

### 2.1 锁定后不再使用全局能量门生成 Region

已知首个雷达前导起点 `t0` 和固定周期 `T` 后，直接预测：

```text
predicted_start(k) = round((t0 + k × T) × fs)
```

每个预测时隙只截取一个固定窗口：

```text
[predicted_start - pre_guard,
 predicted_start + capture + post_guard)
```

窗口之外只消费输入，不创建 Region、不运行相关、不维护全速率 pre-trigger ring。

不要通过累加取整后的 `period_samples` 生成下一时隙，否则长期运行会累积量化误差。每个时隙应从 `t0 + k*T` 独立计算，与 MATLAB `predictFixedIntervalCandidates` 保持一致。

### 2.2 默认每个时隙都输出，而不是“检测成功才输出”

X410 旁路的用途包括分析雷达与通信碰撞。通信干扰可能让雷达前导相关降低甚至完全失败。如果只输出已验证雷达包，最有研究价值的严重碰撞样本反而会被丢掉。

默认策略：

```text
emit_policy = every_slot
```

每个预测时隙输出固定长度 IQ，并在 metadata 标记：

- 是否找到雷达前导；
- 雷达相关 metric；
- 通信相关 metric（若启用）；
- 是否疑似 collision；
- 预测起点与检测起点误差；
- 窗口是否完整。

另提供 `verified_only` 模式用于生产筛选，但不能作为干扰研究的默认值。

### 2.3 计算量应由雷达时隙数决定

假设每个窗口约 202k samples：

```text
100 radar/s → 20.2 MS/s window IQ，约 162 MB/s CF32
200 radar/s → 40.4 MS/s window IQ，约 323 MB/s CF32
```

这远低于当前约 3.5 GS/s SEARCH-only 输入能力，也低于 worker 的目标负载。2000个通信包/s中，只有与预测雷达窗口重叠的部分进入截取数据。

## 3. 建议新增 GNU Radio block

建议新增独立块，不在第一阶段大改现有 `UwbDetector`：

```text
gr::uwb::UwbScheduledExtractor
GRC: uwb_scheduled_extractor
```

### 3.1 Block 类型

采用：

```text
gr::sync_block
1 路 gr_complex stream 输入
0 路 stream 输出
PDU 输出端口：packet
状态输出端口：status
控制输入端口：schedule
```

理由：该块对输入流进行等速消费，不产生 stream 输出，只在固定时隙发布 PDU，语义与现有零输出 `UwbDetector` 一致。

实现前必须按 `../../AGENTS.md`：

1. 搜索本地 GNU Radio 源码中的 zero-output sink、message/PDU 和 `rx_time` tag 处理范例；
2. 明确 `sync_block::work()` 返回值就是本次消费数；
3. QA 先覆盖 scheduler/EOS，再声明完成；
4. `work()` 中禁止动态分配。

### 3.2 建议文件

```text
gr-uwb/include/gnuradio/uwb/uwb_scheduled_extractor.h
gr-uwb/include/gnuradio/uwb/uwb_scheduled_extractor_core.h
gr-uwb/lib/uwb_scheduled_extractor.cc
gr-uwb/lib/qa_uwb_scheduled_extractor.cc
gr-uwb/grc/uwb_scheduled_extractor.block.yml
gr-uwb/python/uwb/bindings/python_bindings.cc
```

算法 core 必须保持 GNU Radio 独立，方便用纯 C++ 做逐 chunk、跨边界和吞吐测试。

## 4. Block 参数与控制接口

### 4.1 构造参数

建议第一版参数：

| 参数 | 类型 | 建议默认 | 说明 |
|---|---|---:|---|
| `sample_rate` | double | 998.4e6 | X410 输入采样率 |
| `packet_interval_s` | double | 必填 | 0.01=100/s，0.005=200/s |
| `first_packet_sample` | uint64 | 可选 | 文件/流中的首包前导起点 |
| `first_packet_time_s` | double | 可选 | UHD 硬件时间域中的首包起点 |
| `pre_guard_samples` | size_t | round(10 us × fs) | 预测起点前保护 |
| `capture_samples` | size_t | round(190～200 us × fs) | 固定截取长度 |
| `post_guard_samples` | size_t | 4096 | 尾部保护 |
| `pool_size` | size_t | 8 | 预分配窗口槽位 |
| `emit_policy` | enum | `every_slot` | `every_slot` / `verified_only` |
| `partial_eos_policy` | enum | `drop` | `drop` / `emit_partial` |
| `verification_enabled` | bool | true | 后台 code 9 检查 |
| `radar_template` | vector/file | code 9 | QM35825 SYNC 模板 |
| `comm_template` | vector/file | optional code 10 | 通信碰撞辅助分类 |

不要把 `sync_symbols=64` 写死。QM35825 雷达脚本当前使用：

```text
code_index = 9
preamble_repetitions = 16
sfd_mode = 4z2
```

这些应由配置传入，或至少在 metadata 中明确记录。

### 4.2 `schedule` 消息端口

支持运行期 PMT dict：

```text
{
  command: "set" | "reset" | "pause" | "resume",
  first_packet_sample: uint64,          # sample-domain 方案
  first_packet_time_s: double,          # UHD time-domain 方案
  packet_interval_s: double,
  pre_guard_samples: uint64,
  capture_samples: uint64
}
```

消息处理线程不得直接修改 work 正在使用的复杂状态。建议：

- message handler 写入 pending config；
- work 在 chunk 边界用短 mutex 或 generation counter 原子切换配置；
- 切换 schedule 时清空未完成窗口，并输出 status 事件。

## 5. 状态机设计

### 5.1 第一阶段状态

```text
UNLOCKED
   │ schedule seed
   ▼
WAIT_WINDOW
   │ 到达 window_start
   ▼
COPY_WINDOW
   │ 固定长度完成
   ▼
ENQUEUE
   │
   └──────────────► WAIT_WINDOW
```

`UNLOCKED` 状态只消费输入，不创建窗口。第一阶段要求由用户或上层提供 `t0` 和 `T`；自动捕获后续再加。

### 5.2 work 热路径

每次 `work(in, n, abs_start)`：

1. 计算当前 chunk `[abs_start, abs_start+n)` 与下一预测窗口的交集；
2. 若完全在窗口外，一次性消费到下一窗口边界，不做逐样本循环；
3. 若与窗口相交，用至多一次/两次 bulk `memcpy` 写入预分配槽；
4. 一个 chunk 可能覆盖零个、一个或多个时隙，必须循环处理所有交集；
5. 窗口完成后仅将 handle 放入有界队列；
6. PMT 构造、相关验证和 `message_port_pub` 在后台 worker 完成。

输入 buffer 继续采用报告验证过的：

```text
min_output_buffer = 512k～1M items
max_noutput_items = 512k～1M
```

### 5.3 绝对坐标

同时维护：

- GNU Radio absolute sample index；
- 可选 UHD `rx_time`；
- schedule index `k`；
- predicted radar start。

预测必须使用：

```cpp
predicted = llround(first_sample_exact + k * period_samples_exact);
```

`period_samples_exact` 保持 double/long double，不要先取整后累计。

## 6. X410 `rx_time` 与流中断处理

真实 UHD 流不能只依赖“从程序启动起累计了多少样本”，因为 overflow、restart 或 rate change 会造成 sample index 与硬件时间失配。

### 6.1 时间映射

当收到 `rx_time` tag：

```text
tag_sample_index ↔ hardware_time_s
```

若 schedule 使用硬件时间：

```text
predicted_sample = tag_sample_index
                 + round((predicted_hw_time - tag_hw_time) × fs)
```

### 6.2 不连续检测

以下情况必须退出锁定或重新映射：

- 新 `rx_time` 与按样本数外推的时间误差超过容差；
- UHD overflow/drop tag；
- sample rate 改变；
- source restart。

输出 `status`：

```text
schedule_lost
rx_discontinuity
window_dropped
partial_window
schedule_updated
```

不得在样本丢失后继续按旧绝对索引静默截窗。

## 7. 后台验证与碰撞分类

### 7.1 默认行为

worker 对每个已截取窗口：

1. 在 `predicted_start ± pre_guard` 范围内搜索 code 9；
2. 做 coarse-to-fine 精定位；
3. 可选计算 code 10 通信模板分数；
4. 生成 metadata；
5. 按 `emit_policy` 发布 PDU。

不要扫描整个 200k capture。相关 horizon 只需覆盖：

```text
pre_guard + 实际 QM35825 preamble + SFD margin
```

### 7.2 分类建议

```text
radar_verified = score9 >= radar_threshold
comm_present   = score10 >= comm_threshold
collision      = radar_verified && comm_present
```

如果通信也使用 code 9，code template 无法区分，需要增加 SFD/PHR/MAC 判别。但这不影响 `every_slot` 原始 IQ 截取。

### 7.3 严重干扰时仍输出

以下场景也必须输出窗口：

- `radar_verified=false`；
- 只有 `comm_present=true`；
- 两个 metric 都低；
- suspected collision。

metadata 标记原因，离线 MATLAB 决定是否执行 SIC。不要让在线相关结果决定是否保留研究数据。

## 9. 时钟漂移跟踪

### 9.1 第一版

固定 `t0`、`T`，guard 取约 ±10 us，与现有 MATLAB 雷达脚本一致。先证明长流不会漏窗。

### 9.2 第二版 alpha-beta tracker

仅用高置信度 code 9 检测更新：

```text
error_k = detected_start_k - predicted_start_k
phase   += alpha × error_k
period  += beta  × error_k
```

要求：

- 只在 `|error_k| < guard` 且 metric 足够高时更新；
- 单次 phase/period 更新限幅；
- suspected collision 不更新，或使用更严格阈值；
- 连续 miss 时逐渐扩大 guard；
- miss 超过 N 个时隙后输出 `schedule_lost`，但 `every_slot` 可继续按旧计划截取一段时间。

另一可选实现是对最近 N 个可靠 start 做稳健线性拟合：

```text
start_k ≈ intercept + k × period
```

与 MATLAB 的独立 `round(t0+kT)` 保持一致。

## 10. 自动捕获与重捕获

不要在第一阶段同时实现，以免将周期截窗和高通信包率分类混在一起。

### Phase 1：外部 seed

- 用户提供 `first_packet_sample/time` 和 `packet_interval_s`；
- 验证 schedule extractor、PDU 和吞吐。

### Phase 2：短时 acquisition

未锁定时：

1. 能量门仅生成短 CLASSIFY 缓冲，不生成完整 Region；
2. 用 code 9 与 code 10 的短前导相关选择 QM35825；
3. 找到一个高置信雷达包后得到 `t0`；
4. 连续第二/第三个候选符合周期后进入 LOCKED；
5. 通信包进入 `REJECTED_HOLDOFF`，直到能量下降，避免同一包重复触发。

目标 classifier ≤100 us/event；2000通信包/s时低于约20%单核。获取锁定后立刻退出全局能量模式。

### Phase 3：重捕获

- schedule lost 后先在预测点扩大 guard；
- 若仍失败，再进入全局短分类；
- 不要因为单个被干扰雷达时隙立即丢锁。

## 11. 内存、队列与线程

### 11.1 固定池

构造期预分配 `pool_size` 个窗口：

```text
window_capacity = pre_guard + capture + post_guard
```

`work()` 中只允许：

- bulk copy；
- handle 入队；
- 固定计数更新。

禁止：

- vector 扩容；
- PMT 构造；
- 文件 I/O；
- 模板重建；
- 长时间等待 worker。

### 11.2 池容量估算

200 packet/s 的周期约5 ms。若 worker 每窗口小于1.5 ms，理论上1个槽即可跟上；默认8槽提供调度抖动余量。

必须统计：

```text
scheduled_windows
completed_windows
emitted_windows
partial_windows
dropped_windows
queue_high_watermark
verification_failures
collisions
```

增加池大小不能代替处理能力验证。持续增长的 queue/high-watermark 表示系统不稳定。

### 11.3 EOS

复用现有 detector 已验证的后台排空语义：有限文件结束前确保最后完整窗口的 PDU 在 message sink 停止前发布。

不完整尾窗按 `partial_eos_policy`：

- 默认 drop 并计数；
- 调试可 emit，metadata `partial=true`。

## 12. QA 测试矩阵

QA 必须先于完成声明。

### 12.1 Core 单元测试

1. 首窗恰好位于 chunk 内部；
2. window start/end 分别跨 chunk；
3. 一个大 chunk 覆盖多个时隙；
4. `t0+kT` 非整数 samples，验证无累计取整漂移；
5. 100/s、200/s 长序列窗口坐标；
6. schedule update/reset；
7. EOS 完整窗/不完整窗；
8. pool 满、队列满计数；
9. 输入中没有能量也按 slot 输出；
10. 窗口 IQ 与原始输入逐样本完全一致。

### 12.2 GNU Radio flowgraph QA

1. `vector_source_c → scheduled_extractor → PDU collector`；
2. PDU 顺序与 schedule index 单调；
3. 最后 PDU 能在有限流结束前送达；
4. 512k/1M work chunk 下跨边界正确；
5. schedule message 运行期更新；
6. rx_time tag 映射和 discontinuity reset。

### 12.3 雷达/通信混合 QA

建立双源 synthetic generator：

- 雷达 code 9：100/200 packet/s；
- 通信 code 10：500/1000/2000 packet/s；
- 两个波形按绝对采样坐标叠加，碰撞时执行复数 IQ 相加，不能简单串联；
- SIR：-20、-10、0、+10、+20 dB；
- 无重叠、部分重叠、前导完全重叠；
- 雷达 jitter、clock drift、随机漏发。

必须验证：

- 输出窗口数只由雷达 schedule 决定；
- 通信包率从0升到2000/s不会增加 Region/window 数；
- 每个预测 slot 均有PDU或明确 drop/status；
- collision 窗口仍被保存；
- `every_slot` 不因 radar verification 失败而丢失窗口。

## 16. 第一阶段明确不做

- 不实时完整解调2000个通信包/s；
- 不在在线路径做完整SIC；
- 不把通信包也输出为PDU；
- 不依赖提高能量阈值区分雷达；
- 不删除严重干扰但未验证成功的雷达时隙；
- 不先改SC16格式；
- 不替换现有稳定 `UwbDetector`。

第一阶段只完成一件事：**按QM35825雷达周期，从X410连续流中以固定计算预算可靠保存每个雷达时隙的混合IQ。**

## 17. 最终完成标准

- 100/200 radar/s × 0～2000 comm/s 时，输入吞吐稳定 ≥1 GS/s；
- 窗口数量只跟radar schedule有关；
- 正常负载 `dropped_windows=0`；
- PDU IQ与源输入逐样本一致；
