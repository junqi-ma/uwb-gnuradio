## 1. 结论摘要

1. **C++ 双 TX 路径在真机跑通**：单 TX 基线 100/100、双 TX 固定/扫描/随机时延各 100–750 拍，
   `echo_fail=0`、`echo_late=0`、CIR 无 drop，`peak_tap=19`（与既有单 TX 一致）。
2. **M5 jammer-only retune 真机可用**：dwell 边界精确、`jam_retune` 全成功、失败有明确状态。
3. **CFO 零点科学在 C++ 双 TX 上完整复现**（§6）：Δf=0 / 982.68 kHz 为梳齿峰，
   **零点在峰旁 8.62 kHz**（+0.5 dB ≈ 本底），第二零点 991.30 kHz——与既有 Python 报告逐点吻合。
4. **发现并修复 4 个真 bug + 1 个接口缺口**（§5），其中 base=0 缺口会让
   "零点是假象（jammer 出带外）"，已被新增的严格回读校验当场抓住。
5. **kernel-UDP 存在真实 TX underflow**（单 TX 也有）：§5.6 修复后第一次被正确计数；
   性能门（200/300 Hz）必须 DPDK，而 **管理口 192.168.20.133 不通** 导致本轮无法启用 DPDK。

## 4. TX async 计数（§5.6）

修复前 `tx_async_counts()` 把"无时间戳/无法归属"的事件一律算 `unmatched`，**真实 underflow 被隐藏**；
修复后所有 drain 到的事件先按 event code 计数，再额外统计归属失败。

TX-only 隔离（`/home/oi/x410_dual_tx_dpdk/diag_async.py`，L=188999，rx=211192，50 Hz，8 拍）：

| 配置 | bursts | underflow | unmatched | ack |
|---|---|---|---|---|
| 单 TX | 8/8 | **51** | 58 | 7 |
| 双 TX | 8/8 | **227** | 241 | 14 |

结论：**单 TX 在 kernel-UDP 下同样 underflow**（UHD `UHD_LOG_FASTPATH("U")` 为设备上报的 underflow），
与既有 DPDK 文档"kernel-UDP 聚合天花板 ~473 MSps"一致。双 TX 只放大。**性能门必须 DPDK**。

app 侧 100 拍：`underflow≈3.4k–5.4k`、`seq_error=0`、`time_error=0`、`ack=196–198`。
（注意：控制台 `U` 字符数 ≠ underflow 计数，§5.6 的意义正在于此。）

## 5. 发现并修复的缺陷

1. **§5.6 async 归属错误**（`uwb_uhd_burst_backend.cc`）：`take_events_for` 只按 ticks 匹配，
   凡不匹配（含无时间戳）一律 `unmatched` 并丢弃，`underflow/seq/time` 永远为 0。
   修为：先按 event code 对**每个** drain 事件计数，再单独统计 `unmatched`。
2. **app PRI 分母错误**（`x410_cg400_hrp_echo_cir_jam.py`）：`_make_dual_tx_block` 传
   `pri_den=rate`，而调度核 PRI=`pri_num/pri_den` 单位是 tick → PRI≈0.02 tick，
   `pre_guard_ticks` 必被拒（`ValueError: pre_guard_ticks must be smaller than the PRI`）。
   修为 `pri_den=1`（与 `base.CppPduEcho` 一致）。
3. **扫描 base 缺失（接口缺口，最严重）**：app 的多 TX schedule PDU **从不发 `freq_hz`**，
   worker 的 `d_mtx_base_hz_` 回落到 `set_freq`（app 从不调用）→ base=0 →
   `tune_tx_channel` 收到的是**偏移量当绝对频率**：实测 `requested=491339 → actual=1e+06`，
   jammer 被调到 ~1 MHz **出带外**，于是 floor"回本底"被误读为 CFO 零点。
   修：app 发 `freq_hz`（`build_cpp_schedule_pdu(base_freq_hz=self.freq)`）+
   worker 对"非零偏移但 base 未知"**硬拒绝**（`jam_scan_base_unknown`，防出带外发射）+
   新增 C++ QA `test_echo_timer_multitx_scan_needs_absolute_base`。
4. **retune 无回读校验**（`uwb_uhd_burst_backend.cc`）：`tune_tx_channel` 曾无条件返回成功。
   新增 100 Hz 严格回读（`kUhdTxFreqReadbackTolHz`）——**正是它把缺陷 3 当场抓出来**
   （`requested=491339 actual=1e+06`）。满足 §5.5"不能把旧频率标成新频率"。
5. **§5.1 逐 TX 通道频率回读缺失**：`prepare()` 只在多通道 streamer 建立后重下发并
   **逐通道严格回读**（本轮未改变 RF 行为，但补齐了规划要求的契约）。

> 早期"启动设定 vs retune 到同频结果不同（+8 dB vs 全零点）"的疑点已解释清楚：
> 那是缺陷 3 造成的假象。修复后两条路径逐点一致（§6.3）。

## 6. CFO 零点科学（双 TX，jam code10，preamble，Δf 扫描，dwell 50）

判据：`floor = mean(|CIR|[40:116])`，基线 = jam-off 单 TX floor `5.361e-4`。

### 6.1 jam-scale 决定零点能否回本底（4 点扫描）

| jam-scale | Δf=0 | 245.67 kHz | 491.34 kHz | 982.68 kHz |
|---|---|---|---|---|
| 0.30 | +15.1 dB | +6.9 | +7.6 | +14.4 |
| 0.15 | +13.9 dB | +4.5 | +5.5 | +13.2 |
| **0.05** | **+10.4 dB** | **+0.6** | **+0.8** | **+9.5** |

jammer 过强（0.8/0.3）→ RX 非线性/IMD 产生**非周期**残余 → 零点抬到 +8 dB；
降到 0.05 → 峰间整段回到本底。**与既有报告"过驱破坏零点"的告警一致。**

### 6.2 Dirichlet 细扫（jam-scale 0.05，15 点，750/750 ok）

| Δf | floor vs 本底 | peak/floor | | Δf | floor vs 本底 | peak/floor |
|---|---|---|---|---|---|---|
| 0 | **+9.8 dB** | 50.9 | | 982.68 kHz | **+9.5 dB** | 54.2 |
| 2 kHz | +9.6 | 53.9 | | 986.68 kHz | +7.9 | 79.0 |
| 4 kHz | +8.6 | 66.1 | | 988.68 kHz | +5.4 | 138.5 |
| 6 kHz | +6.2 | 115.3 | | **991.30 kHz** | **+0.6** | 425.5 |
| **8.62 kHz** | **+0.5** | 432.5 | | 993.68 kHz | +3.1 | 235.1 |
| 11 kHz | +3.7 | 207.9 | | 1000.68 kHz | +0.7 | 409.0 |
| 14 kHz | +3.6 | 209.5 | | | | |
| 18 kHz | +0.7 | 408.6 | | | | |
| 50 kHz | +0.9 | 391.0 | | | | |

- 峰在 `Δf = m·982.68 kHz`（= f_work/SPS），峰旁 **8.62 kHz** 第一零点，
  `982.68k+8.62k = 991.30 kHz` 第二零点 → 零点梳齿间距 `f_work/(SPS·N)=8.62 kHz`。
- 与既有 Python 报告（`测试报告_X410双TX_jammer_CFO零点.md`）**逐点一致**。

## 7. DPDK 带干扰扫率（管理口接通后）

DPDK 真正生效（`mgmt_addr=192.168.20.133,addr=192.168.10.2,use_dpdk=1`，EAL + mlx5_pci，
`--max-fragment-size 262144`）。**带干扰** = 双 TX + jamming（code10 preamble，Δf=491.34 kHz，
jam-gain 60 / jam-scale 0.3），CIR 全链开启，`--no-udp`。

### 7.1 app 实测（30 s，taskset -c 2-19）

| 速率 | echo_ok / pulses | echo_fail | echo_late | underflow | seq/time | res_drop | est_drop | CIR |
|---|---|---|---|---|---|---|---|---|
| 100 Hz | 3000/3000 | 0 | 20 | 0 | 0 | 0 | 0 | 3000/3000 |
| 200 Hz | 6000/6000 | 0 | 60 | 0 | 0 | 0 | 0 | 6000/6000 |
| 300 Hz | 9000/9000 | 0 | 330 | 0 | 0 | 0 | 0 | 9000/9000 |
| 400 Hz | 12000/12000 | 0 | 720 | 0 | 0 | 0 | 0 | 12000/12000 |
| 500 Hz | 15000/15000 | 0 | 700 | 0 | 0 | 0 | 0 | 15000/15000 |

- **每一拍的 TX burst 与 CIR 帧都完成**（`echo_ok == pulses`、`cir ok == pulses`），
  `res_drop = est_drop = 0`，DPDK 下 **underflow ≈ 0**（仅启动 0–4 个，属 startup）。
- 唯一未达 §9.2 硬门槛的是 `echo_late`：100–500 Hz 均非 0，随速率上升。
  经定位（§7.3）为**随机 worker 停顿**，不是带宽/容量问题。

### 7.2 200 Hz 60 s（taskset，带干扰固定频）

`echo_ok=12000/12000`、`echo_fail=0`、`underflow=0`、`seq/time=0`、
`res_drop=0`、`est_drop=0`、`cir 12000/12000`、`late=120`（1.0%）。

### 7.3 关键定位

1. **`max_fragment_size` 是真实吞吐旋钮**：默认 65536 时每拍每通道 3 次 send，
   300 Hz `late=90–120`；改成 **262144（整拍 1 次 send）后同样条件 `late=0`**（10 s 短测）。
   app 已暴露 `--max-fragment-size`，默认改为 262144。
2. `get_time_now()` 的 MPM RPC 延迟稳定（p50 107 µs、p99 108 µs、无 ms 尖峰），
   不是停顿来源。
3. `late` 在相同配置下 30–60 s 内从 0 波动到数百，`worker_max` 偶发 250 ms–1.2 s；
   把 app 移出 DPDK 的 core 0/1（`taskset -c 2-19`）后 200 Hz `late` 140→60，
   方向正确但未清零 → 仍有宿主侧偶发停顿。
4. 分段（200 Hz 稳态，µs/拍）：`tx_send≈3.1–3.6 ms`（等 t_tx 的阻塞等待）、
   `rx_collect≈0.8–1.3 ms`、`pdu_build≈0.55–0.86 ms`、`pdu_pub≈5 µs`、`issue_rx≈5 µs`；
   `worker_mean ≈ PRI`。

### 7.4 本轮新修缺陷

- **jam app 从未调用 `base.resolve_dpdk_args(a)`**（base/sweep 都调了）：`--use-dpdk`
  只打印了 `dpdk_transport` 横幅，设备参数仍是 kernel UDP，`use_dpdk=1` 从未下发
  （表现为 `underflow=44261`）。修复后 DPDK 生效，`underflow → 0`。
- `--max-fragment-size` 暴露并默认 262144（见 7.3.1）。
- **`diag_async.py` 跑飞（10 GB 内存 + 不退出，2026-09-19 现场）**：
  `publish_native=0` 的语义是"满窗"（`uwb_realtime_echo_timer.h:462`），
  `publish_burst` 因此每拍把整个 RX 窗放到 `burst` 消息（rx=211192 → ~825 KiB/拍）；
  旧脚本又把 `burst` 接到无上限的 `blocks.message_debug`，12000 拍 ≈ 10 GiB，
  把宿主推进 swap（其自身测到的 `worker_max` 抖动被此放大，属自污染）。
  另外 `timeout … sudo … python` 的信号未可靠传到孙进程，脚本又卡在逐条
  `pmt.to_python` 转换大消息的收尾循环，所以既不退也不释放。
  已修：`burst` 不再连接（`late_slot_skip` 事件本就来自 `status` 端口），
  只保留 `LateSink`；并加进程内硬超时 + SIGTERM/SIGINT 的 `os._exit` 兜底。
  调用改为 `sudo -E timeout -k 5 <sec> python3 …`（timeout 放在 sudo 内侧）。

### 7.5 结论

**带干扰双 TX 的实测功能上限为 500 Hz**（所有 burst + CIR 完成、0 underflow、0 下游 drop）；
`late` 是当前唯一未达标的门，根因是宿主偶发停顿，需要进一步做 CPU 隔离/优先级，
不能靠降速掩盖。200 Hz 已完成 60 s（§7.2），**10 min soak 与 300 Hz 3×60 s 验收未做**。
