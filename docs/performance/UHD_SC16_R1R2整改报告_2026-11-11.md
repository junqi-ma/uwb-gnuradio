## 1. R1：大间隔 schedule 不得触发假 EOF

### 1.1 根因（复核原文复现）

`uwb_uhd_sc16_pipeline.cc` 的 `rx_producer_loop()` 只在**外层窗口循环**释放严格早于
`win_start` 的样点；内层读循环跨 gap 时只读不放。gap 数据填满 `storage_cap` 后
`room=0`、`to_read=0`，仍调用 `source->read_samples(..., 0, ...)`；
`ReplaySc16Source` 把 `max_samples == 0` 当作 EOF 并永久置 `eof_=true`，于是窗口被
取消、外层 `break`，**后续窗口不再 offered**，进程仍返回 0。

### 1.2 修复

- 新增 `release_before(limit)`：把 live 区释放到 `min(limit, read_end_abs)`，保持
  `valid_begin/valid_n/valid_start_abs/read_end_abs` 一致；在**每个窗口开头**和
  **每次内层读之前**调用。live 区从此不超过 `capacity + 当前读片`，与 gap 无关。
- `to_read == 0` 不再调用 source；记录 fatal source error、`offered+cancelled`、停止。
- 连续 16 次 `n_read == 0 && !is_eof` 判为无进展 fatal；`n_read > 0` 复位。
- source failure 先于 `meta.is_eof` 检查，绝不降级为正常 EOF；真实 EOF 语义不变。

### 1.3 复现对照（同一输入、同一命令）

| 场景 | 修复前 | 修复后 |
| :--- | ---: | ---: |
| baseline `7ddea4c`：period=100000/capture=4000/max=2 | 2/2 | — |
| `170c551` 修复前：同参数 | 2 offered / **1 completed / 1 cancelled** | — |
| 修复后：同参数 | — | **2/2 completed，cancelled=0，exit 0** |
| 修复前：capture=56000，`--t0 100000`，max=1 | **0/1 completed** | **1/1 completed** |
| 修复前：capture=4000，period=40000，max=6 | **2/6 completed**，run 提前结束 | **6/6 completed** |

修复后 `repro-gap.json`：`source_started=true`、`source_failed=false`、
`source_error=""`、`ledger_invariants_ok=true`，读取样点 106,304（gap 分片读过）。

### 1.4 新增 QA

## 2. R2：source 启动失败必须可查询并影响退出码

### 2.1 接口

`UhdSc16Pipeline` 新增：

```cpp
bool source_started() const;      // start_stream() 返回 true
bool source_failed() const;       // 启动失败或 fatal RX 错误
std::string source_error() const; // source_failed() 时的首个原因
```

语义：`ready_ok()` 仍只表示 **Worker 就绪**；`failed()` 现在表示
`任一 Worker Failed || source_failed()`；`init_error()` 在无 Worker 错误时回退到
`source_error()`。状态在 `start()` 与成功的 `initialize()` 后复位；
RX 线程写错误串（互斥量）并 release 发布失败标志。

### 2.2 runner

- 读取三个 accessor，JSON meta 新增 `source_started/source_failed/source_error`；
- `runtime_ok = ready_ok && !failed() && ledger_ok && source_started && !source_failed`；
- **先写 JSON/CSV，再在 `!runtime_ok` 时返回 1**，stderr 列出全部判定项；
- 正常 EOF/用户 stop（source 已启动且无错误）仍返回 0。

### 2.3 新增 QA

- `test_pipeline_source_start_failure`：`start_stream=false`，断言
  `wait_ready()` 仍成功、`start_stream_calls()==1`、`ready_ok()==true`、
  `source_started()==false`、`source_failed()==true`、`failed()==true`、
  `init_error()==source_error()` 非空、0 窗、账本守恒。
- `test_pipeline_zero_read_recovery`：`{0,0,137}` 循环，全部窗完成、
  `read_timeouts>0`、source 不失败。
- `test_pipeline_zero_read_forever`：`{0}`，<5 s 内终止，1 offered/1 cancelled，
  `source_failed()==true`。
- 新增 shell CTest `uwb_qa_sc16_pipeline_runner_exit`：
  不存在的 `--file` → 非零；合法 56k 窗 → 0 且 JSON 的
  `source_started=true`、`source_failed=false`、账本 PASS、1/1/1。

## 3. R3：流控等待与真实文件读取分项

`benchmark_sc16_pipeline_steady.cc` 的 feeder 现在分别计量：

- `feeder_flow_wait_us`：仅 `maybe_wait_for_flow()`；
- `feeder_read_us/calls/bytes`：仅 `::read()` 系统调用（不含流控、不含 `lseek` 重启）。

因此旧报告中的 `rx_read_us`（覆盖整个 `read_samples()`）不能再解释为
“224 KB @ ~0.9 GB/s 的 RX 硬下限”。**旧报告 §5.1“74 µs/窗”、§5.3“250 µs/窗”、
§6.3 第 3 条的 RX 带宽归因撤回**，待用同一 run 的分项配对复测后重写；
ABBA 的端到端时间差值本身不因此失效。

## 4. R4：ABBA 配对复算

`summarize_sc16_round2.py` 保留池化描述表，新增按 `(config, pair)` 的配对表：
`ctrl=(slot0+slot3)/2`、`cand=(slot1+slot2)/2`、`delta=100*(cand-ctrl)/ctrl`。
使用既有 `data_sc16_round2/FINAL` 原始数据复算 56k 六格（每格 5 个完整组）：

| 配置 | 池化中位（旧） | 配对中位 | 配对 min | 配对 max | 配对裁决 |
| :--- | ---: | ---: | ---: | ---: | :--- |
| 56k-rt-n1 | −8.3% | **−8.37%** | −10.02% | −6.36% | ≥5% 下降 |
| 56k-rt-n2 | −7.8% | **−7.37%** | −8.33% | −2.92% | ≥5% 下降 |
| 56k-rt-n4 | −8.4% | **−5.77%** | −14.78% | −3.13% | ≥5% 下降 |
| 56k-q-n1 | −3.3% | **−3.34%** | −3.79% | −1.77% | 5% 以内 |
| 56k-q-n2 | −6.2% | **−5.60%** | −5.92% | −2.42% | ≥5% 下降 |
| 56k-q-n4 | −6.4% | **−5.59%** | −7.29% | −2.66% | ≥5% 下降 |

与旧表的关键差异：

- `56k-q-n1` 的池化 −3.3% 曾被标为“超出噪声”，按 5% 门槛实为 **未达标**；
- `56k-rt-n2` 的池化 IQR 重叠曾被标为“噪声内”，配对 5 组全部下降，
  中位 −7.37%；
- `56k-q-n4` 的 `resample_us_mean` 池化 −4.9% 被标“超出噪声”，配对中位
  −4.15%，**未达 5%**。

4k 各格仍受单次运行 2–10 倍离群值影响，不据此作统计裁决。配对表是描述性
统计（无置信区间、无显著性检验），旧报告的“IQR 不重叠 = 超出噪声”不再作为
统计结论。
