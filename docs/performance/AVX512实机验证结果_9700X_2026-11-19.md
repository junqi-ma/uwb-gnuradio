# AVX-512 实机验证结果（AMD Ryzen 7 9700X，2026-11-19）

对应指南：[AVX512实机验证指南_9700X_2026-11-19](AVX512实机验证指南_9700X_2026-11-19.md)。
本文只记录本轮在 9700X 上的**实测**结果；未做的项目在文末明确列出。
原始日志与 JSON 见 `data_avx512_9700x_20261119/`（约 4.7 MB，仅本机留存，未随本报告入库，见 `.gitignore`）。

## 0. 结论摘要

| 项目 | 结果 |
| --- | --- |
| 硬件/ISA | AMD Ryzen 7 9700X；`avx512f/bw/dq/vl` 全部支持 |
| 基线提交 | `d03a4b3612834be7f28842516f24567e5cb71034`（`feature/sic-research`） |
| 双构建 | `build-avx2`、`build-avx512` 均成功（RC=0） |
| 指定 CTest（6 项） | **5 通过 / 1 失败**：`uwb_qa_uwb_resampler_transposed.cc` |
| 单独 QA | `resampler_avx512` 11/11 通过；`demod_sic_avx512` 21/21 通过；`resampler_transposed` **7 处断言失败** |
| 重采样微基准 | AVX-512 transposed 全面领先，**1.23x / 1.40x / 1.52x**（eq16 / realtime / quality） |
| 端到端回放（4 worker） | FCS 与 AVX2 基本一致（195–197/222）；**eq16、realtime 的 `resample_mean` 出现 AVX-512 反超（变慢），quality 正常变快** |
| 端到端回放（1 worker） | FCS 受单 worker 丢窗强烈影响，无法作为稳定 A/B；单窗口 resample 中位数与微基准同向 |

**最重要的两件事：**

1. `uwb_qa_uwb_resampler_transposed.cc` 在 AVX-512 构建下必然失败，原因是**测试选择器把“主内核”硬编码成 AVX2**，与核心自动选择的 `transposed_avx512` 不一致；AVX-512 内核本身对双精度参考的数值测试是全部通过的。这是测试代码缺陷，不是本轮 DSP 内核回归。
2. 端到端 4 worker 的 eq16/realtime 出现 **AVX-512 `resample_mean` 比 AVX2 慢约 1.6x / 1.3x** 的可重复现象；该现象在隔离微基准、4 进程并发、同进程 4 线程独立内核下均**不能复现**，1 worker 下方向相反（AVX-512 更快）。因此它更像是 live 多 worker 场景下的交互/资源竞争问题，需后续定位；**不能据此判定 AVX-512 内核退化，也不能忽略**。

### 3.3 失败根因（已定位）

`gr-uwb/lib/qa_uwb_resampler_transposed.cc:69`：

```cpp
const char* primary_kernel()
{
#if UWB_SIMD_LEVEL >= 1
    return "avx2";
#else
    return "scalar";
#endif
}
```

在 `UWB_SIMD=AVX512` 构建中 `UWB_SIMD_LEVEL=2`，但该函数仍返回 `"avx2"`，于是：

- `TransposedResampler direct(taps)` 被显式固定为 **AVX2**（`transposed_avx2`）；
- `Core core(taps); core.set_kernel("transposed")` 走
  `enable_transposed("auto")`，`resolve_kernel()` 在 AVX-512 构建中自动选择
  **`transposed_avx512`**；
- 后续内核名比较和 `memcmp` 实际是在比较 **AVX-512 与 AVX2 的输出**，必然失败。

旁证：

- 同一测试的 `test_transposed_65_48_all_profiles` /
  `test_transposed_65_32_all_profiles` / `test_transposed_production_450k`
  全部通过；其中 `check_tap_set()` 已显式覆盖 `"avx512"` 内核，并以
  双精度 `reference_upfirdn` 在 `1e-5` 容差内比较（`n=0,47,1024,56000`、
  rails/impulse、非对齐指针）。
- 同一测试在 `build-avx2` 下 4/4 通过（因为 direct 与 core 都解析为 AVX2）。

**结论**：AVX-512 transposed 内核的数值正确性未被否定；失败来自 QA 的
“主内核”选择逻辑没有跟随 `UWB_SIMD_LEVEL=2`。按测试自身意图，`primary_kernel()`
在 AVX-512 构建应返回 `"avx512"`。本次**未修改仓库代码**，也未验证修正后的
`memcmp` 是否逐位通过（修正后 direct 与 core 会调用同一 AVX-512 实现，预期一致，
但未经实测确认）。

## 4. 重采样微基准（450,000 样本窗口）

### 4.1 方法与命令修正

指南中的 `--kernel c1_fixed_phase` **不是合法内核名**，基准会报
`RationalResamplerLmCore::set_kernel: unknown c1_fixed_phase`。
`c1_fixed_phase` 是“C1 宏块 + `--fixed-phase 1`”的配置标签，正确用法是
`--kernel default`（或不传 `--kernel`）。本轮 C1 基线使用：

```bash
env -u LD_LIBRARY_PATH taskset -c 5 \
  ./gr-uwb/build-<X>/apps/benchmark_sc16_burst_core \
  --taps testdata/resampler_65_48/taps_<profile>.txt \
  --length 450000 --reps 30 --warmup 10 \
  --fixed-phase 1 --window-mode 1 --kernel default|transposed
```

每个 (profile, kernel) 按 **AVX2 → AVX512 → AVX512 → AVX2**（ABBA）跑 2 轮，
下表取两轮均值的中位数。绑核 CPU 5；governor `performance`。
原始文本：`bench_matrix2.log`；逐次 JSON：`bench_json/`。

### 4.2 结果

加速比（AVX2 / AVX512，mean）：

| profile | C1 fixed-phase | transposed |
| --- | ---: | ---: |
| eq16 | 1.04x | **1.23x** |
| realtime_minorder | 1.20x | **1.40x** |
| quality_minorder | 1.45x | **1.52x** |

实际选中的内核（基准自报）：

- eq16 C1：两构建均为 `avx2_fma_macroblock`（按设计的保守选择）。
- realtime / quality C1：AVX512 构建自动升级为 `avx512_fma_macroblock`。
- transposed：AVX2 构建为 `transposed_avx2`，AVX512 构建为 `transposed_avx512`。

### 4.3 观察

1. **transposed + AVX-512 稳定领先**：三档 1.23x / 1.40x / 1.52x，
   p50/p95 与 mean 一致，无明显长尾。
2. **C1 eq16 的 4% 差异不可归因于 AVX-512**：两构建实际执行同一个
   `avx2_fma_macroblock`，校验和也完全相同（`0xe2e85a8a09eddbde`）；
   AVX-512 构建两轮为 593.5 / 570.3 µs，AVX2 构建为 605.9 / 606.2 µs，
   属于代码布局/运行波动，不作为加速证据。
3. **校验和**：C1 三档跨构建完全一致；transposed 跨构建**不一致**：
   - eq16：`0x7ed3be06b67d7e8b`（AVX2） vs `0x470513a55363555a`（AVX512）
   - realtime：`0x57df713b0223c167` vs `0xba328280c0e08fd9`
   - quality：`0xe8a0419add31a1bb` vs `0x97ace2ad62468ad9`
   即 AVX2/AVX-512 transposed **不是逐位一致**，但各自均在 `1e-5` 容差内
   匹配双精度参考（见 §3.3 的 QA 覆盖）。若下游要求跨 ISA 逐位一致，
   需要另行确认；本轮不把校验和不同当作正确性失败。

## 5. 端到端 `uwb_dw3000_live` 回放

### 5.1 数据与参数

- 回放文件：`testdata/x410_fixed_tone_live_20261115/clean_1s.sc16`
  （737.28 MS/s、1 s、约 200 个 5 ms 周期包；这是本机唯一能被当前构建
  正常解码的 1 s SC16 录波）。
- `testdata/dw3000_..._20260825_0{1,2}.dat` 与 `qm35_offline_..._0p2s`：
  当前构建下 `TIMING_FAILED` ≈ 100%，未用于 A/B（避免用全失败数据得出
  伪“FCS 一致”结论）。

命令基线：

```bash
env -u LD_LIBRARY_PATH taskset -c <cores> \
  ./gr-uwb/build-<X>/apps/uwb_dw3000_live \
  --replay testdata/x410_fixed_tone_live_20261115/clean_1s.sc16 \
  --mode continuous --sync acquire --cir full --fused on \
  --workers <1|4> --period-ms 5 \
  --timing-sparse <on|off> \
  --interference off --tone off --print summary --summary 40
```

### 5.2 单 worker（指南要求的耗时口径）

ABBA（A=AVX2，B=AVX512，B，A），绑核 `5,6`。注意：单 worker + `--cir full`
时每包解码约 5–6 ms，而包周期 5 ms，**该配置本身无法实时消化 200 包/s**，
因此队列丢窗（`DROPPED_QUEUE`）和最终 FCS 计数会随调度波动。

| 配置 | 构建 | run | completed | FCS | 唯一包时隙 | OK 包 resample 中位 µs | OK 包 demod 中位 µs |
| --- | --- | --- | ---: | ---: | ---: | ---: | ---: |
| sparse on | AVX2 | a1 | 840 | 98/840 | 98/200 | 473.6 | 6270.9 |
| sparse on | AVX2 | a2 | 467 | 149/467 | 149/200 | 427.1 | 5626.4 |
| sparse on | AVX512 | b1 | 575 | 134/575 | 134/200 | 383.4 | 5631.8 |
| sparse on | AVX512 | b2 | 905 | 82/905 | 82/200 | 459.6 | 6371.7 |
| sparse off | AVX2 | a1 | 376 | 161/376 | 161/200 | 428.8 | 5736.1 |
| sparse off | AVX2 | a2 | 476 | 149/476 | 149/200 | 428.2 | 5726.6 |
| sparse off | AVX512 | b1 | 484 | 150/484 | 150/200 | 394.1 | 5722.0 |
| sparse off | AVX512 | b2 | 603 | 137/603 | 137/200 | 416.4 | 5738.1 |

结论：

- 单窗口 `resample` 中位数：AVX-512 在 4 组可比数据中的 3 组更快
  （383–460 µs vs AVX2 427–474 µs），方向与微基准一致。
- `demod` 基本相同（5.6–6.4 ms，被 Full CIR 主导），AVX-512 的
  16-lag 稀疏匹配滤波在这一段没有量级收益。
- FCS 计数随丢窗大幅波动（82–161/200），**单 worker 不适合做端到端 FCS A/B**。

### 5.3 4 worker：FCS 一致性（补充验证）

为了让 FCS 分母稳定（不丢窗），用 4 worker 重跑（仅用于 FCS 对照）：

```text
cycle1  AVX2   sparse on : 195/222      AVX512 sparse on : 196/222
cycle1  AVX2   sparse off: 197/222      AVX512 sparse off: 197/222
cycle2  AVX2   sparse on : 195/223      AVX512 sparse on : 195/224
cycle2  AVX2   sparse off: 196/224      AVX512 sparse off: 197/222
```

两构建 FCS 成功数只差 0–1 包，差异来自结尾 `INCOMPLETE_WINDOW` 的分母变化；
**未发现 AVX-512 引起的 FCS 退化或改善**。约 200 个包中固定有 4–5 个未被
检测/解码，与该录波的检测特性有关，两构建一致。

### 5.4 4 worker：`resample_mean` 反超异常（重点）

同一 4 worker 配置下（`taskset 0,1,5,6,7`，两轮重复）：

| taps | AVX2 `resample_mean` | AVX512 `resample_mean` | 现象 |
| --- | ---: | ---: | --- |
| eq16（默认） | 447.5–460.6 µs | 713.5–729.2 µs | **AVX512 慢约 1.6x** |
| realtime | 583.6 µs | 760.7 µs | **AVX512 慢约 1.3x** |
| quality | 1099.6 µs | 913.7 µs | AVX512 快约 1.20x（正常） |

对应 `demod_mean` 三档均约 5.2 ms，两构建相同；`compute_mean` 的差异
基本由 `resample_mean` 贡献。

已做的排除性验证（均为临时实验，源码已恢复）：

1. **隔离微基准**（同 taps、同 450,000 窗口、单进程单线程）：
   AVX512 transposed 446 µs vs AVX2 546 µs（AVX-512 更快）。
2. **4 进程并发**（每进程绑不同核，`--kernel transposed`）：
   AVX512 327 µs vs AVX2 402 µs（AVX-512 更快，无退化）。
3. **同进程 4 线程、每线程独立 core、持续负载（800 rep）**：
   AVX512 488–503 µs vs AVX2 568–570 µs；采样频率始终 5.4 GHz，
   无降频（日志 `longrun_build-avx*.log`）。
4. **live 内临时计时探针**（已回退）确认：
   - 实际窗口 `count=450000`，输出 `609396`，内核为 `transposed_avx512`；
   - 4 worker 时该调用本身即 ~730–915 µs，且
     `cpu_us ≈ compute_us`（`CLOCK_THREAD_CPUTIME_ID`），不是被抢占；
   - 1 worker 时同一调用约 444–496 µs。
5. 该现象与输入数据无关（用录波片段替代随机输入，隔离结果不变）。

因此当前可下的结论是：

- **不是** transposed AVX-512 内核在隔离条件下的性能回归；
- **是** live 多 worker（尤其 eq16 + `--cir full`）下的可重复交互现象，
  1 worker 不复现、4 进程/4 线程独立内核不复现、quality 档不复现；
- 机理尚未定位，需后续用 live 全链路 profiling（RX 前端 + 4 worker +
  reporter 同时活跃）继续排查。**在定位前，不建议把 4 worker live 的
  eq16 resample 数据当作 AVX-512 收益或退化的最终结论。**

### 5.5 其他记录

- `uwb_dw3000_live` 的 `PacketProcessor` 构造函数会**无条件**
  `rs_.set_kernel("transposed")`，即当前 live 默认走 RS-5 transposed 内核，
  而不是 C1 宏块。解释 §5.2/§5.4 时应以此为前提。
- 单 worker 回放的 `SUMMARY` 只覆盖最后一批/部分批，故 §5.2 的耗时使用
  逐包 `PACKET ... resample_us/demod_us` 的中位数统计，避免批均值偏差。

## 6. 与指南的偏差

| 指南 | 实际 | 原因 |
| --- | --- | --- |
| `taskset -c 2` | `taskset -c 5`（基准）/ `5,6`、`0,1,5,6,7`（live） | 本会话亲和集为 `0,1,5-7`，CPU 2 不可用 |
| `--kernel c1_fixed_phase` | `--kernel default` + `--fixed-phase 1` | 前者不是合法内核名 |
| 期望 CTest 全部通过 | 5/6 通过 | `resampler_transposed` 测试选择器缺陷 |
| 期望回放 200/200 FCS | 4 worker 195–197/222；1 worker 大幅波动 | 当前构建检测特性 + 单 worker 实时性不足 |

## 7. 建议的后续动作

1. **修 QA 选择器**（测试代码，一行级）：
   `primary_kernel()` 在 `UWB_SIMD_LEVEL >= 2` 时返回 `"avx512"`，
   `>= 1` 时返回 `"avx2"`；然后重跑 `uwb_qa_uwb_resampler_transposed.cc`，
   确认 `core` 与 `direct` 的 `memcmp` 逐位通过。
   若修正后 `memcmp` 仍失败，则说明 core 的 `reset()`/窗口路径与独立内核
   存在真实差异，需要单独排查。
2. **定位 4 worker live 的 eq16/realtime resample 反超**：
   在 live 中同时记录 RX 前端、4 个 worker 的 `CLOCK_THREAD_CPUTIME_ID`
   与频率/功耗，确认是否为 512-bit 执行单元/缓存带宽在多 worker 下的竞争；
   在定位前不要用 4 worker live 数据评估 AVX-512 收益。
3. **考虑为 live 增加重采样内核选择开关**：
   当前 `PacketProcessor` 硬编码 `"transposed"`，无法在 live 中直接 A/B
   `c1` 与 `transposed`，也不利于隔离上述现象。
4. 若要声明跨 ISA 逐位一致，需要明确 transposed 的校验和差异是否可接受；
   当前 QA 只保证对双精度参考的 `1e-5` 容差一致。
