# UHD SC16 第二轮优化独立复核意见

复核对象：HEAD `bd306b3`，对照 `7ddea4c`。结论：暂不验收，存在已复现的 RX 功能回归和失败传播、性能归因问题。未修改生产代码。

## R1 [P1] 大调度间隔使固定 RX 缓冲填满，提前假 EOF

位置：`gr-uwb/lib/uwb_uhd_sc16_pipeline.cc:1280` 附近的窗口释放逻辑及 `1300` 附近 read 循环。

释放旧数据仅发生在外层窗口循环。若 win_start 远大于当前 read_end_abs，内层循环把窗口之前的间隔样点全部留在 storage 中，没有边读边释放。storage 填满后 room=0，to_read 被设为 0，仍调用 source->read_samples。

ReplaySc16Source 对 max_samples=0 返回 EOF，导致尚有数据的源被误判结束。其他 source 若返回非 EOF 的零样点则可能零进展循环。因此“远间隔分块读过且内存有界”的合同未实现。

已用当前 build 与原始 baseline 二进制执行相同命令，输入文件有 6,000,000 点，足够覆盖两窗：

```bash
gr-uwb/build-sc16-burst-opt/apps/uwb_uhd_sc16_pipeline_runner \
  --file testdata/uhd_sc16/sim_preamble_sc16_737m28_rate.bin \
  --native-rate 737280000 --work-rate 998400000 \
  --period 100000 --pre-guard 0 --capture 4000 --post-guard 0 \
  --max-windows 2 --consumer sensing --json-out /tmp/sc16-review-gap.json
```

| 版本 | offered | admitted/completed | cancelled |
|---|---:|---:|---:|
| baseline 7ddea4c | 2 | 2 | 0 |
| candidate | 2 | 1 | 1 |

candidate 仅读取 53,152 样点即退出，返回码 0。复核日志保存在 `/tmp/sc16-review-gap.log`、`/tmp/sc16-review-gap-baseline.log`，JSON 如上。

整改：内层读取过程中及时释放严格早于 win_start 的数据，保证继续读取时有空间；禁止用零长度 read 探测 EOF。补 period 及首窗 t0 均大于 storage_cap 的测试，分别覆盖真实 ReplaySource、short-read 和零读非 EOF fake source。必须核对绝对坐标及全部窗口 IQ；不能仅验证账本守恒。

现有 gap QA 为 period=5000/capacity=2200，没有超过缓冲大小，无法抓到此回归。

## R2 [P2] 新增 source 启动失败未进入失败状态，runner 仍可能成功退出

位置：`uwb_uhd_sc16_pipeline.cc:1200`、`:975`，`uwb_uhd_sc16_pipeline_runner.cc:943`、`:1374`。

start_stream() 返回 false 时 RX 只打印消息并设置 rx_finished；failed() 只检查 WorkerReadyState::Failed，因此源启动失败后 ready_ok/failed 无法反映源失败。尤其 UHD stream command 从 open 移到 start_stream 后，原先 initialize() 可发现的错误转为后台静默失败。

此外 runner 计算 ready_ok、inv_ok 并输出 JSON，却在末尾无条件 return 0（除文件写入错误）。报告关于“失败运行返回非零”的结论未被生产 runner 实现支持。

整改：增加可查询的 pipeline/source 失败状态，明确 Worker ready 与 source running 的区别；runner 对初始化失败、source 启动失败、账本异常返回非零。不要把所有正常 EOF/用户停止一律视为错误。补 start_stream=false 的 fake source 以及 runner 退出码测试。本项为静态代码确认，尚未在 UHD 实机触发。

## R3 [P2] 把 feeder 等待计入 read 成本，错误推导 RX 硬下限

位置：`uwb_uhd_sc16_pipeline.cc:1338` 的 read_ns 计时；`benchmark_sc16_pipeline_steady.cc:199` 的 read_samples 和 `:258` 的 maybe_wait_for_flow。

稳态基准 source 在 read_samples 内先执行 maybe_wait_for_flow；pipeline 的 read_ns 覆盖整个调用。因此报告中约 250 µs/窗包括等待 DSP/提交释放 in-flight 配额，不能解释为 ::read 文件读取时间或 WSL 页缓存带宽上限。

报告同时给出四核约 79 µs/窗与“唯一串行 RX 每窗 read 250 µs 硬下限”，也说明这些口径不能直接用于瓶颈推导。

整改：source 内分别计量流控等待、真实系统调用和其他读处理；在同一 run 上核对分项，不跨运行直接相减。修订报告 §5.1、§5.3、§6.3 等归因。ABBA 的端到端时间差不因此自动无效，但不能用这些诊断认定 RX/load-bound；C2 的端口/带宽归因也应降为假设，除非另有证据。

## R4 [P2] ABBA 采集未按配对差值分析，未完全执行性能验收合同

位置：`tools/performance/summarize_sc16_round2.py:43`。

当前汇总把同变体所有有效运行混在一起求中位数，以两个边际 IQR 是否重叠判断噪声。没有按 ABBA 组计算配对 delta，因此不能等同于任务书的“配对中位数改善”；IQR 不重叠也不是统计置信结论。

整改：保留现有描述统计，同时按 ABBA 组给出两次 A/B 聚合后的配对差值、配对百分比及分布，并据此重新裁决 >=5% 与噪声门槛。先复算现有原始数据，避免无理由重跑矩阵。对无法确定的格明确写不确定。

## 本次验证范围

- 当前候选 build 针对性 CTest：pipeline 与 resampler_burst_opt 两目标通过，合计 5.05 s。
- `compare_pipeline_windows.py --self-test`：19 项通过。
- 额外大间隔两窗用例：baseline 通过、candidate 失败，见 R1。
- 静态检查新 RX、ready/失败传播、惰性调度表、基准 feeder 和汇总逻辑。
- 未重跑全量 CTest、完整性能矩阵或 UHD 实机；未将已有测试通过解读为 R1 等缺陷不存在。

建议保留 A1/C1 的代码与已有收益证据，先修复 R1/R2，修正 R3/R4 的测量结论，再决定最终验收。修复后至少复跑大间隔/首窗偏移/重叠窗/停止/源失败、核心位级 QA 和最终串行全量测试；影响 RX 节奏的修改需配对复测代表格。
