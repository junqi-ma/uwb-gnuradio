## 三、审查发现的缺陷与整改建议

### R1 [中优先级] `[SUMMARY]` 实时日志的 `rate` 计算分母误用累计运行时间

- **位置**：
  - `gr-uwb/lib/uwb_pipeline_output_writer.cc:737-743`
  - `gr-uwb/lib/uwb_pipeline_output_writer.cc:782`
- **现象与根因**：
  - `emit_summary()` 在每次输出 `[SUMMARY]` 后会将 `sum_windows` 重置为 `0`（L782），但计算速率时却除以自运行开始以来的累计时长：
    `const double secs = std::chrono::duration<double>(now - run_start).count();`
    `const double rate = secs > 0.0 ? static_cast<double>(sum_windows) / secs : 0.0;`
  - 在 `B64_jam`（`--live-log summary --live-log-interval-ms 5`）实测中，连续两行同样处理 4 个窗口的摘要显示出不断衰减的假速率：`[SUMMARY] win=4 rate=46.2/s ...` $\to$ `[SUMMARY] win=4 rate=43.3/s ...`。
  - 此外，当摘要间隔较短（如 `--live-log-interval-ms 1`）时，启动初始化窗口尚无数据时也会按周期持续输出空闲行 `win=0 rate=0.0/s`。
- **整改建议**：
  1. 若定义为“本摘要周期瞬时处理速率”，应以 `now - last_summary`（区间时长）作为 `rate` 的分母，并在计算时做好最小正时长保护；若定义为“运行以来平均速率”，则分母用 `now - run_start` 时分子应使用未清零的累计总窗数。
  2. 可选优化：当 `sum_windows == 0` 且运行尚未收到首个窗口（或增加首包到达前抑制选项）时，减少无意义 `win=0` 刷屏。
  3. 在 `qa_uwb_pipeline_output_writer.cc` 增加多周期摘要速率单调性与周期一致性断言。

### R2 [中优先级] `demod_results.jsonl` 中 `predicted_start_sample` 在纯通信模式下恒为 `-1` 且与 SFD 语义混用

- **位置**：
  - `gr-uwb/lib/uwb_uhd_sc16_pipeline.cc:3358-3380`、`3554`
  - `gr-uwb/lib/uwb_pipeline_output_writer.cc:603`
- **现象与根因**：
  - 写入通信解调记录时，`predicted_start_sample` 直接取自工作线程的 `out_pred_sfd`。
  - 但 `out_pred_sfd` 仅在 `if (mode_runs_sensing(cfg_.consumer_mode))` 分支内部计算并更新；因此在 `comm` 和 `sic_plus_comm` 模式下，`demod_results.jsonl` 中所有记录均输出 `"detected_start_sample":553,"predicted_start_sample":-1`。
  - 同时，即便在 `both` 模式下，该字段实际填充的也是 SFD 预测起点而非 SYNC 前导检测的预测起点，与邻近字段 `detected_start_sample`（前导起点）存在命名语义错位。
- **整改建议**：
  1. 明确 `predicted_start_sample` 的协议语义：若表示前导检测的预测起点，应由公共前导/通信调度预测路径提供；若意图输出预测 SFD 起点，建议改名为 `predicted_sfd_start_sample` 或确保在通信路径也可获得对应预测值。
  2. 补充 `--consumer sic_plus_comm` / `comm` 下该字段的契约单测，避免静默输出 `-1`。

### R3 [低优先级] `verify_ucr4_output.py --expect-windows` 未适配纯通信模式

- **位置**：
  - `tools/performance/verify_ucr4_output.py:391-422`
- **现象与根因**：
  - `_check_expect_windows(report, rows, expect_windows)` 无条件检查 `cir.jsonl` 的行数与 `pulse_id` 序列。
  - 在 `B64_clean` / `B64_jam`（`--consumer sic_plus_comm`）输出目录上执行 `--expect-windows 8` 时直接报 `FAIL expect_windows: got 0 jsonl rows, expected 8`（`1 of 16 checks failed`），而未校验 `demod_results.jsonl` 的 8 条记录与 `packet_id` 连续性。
- **整改建议**：
  - 为 `verify_ucr4_output.py` 增加模式识别或 `--expect-comm-windows` / `--mode {auto,sensing,comm,both}` 参数：仅启用通信落盘时按 `demod_results.jsonl` 的行数与 `packet_id` 序列校验窗口预期。

### R4 [低优先级] 纯通信模式下默认仍创建 0 字节 `cir.ucr4` / `cir.jsonl`

- **位置**：
  - `gr-uwb/apps/uwb_uhd_sc16_pipeline_runner.cc:833-836`、`1440-1444`
- **现象与根因**：
  - `OutputPersistenceConfig::write_cir` 与 `write_comm` 默认均为 `true`，需显式传入 `--no-cir-write` / `--no-comm-write` 关闭。在只运行 `--consumer comm` 或 `--consumer sic_plus_comm` 且未额外传 `--no-cir-write` 时，输出目录仍会生成空文件 `cir.ucr4` 和 `cir.jsonl`。
- **整改建议**：
  - 在 runner 参数装配阶段，若未显式覆写输出开关，则根据 `--consumer` 自动对齐默认落盘流（例如纯 `comm` / `sic_plus_comm` 自动设 `write_cir = false`，`sensing` 自动设 `write_comm = false`）。

### R5 [低优先级] 写盘提交热路径临时对象拷贝与退出多刷一次统计

- **位置**：
  - `gr-uwb/lib/uwb_uhd_sc16_pipeline.cc:3543`、`3559`
  - `gr-uwb/lib/uwb_pipeline_output_writer.cc:903`、`956`
- **现象与建议**：
  1. `commit_result()` 开启写盘时在栈上构造临时 `OutputWindowRecord rec;` 会引发一次 `sic_status` 字符串（如 `"committed_preamble_sparse_pulse"`，超过 SSO）拷贝；可直接复用槽位中的目标字段或传入 `std::string_view`。
  2. `writer_loop()` 退出前已在 L903 调用 `flush_all()`，`stop_locked()` 在 join 后于 L956 再次调用 `flush_all()`，导致小流量运行中 `aggregate_flushes` 多统计一次空刷盘（如 8 窗跑出 `aggregate_flushes: 3`）。建议在 `flush_all()` 仅在存在未刷缓冲字节时增加刷盘计数，或去除重复调用。
