# GNU Radio 软件升采样 65/48：结果分析与下阶段建议

> 分析依据：`测试报告_GNURadio软件升采样_65_48.md`  
> 目标速率：737.28 MS/s → 998.4 MS/s（65/48）  
> 测试平台：i7-12700，AVX2+FMA，GNU Radio 3.10.1.1，VOLK 2.5.1

## 1. 当前结果

### 1.1 正确性已达标

- 固定 65/48 core/block 已精确复现 `upfirdn` 契约。
- 7 组 golden 全部通过，最大绝对误差不超过 `4.8e-7`。
- chunk 不变性、EOS、tag、`rx_time`、overflow/reset 均已验证。
- scalar、VOLK、宏块和多 worker 路径结果一致，CTest `11/11` 通过。

因此，当前问题已经不是算法或 GNU Radio 调度语义错误，而是连续满速处理所需算力超过主机实现能力。

### 1.2 连续流性能未达标

| 阶段 | 最优配置 | 输入吞吐 | 输出吞吐 | 实时率 |
|---|---|---:|---:|---:|
| Level A | GNU Radio 内置 default taps | 67.2 MS/s | 91.0 MS/s | 0.091× |
| Phase 2 | 固定 65/48 block，realtime taps | 69.1 MS/s | 93.5 MS/s | 0.094× |
| Phase 3 单核 | AVX2 宏块，realtime taps | 88.1 MS/s | 119.3 MS/s | 0.120× |
| Phase 3 多核 | 20 workers，realtime taps | **217.0 MS/s** | **293.8 MS/s** | **0.294×** |

最优结果相对 Phase 2 提升约 3.1 倍，但距最低实时门槛仍差约 3.4 倍，距 1.2 倍生产余量约差 4.1 倍。连续 CF32 主机升采样方案判定为不满足生产要求。

## 2. 主要瓶颈

1. **FIR 计算是第一瓶颈。** Profile 显示 FIR 占总耗时 87%～97%；数据拼装约 3%～5%，phase/schedule 约 2%～3%，状态维护可忽略。
2. **单核算力不足。** 998.4 MS/s 输出下，quality/realtime 分别需要约 82.9/40.9 GMAC/s；quality 单核理论上即不可行，realtime 即使按理论峰值也缺少生产余量。
3. **多核扩展在约 8 workers 后基本饱和。** realtime 从 8 workers 的 211.2 MS/s 增至 20 workers 仅到 217.0 MS/s。限制来自串行 schedule、线程同步、滑动窗口 cache 冲突、FIR 读带宽及 P/E 核混合超订。
4. **不是基础 flowgraph 搬运瓶颈。** source-only 约 1.4 GS/s，明显高于输入合同；因此继续调整 GNU Radio buffer、chunk 或普通调度参数不会带来数量级提升。
5. **SC16/内存带宽尚不是已证明的主瓶颈。** Level C 可能减少流量，但无法消除 FIR 主导的计算量，不应在缺少新 profile 证据时作为主攻方向。

## 3. 下阶段建议

### 3.1 先做一次有边界的 FIR 降复杂度验证

当前滤波器存在明显的过设计风险：taps 已缩放到 `sum(taps)=65`，频响通带增益约为 `20log10(65)=+36.26 dB`，但设计脚本直接用阻带绝对幅度 `≤ -70 dB` 验收。若规格中的“阻带 70 dB”采用通常的相对通带定义，正确判据应为：

```text
20log10(|Hstop| / |Hpass|) ≤ -70 dB
```

即当前缩放方式下，阻带绝对阈值约为 `-33.74 dB`。原 quality/realtime 报告的绝对阻带约 `-97/-96 dB`，相对通带实际约为 `-133/-132 dB`，远超 70 dB 目标。

按相对 70 dB、通带纹波不超过 0.1 dB 进行初步 SciPy 搜索：

| profile | 当前 taps / 每相 taps | 初步候选 taps / 每相 taps | 计算量变化 |
|---|---:|---:|---:|
| realtime，B=290 MHz | 2635 / 41 | **1319 / 21** | 约降低 49% |
| quality，B=330 MHz | 5363 / 83 | **2749 / 43** | 约降低 48% |

该结果尚不是新的生产滤波器，只说明值得进行一次 **Phase 3.5 最小阶数验证**：

1. 明确规格中的 70 dB 是相对通带还是缩放后绝对幅度；统一 Python、MATLAB 与报告的归一化口径。
2. 以 Kaiser 候选为基线，再用等波纹设计搜索满足同一指标的最小 taps；不得同时降低带宽和阻带指标。
3. 重新生成 impulse/tone/random/UWB golden，并用真实 `testdata/` 验证 packet start、相关峰、解调成功率及 IQ 误差。
4. 对 21/43 taps-per-arm 候选分别测单核与 8/20 workers，不按 taps 比例推算最终吞吐。
5. 若 realtime 候选仍低于 `0.85×` 实时，结束连续主机路径优化并转向 PDU/RFNoC；达到 `0.85×` 后才继续评估能否达到最低 `1.0×` 和生产 `1.2×`。

按 taps 线性估算，realtime 路径可能由当前 `0.294×` 提升到约 `0.57×`，仍不能保证实时；但当前 quality 多核曾达到约 20.7 GMAC/s，已接近 21-tap 候选所需约 21.0 GMAC/s，因此必须用实测裁决，不能提前排除。

不建议优先采用 CIC/IIR 或多级 5/4×13/12：UWB 通带接近输入 Nyquist，首级仍需承担窄过渡带抑制；多级方案还会增加中间流量、相位和边界验证成本。可先做 MAC/s 成本模型，只有理论操作量低于单级最小阶数方案时再实现。

### 3.2 主架构：原生率截窗，再按 PDU 升采样

已知 `t0/T` 的 QM35825 周期旁路场景，应在 **737.28 MS/s 原生采样率**先使用 `UwbScheduledExtractor` 截取所需窗口，只对截出的短 PDU 执行 65/48 重采样，不再对空闲区和无关通信数据做连续 FIR。

该方案把计算量近似缩小为连续流的占空比。按当前 217 MS/s 的实测能力，纯吞吐临界占空比约为 29%；工程上应保留队列、突发和下游处理余量，目标占空比宜控制在 20% 以下，并以实际 slot 长度和频率复测。

实施重点：

1. 固定 737.28 MHz 域的 `t0/T`、窗口长度和绝对样本坐标换算规则。
2. 输入窗口加入足够的 FIR 前后保护区；升采样后按群时延和目标 998.4 MHz 坐标精确裁剪。
3. PDU resampler 复用现有 polyphase core、预分配 scratch 和有界 worker 队列，避免逐包临时大内存分配。
4. quality profile 作为正确性默认档；realtime profile 只有在真实 UWB 检测/解调结果与 MATLAB 等价后才可启用。

### 3.3 建立面向生产场景的验收

- 用真实 `testdata/` 对比 MATLAB：packet start、输出长度、IQ 截取范围及样本值逐 packet 核对。
- 覆盖跨 chunk、跨周期、相邻窗口、overflow/reset、队列满和停流 drain。
- 按实际 slot/s 和占空比测量端到端吞吐、p95/p99 延迟、drop 数及 10 分钟稳定性。
- 将“连续样点吞吐”改为“最大持续 slot/s + 峰值突发承载能力”作为主要生产指标。

### 3.4 备选：RFNoC/FPGA 连续重采样

若必须保留全带宽连续 998.4 MS/s 输出，或实际窗口占空比/突发率超过主机 PDU 路径能力，应把 65/48 polyphase FIR 下沉到 X410 RFNoC/FPGA。主机连续 CF32 方案已触发停止条件，不建议继续投入 AVX2 微调或增加更多 CPU worker。

## 4. 建议决策

**先完成一次有明确停止条件的 FIR 最小阶数复测，修正阻带归一化口径并验证约 50% 的 taps 降幅。无论该实验是否接近实时，主架构仍优先推进“737.28 MHz scheduled 截窗 → PDU 级 65/48 → 998.4 MHz 解调”；只有短 FIR 连续流实测达到至少 `0.85×`，才值得继续争取连续主机实时。若 PDU 路径不满足实际占空比和延迟要求，则进入 RFNoC/FPGA 方案。**
