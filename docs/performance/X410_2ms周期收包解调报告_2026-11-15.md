# X410 2 ms / 1 ms 周期收包与解调报告（2026-11-15）

对象：DW3000 发射周期由 5 ms 依次改为 **2 ms** 和 **1 ms** 后，X410 连续接收 +
原生 SC16 流水线（重采样 737.28→998.4 MS/s、单音消除、target lock、融合 CMF）
的收包与解调表现。§1–§7 是 2 ms，§8 是 1 ms。

基线代码：本工作区未提交状态（`--fused on --cir full` 已设为默认，
整数 chip 网格门限默认 6.468 ppm）。构建目录 `gr-uwb/build-cfo-tail-fix`。

---

## 1. 结论摘要

1. **周期确认 2.0001 ms**（自相关唯一强峰，谐波 4.0001 / 6.0002 / 8.0002 ms），
   1 s 内 500 包。
2. **时钟仍然合格**：CFO +3.62 kHz = 0.56 ppm，周期拟合 −0.50 ppm，
   payload 漂移 0.08 样点，FCS 500/503（99.4%）。
3. **单 worker 撑不住 2 ms**：494 个时隙只提交 342 个，`dropped_queue=152`，
   **丢 31% 的包**，FCS 358/499（71.7%），端到端延迟 66 ms。
4. **2 worker 是 2 ms 下的最优点**：0 丢队列、99.5% 解码、单包 3154 µs、
   延迟 3.9 ms、每个 worker 占用 78% 单核。
5. **4/8 worker 单包更慢且没有任何解码率收益**：compute 3630 / 3594 µs
   （相对 2 worker +15% / +14%），p95 4774 / 4625 µs（+23% / +19%），
   解码率不变（99.5%）。
6. **周期越短，内存带宽越早成为瓶颈**：5 ms 时 W=1→W=4 的重采样只慢 3.6%，
   2 ms 时慢 11%；解调从 +17% 恶化到 +76%。
7. **1 ms（§8）**：周期 1.0000 ms、时钟 0.40 ppm。**必须加 `--raw-blocks 512`**
   （默认 8 MiB 环会丢 62–84 M 样点）；**2 worker 丢 72% 的包，4 worker 是唯一可靠
   配置（3/3 轮 99.7–99.8%，但每个 worker 占 91% 单核，无余量）**；8 worker 反而
   不稳（单包 +20%，3 轮里 1 轮丢样点）。重采样单独就要 **2.04 核**。
8. **0.5 ms 不可行（算术）**：0.5 ms = 368,640 原生样点，比提交窗口 450,000 还短，
   窗口会与下一个包重叠（§8.6）。
9. **1 ms 下窗口有 16.8% 是白跑（代码事实）**：几何只需要 374,217 样点
   （36,864 + 329,161 + 8,192），实际提交 450,000，多出的 75,783 全部在包尾之后。
   按几何裁剪估算可省 0.34 核（§8.6）。
10. **重采样默认抽头从 Hpad 48 改为 Hpad 16（§9）**：原默认不是 32 而是 **48**
    （`taps_quality_minorder`，T=2707）。新增 `--taps`，默认 `eq16`（T=1039）：
    重采样 **−52.6%**、compute −33.4%（2 ms/W=4），1 ms/W=4 每 worker 从
    **92.8% 降到 64.3%**，实机 1 ms 10 s 达 99.81% FCS、0 丢样点。
    四个系数集的失败包**互不重叠**且都是 `tmetric` 掉到 0.67 的对齐边缘包，
    **eq16 没有系统性解码损失**。

## 7. 与 5 ms 的对比：周期越短，多 worker 代价越大

同一台机器、同一份 trim6b 5 ms 采集（`rx_ch3_rx1_1s_trim6b.sc16`）：

| | 重采样 W=1→W=4 | 解调 W=1→W=4 | compute W=1→W=4 |
|---|---|---|---|
| 5 ms | 1798.7 → 1846.9（**+2.7%**） | 984.4 → 1154.9（**+17.3%**） | 2783.2 → 3001.9（+7.9%） |
| **2 ms** | 1846.5 → 2058.9（**+11.5%**） | 890.0 → 1570.8（**+76.5%**） | 2736.6 → 3629.7（**+32.6%**） |

机制：2 ms 下重采样占流的 **30.5%**（5 ms 时 12.2%），4 个 worker 同时执行
65/48 有理重采样，内存带宽被打满；解调阶段的环形缓冲读写同样受限，所以退化更重。

含义：**worker 数的上限随周期缩短而下降**。5 ms 时最多 4 个，2 ms 时 2 个最优。

## 8. 追加：1 ms 周期（2026-11-16）

发射周期再改为 1 ms 后重测。采集 `rx_1ms_1s.sc16`（1.0 s，737,280,000 样点，
0 错误；首次采集在 854 ms 溢出，把 `num_recv_frames` 从 65536 提到 131072 后干净）。

### 8.1 周期与时钟

| 方法 | 结果 |
|---|---|
| 包络自相关 | **1.0000 ms**（ac +1,563,601），2.0001 / 3.0001 / 4.0001 ms 谐波 |
| 0.5 / 1.5 ms 对照 | 负相关（−1.09e6），无竞争峰 |

| 项 | 值 |
|---|---|
| CFO | +2.57 kHz（+1.67 … +3.66） |

| payload 漂移 | **0.06 样点** |
| 周期估计 | −0.37 … −0.45 ppm |

时钟继续变好（0.66 → 0.56 → 0.40 ppm），不是本轮瓶颈。

### 8.2 关键：默认 8 MiB 环在 1 ms 下不够

1 ms 下窗口占流的 **61.0%**（5 ms 12.2%、2 ms 30.5%），主线程要按 1000 窗/s
从单音消除装饰器的有界环里读走 450 M 样点/s。默认 `--raw-blocks 128`（8 MiB，
5.7 ms 余量）不够：

| 配置 | 环大小 | 丢样点 | 不连续 | FCS |
|---|---|---|---|---|
| W=8 默认 | 8 MiB | **62,128,128** | 596 | 835/1409（59.3%） |
| W=8 `--raw-blocks 512` | 32 MiB | 0 | 0 | 1015/1016（99.9%） |

**1 ms 必须加 `--raw-blocks 512`**（32 MiB，45 ms 余量）。

### 8.3 worker 数（`--raw-blocks 512`，3 轮）

| W | 时隙 | 丢队列 | 丢样点 | FCS（3 轮） | 每 worker 单核 |
|---|---|---|---|---|---|
| 2 | 549–576 | **413–440** | 0 | 604/1001、629/1001（60–63%） | **146%（不可能）** |
| **4** | 987–990 | 0–2 | 0 | **1013/1016、1014/1016、1014/1016（99.7–99.8%）** | **91%** |
| 8 | 875–989 | 0 | 0 / 14.7 M / 0 | 99.9% / 85.6% / 99.8% | 55% |

单包耗时（3 轮均值）：

| W | compute | 重采样 | 解调 | p50 | p95 | 延迟 |
|---|---|---|---|---|---|---|
| 4 | 3642.1 | 2040.4 | 1601.7 | 3416.9 | 4911.1 | 5.1–10.1 ms |
| 8 | 4380.6 | 2336.9 | 2043.7 | 4083.6 | 6455.0 | 4.5 ms |

串行线程（每 1 s）：W=4 frontend 287 ms（28.7%）、单音消除 167 ms（16.7%）；
W=8 frontend 378 ms（37.8%）、单音消除 311 ms（31.1%）。

### 8.4 1 ms 的结论

1. **2 worker 完全不够**：`dropped_queue` 413–440，丢 72–75% 的包。
2. **4 worker 是唯一可靠配置**：3/3 轮 99.7–99.8%，但**每个 worker 占 91% 单核**，
   余量只有 9%。任何外部负载都会把它推过线（默认 8 MiB 环时 3 轮里就有 1 轮掉到 93.5%）。
3. **8 worker 反而不稳**：单包 compute 从 3642 涨到 4381（+20%），
   重采样 2040→2337（+15%），3 轮里 1 轮掉样点、FCS 85.6%。
4. **重采样单独就要 2.04 核**（1000 包/s × 2040 µs）。这是 1 ms 下的硬底：
   窗口占流 61%，重采样吞吐 245 MS/s 而流是 737.28 MS/s。

### 8.5 周期与 worker 上限的关系

| 周期 | 窗口占流 | 重采样 W=1→W=4 | 解调 W=1→W=4 | 可靠 worker 上限 |
|---|---|---|---|---|
| 5 ms | 12.2% | +2.7% | +17.3% | 4（8 只是慢，不出错） |
| 2 ms | 30.5% | +11.5% | +76.5% | 2–4（4 略慢但不丢） |
| **1 ms** | **61.0%** | — | — | **4（91% 单核，无余量）** |

**结论：周期越短，重采样占比越高，内存带宽越早成为硬墙。** 1 ms 已经把这台机器
（Ryzen 7 9700X，8 核 13 逻辑）压到边缘；再往 0.5 ms 走，必须先优化重采样本身
（当前 245 MS/s，需要 ≥450 MS/s 才能把窗口占比压回可承受范围）。

### 8.6 再往 0.5 ms 走的结构性阻塞，以及窗口里可回收的 16.8%

**0.5 ms 不可行（算术，不是实测）**：0.5 ms 在 737.28 MS/s 下只有 **368,640** 原生样点，
而提交的窗口是 **450,000** 样点——窗口比周期还长，会与下一个包重叠。要支持 0.5 ms
必须先把窗口压到 < 368,640，但当前几何的最小值是
`pre_guard 36,864 + capture 329,161 + post_guard 8,192 = 374,217`，**已经超过 368,640**。
而且 `capture` 是按 127 B 最大 PSDU 定的（这样窗口容量不依赖待解包的 PHR），
要再压只能牺牲最大包长。所以 0.5 ms 不是调参问题，是窗口几何问题。

**1 ms 下窗口有 16.8% 是白跑（代码事实）**：

| 项 | 样点 | 说明 |
|---|---|---|
| `pre_guard` | 36,864 | 包起点前的保护段 |
| `capture` | 329,161 | 127 B PSDU 的最大包长 |
| `post_guard` | 8,192 | 包尾保护段 |
| **几何需要** | **374,217** | `target_window_geometry::capacity()` |
| **实际提交** | **450,000** | `constexpr size_t window = 450000`（`uwb_dw3000_live.cc:52`） |
| **多出** | **75,783** | **占提交窗口 16.8%，全部落在包尾之后** |

提交点是 `ws = pending_seed - pre_guard`、长度 `window`，所以多出的 75,783 样点
在包尾之后，不参与任何解调。重采样成本与样点数成正比，因此：

```
1 ms / W=4 实测重采样   2040.4 µs
按几何裁剪后（估算）    2040.4 × 374,217 / 450,000 = 1697 µs
每包省                  343 µs
1000 包/s 合计省        0.34 核
```

**这是估算，不是实测**（`window` 是编译期常量，未改）。但它说明 1 ms 下
重采样的 2.04 核里有约 0.34 核是纯粹的窗口超配。

### 8.7 下一步该动哪里

按收益/风险排序：

1. **把 `window` 从 450,000 裁到几何容量 374,217**（一行改动）。估算省 0.34 核，
   1 ms 下每 worker 从 91% 降到约 83%，这是最直接的一步。
2. **只重采样解调真正需要的区间**。现在解调拿到 450,000×48/65 = 332,307 个 work
   样点，而几何只需要 276,345——多 20%。这部分同时影响解调的 coarse scan。
3. **抽头数**：`quality_minorder` 的 `Hpad=32` 换成 `realtime_minorder` 的 `Hpad=16`
   可省一半乘加，但频响余量只有 0.029 dB（见 65/48 等波纹 FIR 实验报告），
   需要先确认 FCS 不掉。

第 1 条和第 2 条合起来，理论上能把 1 ms 的重采样从 2.04 核降到 1.2–1.4 核，
4 worker 的余量从 9% 提到 25% 以上。

## 9. 重采样抽头：默认从 Hpad 48 改为 Hpad 16（eq16）

原默认**不是** 32 tap，是 **Hpad 48**。`uwb_dw3000_live.cc` 加载的是
`taps_quality_minorder.txt`（T=2707），而内核成本正比于
`Hpad = 8*ceil(ceil(T/65)/8)`，不是 T：

| `--taps` | 文件 | T | **Hpad** | 纹波 | 全阻带 | 通带 | 设计 |
|---|---|---|---|---|---|---|---|
| `quality`（原默认） | `taps_quality_minorder` | 2707 | **48** | 0.0050 dB | −70.03 dB | 330 MHz | Kaiser |
| `eq32` | `taps_quality_eq32` | 2079 | 32 | 0.0849 dB | −76.03 dB | 330 MHz | 等波纹 |
| `realtime` | `taps_realtime_minorder` | 1319 | 24 | 0.0053 dB | −70.07 dB | 290 MHz | Kaiser |
| **`eq16`（新默认）** | `taps_realtime_eq16` | 1039 | **16** | 0.0868 dB | −74.56 dB | 290 MHz | 等波纹 |

新增 `--taps eq16|quality|eq32|realtime`，默认 `eq16`。四个系数集都已在
`testdata/resampler_65_48/`，`sum` 都是 65.0000。

### 9.2 速度

**5 ms / W=1 / 2 轮**（无竞争的单包成本）：

| taps | compute | 重采样 | 解调 |
|---|---|---|---|
| quality | 2950.4 | 1925.9 | 1024.5 |
| eq32 | 2445.2 | 1408.2 | 1037.0 |
| realtime | 2118.5 | 1096.0 | 1022.5 |
| **eq16** | **1970.0** | **958.9** | 1011.1 |

**1 ms / W=4 / 3 轮交替**（quality 与 eq16 同批）：

| taps | compute | 重采样 | 解调 | 每 worker 单核 |
|---|---|---|---|---|
| quality | 3711.3 | 2190.3 | 1521.0 | **92.8%** |
| **eq16** | **2570.0** | **1100.2** | 1469.8 | **64.3%** |

重采样降幅与 Hpad 不成正比（48→16 是 3 倍，实测只有 2 倍），说明内核不是纯乘加
受限，有固定的装载/写回开销。

### 9.3 解码质量：eq16 没有系统性损失

先看容易误判的一步：**1 ms 单批测出 eq16 失败 4 个、quality 失败 1 个**，
看起来像 eq16 更差。但把失败包按绝对起点对齐后发现，**每个 tap 集失败的是不同的包**：

| taps | 失败包（绝对起点） |
|---|---|
| quality | 46476111、376777366、721824213 |
| eq32 | 304523967、447556207 |
| realtime | 152644372、640723459 |
| **eq16** | **（无）** |

（2 ms 采集、W=4、3 轮、`dropped_queue=0`，共 ~1500 包/配置。）

而且每个失败包的特征完全一致：**该 tap 集下 `tmetric` 掉到 ~0.67，而同一包在
其他 tap 集下是 ~0.70–0.79**。例如：

```
start=376777366  quality  tmetric=0.6720  → PAYLOAD_FAILED
                 eq16     tmetric=0.7850  → OK
start=304523967  eq32     tmetric=0.6681  → PAYLOAD_FAILED
                 quality  tmetric=0.7808  → OK
```

所以这是**时延对齐的边缘包**（每个系数集的群时延不同：48→1353、32→1039、
24→659、16→519 work 样点），不是滤波器质量。四个系数集在 ~1500 包上的失败率
都在 0–3 个（0–0.2%），且互不重叠。

**结论：eq16 没有系统性解码代价。** 1 ms 下 quality 的 3 个额外失败是那一批
机器负载（`per-worker 92.8%`）造成的过载，不是滤波器。

### 9.4 1 ms 实机复核（eq16，10 s，W=4）

| 目标时隙 | 丢队列 | 丢样点 | FCS | 锁 |
|---|---|---|---|---|
| 8010 | **0** | **0** | **8203/8219（99.81%）** | 14 次进入，0 holdover，0 重捕获 |

单包：compute **2398.8**（p50 2237.6、p95 3267.1、p99 4716.9）、重采样 1062.7、
解调 1336.1、**每 worker 60.0% 单核**（quality 是 92.8%）。周期估计 −0.275 ppm。

**这是 1 ms 第一次有 30% 以上的余量。** 之前 quality 在 1 ms 下每 worker 占
91–93%，任何外部负载都会推过线；现在 60%，可以承受正常波动。

## 10. 必须保留的限制

1. 只测了 2.000 ms 和 1.000 ms 两个周期，没有 3 ms / 4 ms / 0.5 ms 的扫描。
2. 只测了 127 B PSDU、code10、4z2 SFD、STS off 一个 PHY 配置。
3. 实机 10 s 各 1–2 次（1 ms 没有做实机 10 s），且受外部负载干扰
   （loadavg 1.0–4.4），**不构成 P99 或长时间 soak 结论**。
4. 回放是 paced 的，所以"丢队列 / 延迟"反映的是真实实时约束下的行为，
   但绝对耗时仍受机器状态影响（同一配置不同轮次 ±5%）。
   **1 ms 下这个抖动足以翻转结论**：W=4 用默认 8 MiB 环时 3 轮里有 1 轮掉到 93.5%，
   W=8 3 轮里有 1 轮掉到 85.6%。所以 1 ms 只给了 3 轮，不足以宣称稳定。
5. **1 ms 的 `--raw-blocks 512` 是必要但未论证最优的**：只验证了 128（不够）和
   512（够），没有扫 192 / 256 / 384 找最小够用值。32 MiB 环对内存有实际占用。
6. §8.6 的"裁剪窗口省 0.34 核"是**按样点数的估算**，不是实测（`window` 仍是
   编译期常量 450,000）。
7. **抽头切换只验证了 live 收包解调路径**。等波纹报告要求 realtime 档
   （eq16 属于该档：290 MHz 通带、0.0868 dB 纹波）先补 SIC 验证再用；本轮没有
   跑 SIC，SIC + eq16 的组合未验证。
8. **抽头的失败包分析只覆盖 ~1500 包/配置**（2 ms 采集 3 轮）。0.2% 量级的差异
   在这个样本量下只能说明"没有系统性差异"，不能给出精确的失败率。
9. 未验证：UHD 定时命令路径、8 worker 以上的扩展性、多径/AWGN/ISR、
   CFO 扫频与 SFO、MATLAB 交叉验证。
10. 未提交、未推送、未 install。
